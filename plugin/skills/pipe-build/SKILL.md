# /pipe-in:pipe-build — パイプを作る・直す

依頼: $ARGUMENTS

（空なら、新しく作るのか、どのパイプを直すのかと、対象プロジェクトの場所を聞いてから始める）

パイプは1つのフォルダ（`pipe.toml`・`prompts/`・`README.md`）です。書き方は `pipe-in-gen --help` で確かめる。人が読む説明は公開リポジトリの `docs/guide/pipes.md`（https://github.com/nigoh/pipe-in/blob/main/docs/guide/pipes.md）にあります（プラグインには入っていないので、この会話では開かない）。
ここに書いたのは進め方だけです。この会話では、ファイルを書くのは pipe-builder に任せ、自分では書きません。

## 0. 前提を確かめる

- `pipe-in-gen --help` が動くかを確かめる。動かなければ、pipe-in の入れ方（`git clone https://github.com/nigoh/pipe-in.git` で取ってきて、そのフォルダで `pip install -e .`）を案内して止まる。
  pipe-builder の書き込みを絞るフックも `pipe-in-gen` で動くので、これが無いまま先に進まない。
- 対象プロジェクトのフォルダを決める（指定がなければ今のフォルダ。違いそうなら聞く）。
- `pipe-in-gen list --project <対象>` で、ひな形とすでにあるパイプを見る。

## 1. 作るか直すかを決める

- 依頼にある名前のパイプが一覧にあれば「直す」、なければ「作る」。
- 目的だけが書かれていて、近いパイプがすでにあるときなど、どちらとも決められないときだけ聞く。

## 2a. 作る

1. 目的を確かめる：何を作りたいか（成果物）、だれが読むか、どこまでを対象にするか、を一言ずつにまとめる。あいまいな点だけを質問にまとめて聞く（聞かなくても決められることは、決めて伝える）。
2. 対象を読む（読むだけ）：言語・テストのコマンド・ソース／文書／仕様書の場所。
3. 形を決めて見せる：ひな形（`dev` / `diagrams` / `spec-qa`）でほぼ足りるならそれをもとにし、足りなければいちばん近いひな形から段を足す・削る。
   段ごとに、名前・表示名・成果物・`access`・`review`・`bash`・`check`・指示の要点を表にして見せ、確認を取る。決め方は下の「段の決め方」。
   図で組み立てたい人には、VSCode の「pipe-in: パイプ作業台を開く」（作業台）も案内する。

## 2b. 直す

1. `pipe.toml` と `prompts/` を読み、今の段を表にして見せる（名前・表示名・`access`・`review`・`bash`・`check`・つなぎ（`on_fail`・`routes`・`next`・`group`））。
2. 直したい点を聞き、変える点を「前 → 後」の表で見せて確認を取る。
   - 段の名前を変える・段を消すときは、つられて変わる所（ほかの段の `on_fail`・`routes`・`next`、`prompts/` のファイル名、README の段の表）も表に入れる。
   - **権限が広がる変更**（`access` を広くする・`bash`・`web`・`mcp` を足す・`writes` を緩める）には「⚠ 権限が広がる」と印を付け、なぜ要るのかを添えて、はっきり確認を取る。

## 3. pipe-builder に任せる

確認が取れたら、エージェント pipe-builder（一覧では `pipe-in:pipe-builder`）を呼ぶ。渡すもの:

- 対象プロジェクトのパスと、パイプの名前
- 作るときはもとにするひな形、直すときはパイプのフォルダのパス
- 確認が取れた段の表（作るとき）か「前 → 後」の表（直すとき）。表に無いことはさせない
- 確認が取れた権限の変更の一覧（これに無い権限の拡大は、pipe-builder が差し戻してくる）

pipe-builder が差し戻してきたら、理由を人に見せ、表を直して確認を取り直してから、もう一度任せる。

## 4. 結果を伝える

- 変えたファイルの一覧・段の差分の要約・`pipe-in-gen check` の結果・直せなかった点を見せる。
- `⚠` の警告が返ったら、そのまま見せる。直すなら、2b と同じく「前 → 後」の表で確認を取ってから、もう一度 pipe-builder に任せる（`access` を `docs` にするなどの直しは「⚠ 権限が広がる」の印を付ける）。
- 流すコマンドを示す：`pipe-in --pipe <名前> --project <対象> --text "依頼メモ"`（`input` が required なら依頼メモは必須）。
  チャットから流すなら `--pause` を付け、確認の段で `--review approve` / `--review revise --feedback "…"` / `--review quit`（どれも `--pipe <名前>` と一緒に）で答える。
- 記録は `<work_dir>/<名前>/`（既定は `docs/pipeline/<名前>/`）に残る。
  対象が公開リポジトリなら、`docs/pipeline/` を `.gitignore` に入れることと、`.pipe-in/pipes/` の指示文に社内の事情が入っていないかを見てからコミットすることを勧める。
- **流すのは、人に言われてから。** pipe-in を流すと Claude の利用料がかかる。

## 段の決め方

- `access` は、目的を満たす中でいちばん狭い型にする（文書を作るだけなら `read`、別のフォルダに文書や図を置くなら `docs`）。書き込む場所が決まっているなら `writes` で絞る。
- `bash = true` は、テストの実行など本当に必要な段だけ。
- 人が中身を確かめるべき段（方針が決まる段・最終の成果物）には `review = true`。
- 図は Mermaid で書かせる。
- 作った物を確かめる段には `[stages.check]`（`verdict = true` で判定させ、`on_fail` で直す段へ戻す。テストで確かめられるなら `command`）。
- 目的で道が分かれるなら `[stages.routes]`、分岐先の最後には `next`。互いに独立した段は `group` で同時に流す。
- 段の中で手分けしたいときは `[stages.agents.<名前>]`。方針だけを立てさせたい段は `permission_mode = "plan"`。
- サブエージェントは待つ形（`run_in_background: false` を付ける。付けないと裏で動くので止まる）でしか呼べず、`isolation` も付けられない。1回の実行で呼べるのは `max_agent_calls` 回まで（既定 20。`agents` のある段だけに書ける）。手分けの数が多い段だけ、要る数を `max_agent_calls` に書く。サブエージェントの中からさらにサブエージェントを呼ぶと止まる（Claude Code では既定で呼べるが、pipe-in のガードが止める）。段の指示文にもこの呼び方を書いておくと、止められて呼び直す手間が減る。
- Bash を裏で動かす呼び方（`run_in_background: true`）は、どの段でも止まる。
- 試作・図・下書きなど、成果物のほかに置く場所が要る段は `access = "docs"` と `docs_dir`（要るなら `writes` で絞る）にする。`access = "read"` の段は、Bash でも自分の成果物のほかは書けない。
- `agents` のある段の指示文には、サブエージェントを `run_in_background: false` で呼び、全部返るまで成果物を書かないことを書く（返る前に成果物を書いて終えると、批評や採点が抜ける）。
- テストを書く段（`access = "tests"`）は、あとの段に `check.command` があるなら `bash = true` にして、あとの段の `check.command` と同じ検査（lint・型検査・文書の機械検査など）を自分でも流させる。書いたテストがその検査で落ちると、実装の段が直せずに差し戻しが回る。
- 実装の段（`access = "code"`）の指示文には、テストを Bash でも書き換えないこと（直したいテストは理由を成果物に書く）を書く。決まった形の書き込みはガードが止めるが、スクリプトを流すなどのすり抜けの道は残る。
- 検査（`[stages.check]`）の `on_fail` は、指摘を直せる段（`code`・`tests`・`docs`）に戻す。読むだけの段に戻しても直せない。
- 新しい項目や部品を足す段の指示文には、既定のままなら前と同じ結果になること（新しいキーを false にしたら前とバイト同一など）を確かめさせる。前の結果が変わると、どこで悪くなったかを比べられない。
- Web や MCP は、要る段だけに `web`・`mcp` を書く。`web` はできればドメインの一覧で絞り、MCP は読むだけの道具を選ぶ。MCP を使うなら、対象の `pipeline.toml` の `setting_sources` に設定の出どころが要ることを伝える。
- 会話を挟まずに Claude に段を組ませる `pipe-in-gen design` もあるが、利用料がかかるので、人に言われたときだけ使う（pipe-builder には使わせない）。

## 流すとき

- 長い段（実装・批評など）は `max_turns` を足りるだけにする（目安 80〜150。実際に流した経験の値）。足りないと、pipe-in はその段を失敗として止める（成果物を書く前に止まることがある）。
- 対象の `pipeline.toml` の `setting_sources` は、段に読ませる設定の範囲を要るものだけに絞る（例：`["project"]`。手元の user の設定に左右されない）。`["project"]` は `.claude/settings.local.json`（local）も読まないので、要るなら `["project", "local"]` にする。
- 段の始めに SDK が応答を待ちきれずに止まる環境では、流すときに環境変数 `CLAUDE_CODE_STREAM_CLOSE_TIMEOUT`（ミリ秒）を長めにする（例：`300000`）。これは Python 版の SDK のコードが読む変数で、公式の文書には載っていない。
- 1回目は `--pause` で流し、段ごとの成果物と止められた操作（`99_summary.md`）を見てから、指示文を直す。止められた操作が多い段は、`access`・`writes`・`bash` か指示文が合っていない。
