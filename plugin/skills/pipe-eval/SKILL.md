# /pipe-in:pipe-eval — 成果物を検査のコマンドで確かめる

依頼: $ARGUMENTS

（空なら、どのパイプの成果物を確かめるのかを聞いてから始める）

ここに書いたのは進め方だけです。この会話では、検査のコマンドを流して結果を伝えるだけで、成果物・パイプ（`pipe.toml`）・記録（`state.json` など）は書かない・直さない・差し戻さない。
このスキルは人が呼んだときだけ動く。コマンドを流すのは、一覧を見せて返事をもらってからです。pipe-in 本体や Claude を呼ぶコマンドは流さないので、pipe-in の利用料はかからない（渡されたコマンドがかかるものなら、それは人に伝えてから）。
合格・不合格を決めるのはこの検査で、審査（/pipe-in:pipe-judge）の点は人が読む材料です。

## 0. 前提を確かめる

- 対象プロジェクトのフォルダを決める（指定がなければ今のフォルダ。違いそうなら聞く）。`pipe-in-gen` は要らない。
- 記録の場所を探す。対象の `pipeline.toml` の `work_dir`（なければ `docs/pipeline`）の下の `<パイプの名前>/`。開発フローの記録は `work_dir` の直下。新しい名前の置き場所が先で、前の名前のころの場所も読む。
- 記録の `state.json` が見つからなければ、まだ流していないか、場所が違う。検査せずに止まる。「先に `pipe-in --pipe <名前>` で流してください」と伝える（流すのは言われてから）。

## 1. 検査の項目を決める

出どころは次の順です。

1. コマンドが引数で**渡された**ら、それが先。渡されたコマンドごとに 1 項目。`timeout_sec` は 600 秒。
2. なければ、パイプの `pipe.toml` の `[stages.check]` に `command` を持つ段を、段の順に 1 項目ずつ。`timeout_sec` もここから読む（なければ `[stages.check]` の既定の 600 秒）。
3. どちらもなければ、項目は 0 件です。検査することが無いので、流さずに `verdict` を `fail` にして、「検査の項目が 0 件」と伝える（0 件を合格にしない）。

`[stages.check]` の `command` は、`verdict` で判定させる段（`command` を持たない）とは別です。そちらは対象にしない。

## 2. 一覧を見せて返事を待つ

流す前に、項目の一覧を表で見せる：段の名前（`name`）・コマンド・作業フォルダ（対象プロジェクトのフォルダ）・`timeout_sec`。
「流してよいか」と聞き、返事を待つ。返事が来るまで、1 つも流さない。人が一部だけ選んだら、その分だけ流す。

## 3. 流して、結果を返す

- 項目ごとに Bash で、作業フォルダでコマンドを 1 つずつ流す。`timeout_sec` を超えたら不合格にする。
- **終了コード 0 だけが合格**。0 以外、`timeout_sec` を超えた、コマンドが見つからないなど流せなかった項目は不合格（`passed: false`）。理由を `output_tail` に書く。
- JSON を 1 つ返す。

```json
{
  "items": [
    { "name": "<段の名前かコマンド>", "command": "<流したコマンド>", "exit_code": 0, "passed": true, "output_tail": "<出力の最後の 20 行まで>" }
  ],
  "verdict": "pass"
}
```

- `verdict` は、全項目が `passed` なら `pass`、1 つでも不合格か項目が 0 件なら `fail`。
- 出力が長いときは最後の 20 行までを `output_tail` に入れる。秘密らしい文字列（キー・トークン）が混ざっていたら伏せる。

## 4. 結果の後

- 不合格の項目と、`output_tail` から見える原因の見立てを短く添える。見立ては見立てと書く。
- 成果物もパイプも直さない。直すか、パイプに差し戻すかは人が決める。このスキルから自動で直しに行かない。
