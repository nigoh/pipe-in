# /pipe-in:pipe-eval — 成果物を検査する

依頼: $ARGUMENTS

（空なら、どのパイプか聞いてから始める）

検査のコマンドを流して結果を伝えるだけ。成果物・パイプ（`pipe.toml`）・記録（`state.json` など）は書かない・直さない・差し戻さない。
人が呼んだときだけ動き、流すのは一覧を見せて返事をもらってから。pipe-in や Claude を呼ぶコマンドは流さない（利用料のかかるコマンドは人に伝えてから）。
合否はこの検査で決め、審査（/pipe-in:pipe-judge）の点は人が読む材料。

## 0. 前提を確かめる

- 対象のフォルダは、指定がなければ今のフォルダ（違いそうなら聞く）。`pipe-in-gen` は要らない。
- 記録は、対象の `pipeline.toml` の `work_dir`（なければ `docs/pipeline`）の下の `<パイプの名前>/`（開発フローは `work_dir` の直下）。前の名前の場所も読む（新しい名前が先）。
- `state.json` が無ければ、まだ流していないか、場所が違う。検査せずに止まる。「先に `pipe-in --pipe <名前>` で流してください」と伝える（流すのは言われてから）。

## 1. 検査の項目を決める

1. コマンドが引数で渡されたら、それが先。1 つ 1 項目で、`timeout_sec` は 600 秒。
2. なければ、`pipe.toml` の `[stages.check]` に `command` を持つ段を、段の順に 1 項目ずつ（`timeout_sec` もそこから。なければ 600 秒）。
3. どちらもなければ 0 件。流さずに `verdict` を `fail` にし、「検査の項目が 0 件」と伝える（0 件を合格にしない）。

`verdict` で判定させる段（`command` を持たない）は対象にしない。

## 2. 一覧を見せて返事を待つ

流す前に、段の名前（`name`）・コマンド・作業フォルダ（対象のフォルダ）・`timeout_sec` を表で見せる。
「流してよいか」と聞き、返事を待つ。返事が来るまで 1 つも流さない。一部だけ選ばれたら、その分だけ流す。

## 3. 流して、結果を返す

- 作業フォルダでコマンドを 1 つずつ、1 回の Bash で 1 項目だけ流す（ほかの項目と `;`・`&&`・改行でつながない。`; echo "exit=$?"` だけは付けてよく、その値を終了コードにする）。`timeout_sec` を超えたら不合格。
- **終了コード 0 だけが合格**。時間切れ・コマンドが無いなど流せなかった項目も不合格（`passed: false`）で、理由を `output_tail` に書く。
- JSON を 1 つ返す。

```json
{
  "items": [
    { "name": "<段の名前かコマンド>", "command": "<流したコマンド>", "exit_code": 0, "passed": true, "output_tail": "<出力の最後>" }
  ],
  "verdict": "pass"
}
```

- `verdict` は、全項目が `passed` なら `pass`、1 つでも不合格か 0 件なら `fail`。
- `output_tail` は出力の最後の 20 行まで。秘密らしい文字列（キー・トークン）は伏せる。

## 4. 結果の後

- 不合格の項目と、`output_tail` から見える原因の見立てを短く添える（見立てと書く）。
- 成果物もパイプも直さない。直すか差し戻すかは人が決める。自動で直しに行かない。
