# pipe-in-{{name}}：仕様書の指摘（同じ指示の2体の共通部分）

同じ指示の2体が、別々に仕様書の指摘を挙げます。両方が同じ節に挙げた指摘だけを残します。
共通部分を取るのは `pipe-in-gen quorum` で、モデルは呼びません。残った指摘は、引用と出典を `pipe-in-gen findings-check` が機械で確かめます。

## 段

| 段 | 成果物 | 書き込める範囲 | 人の確認 | モデル |
|---|---|---|---|---|
| `review-a`（指摘 A） | `01_review_a.json` | 成果物だけ | なし（同時に流れる） | haiku |
| `review-b`（指摘 B） | `02_review_b.json` | 成果物だけ | なし（同時に流れる） | haiku |
| `quorum`（共通部分） | `03_quorum.md` と `04_common.json` | 成果物だけ | なし | haiku |

`review-a` と `review-b` は同じ指示文（`prompts/01_review.md`）です。読み方は変えません。
`quorum` 段のモデルは確かめて1行書くだけで、共通部分は `check.command` が取ります。どの段も、Bash・Web・MCP は使えません。

## 使いどころ

Haiku など、誤指摘が多いモデルのときに使います。同じ課題を2体に読ませて両方が挙げたものだけを残すと、誤指摘が減ります。
比較実験では、同じ課題を何回か解かせて多く出た指摘を残す方式と F1 が同等で、費用はその69〜80%でした。

## 使わないとき

- 強いモデル（Sonnet）のとき。誤指摘がもともと少なく、1体のほうが共通部分より正しい指摘を落としません。
- 読み方を変えた2体にしたいとき。観点が違うと一致しにくく、共通部分がほとんど残りません。
- 1体で解ける課題のとき。費用が増えるだけです。1体で足りるかを先に確かめてください。

## 仕様書と出典の台帳の置き方

対象プロジェクトに、次の2つを置きます。

- 仕様書：`docs/review-quorum/spec.md`（Markdown 1ファイル）
- 出典の台帳：`docs/review-quorum/sources.json`。仕様書だけなら、次の1件で足ります。

```json
{"v": 1, "sources": [{"id": "SRC-001", "kind": "spec", "title": "仕様書の名前", "version": "1.0", "where": "全体", "file": "spec.md"}]}
```

`file` は仕様書のファイル名（`spec.md`）です。

## 流し方

```bash
pipe-in-gen new reviews --from review-quorum
pipe-in-gen check reviews     # 作ったあとに、誤りと警告が無いかを確かめる
pipe-in run reviews
```

## 3体目は流さない

このパイプは2体だけです。2体の節の一致が低い（0.8 未満）と、3体目が要るかもしれません。
`quorum` 段の command は `--no-third` を付けてあり、要るときも共通部分だけを書いて先へ進みます。
3体目が要るかは、`pipe-in-gen quorum` を `--no-third` なしで手で流すと、終了コード 3 と「3体目が要ります」で分かります。要るときは、同じ指示でもう1体の指摘を作り、3つのファイルを渡して流し直せます（2つ以上のファイルにある節だけが残ります）。

## 気をつけること

- 節の名前（`location.section`）が一致のキーです。仕様書の見出しがゆれる・番号だけの文書では、同じ場所への指摘が一致せず、正しい指摘も落ちることがあります。
- 共通部分に残るのは、両方が挙げた節だけです。片方しか気づかなかった本物の指摘は落ちます。

## 費用の目安

2体と軽い1段で、1体のおよそ2倍強です。

## 限界

比較実験は Haiku が中心で、課題は生成器のものです。60 課題をまとめた数字は、実験のあとの事後の解析です。くわしくは `docs/research/harness-compare/README.md` を見てください。
