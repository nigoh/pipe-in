# 採点の依頼

あなたは採点役です。同じ依頼に対して書かれた2つの「対応メモ」（甲と乙）を読み、下の正解とルーブリックで採点してください。どちらを誰が書いたかは伏せてあります。推測しないでください。

## メモが書かれた依頼

あるプロジェクト（Acme Notes）を、GitHub に MIT で公開し、有料の SaaS で運用し、Docker イメージで顧客に配る前に、ライセンス・許諾の面で「何を、どの順で、どう直すか」をまとめる。読む人は、公開してよいかを決める開発の責任者（法務の専門家ではない）。このメモだけで、公開を止めるべきかを判断でき、直す作業を担当に割り振れることが目的。

## 正解（プロジェクトに実際にある問題）

出す前に直す必要があるもの（10個）：

1. `src/acme_notes/vendor/textdiff.py`：GPL-3.0-or-later のファイルが MIT のプロジェクトに混ざっている。差し替えるか書き直す。
2. `requirements.txt` の PyMuPDF：AGPL-3.0（または有償の商用ライセンス）。差し替えるか、商用ライセンスを買う。
3. `data/sentiment_lexicon.csv`：CC BY-NC 4.0（商用不可）のデータを、有料プランの機能で使っている。差し替えるか許諾を取る。
4. `third_party/fastcache/`：Apache-2.0。ヘッダが NOTICE ファイルに触れているのに NOTICE が同梱されていない。上流の NOTICE を入れる（軽い作業）。
5. `src/acme_notes/utils/retry.py`：Stack Overflow の回答から写したコード（CC BY-SA 4.0）。MIT として出せない。書き直す。
6. `static/fonts/`（Lumen）：OFL 1.1 で「Lumen」が予約されたフォント名。サブセット化（改変）したのに同じ名前で配っている。名前を変えるか、元のファイルをそのまま使う。
7. `static/icons/pro/`：Font Awesome Pro の有償アイコン。公開リポジトリに置けない。外すか Free 版に替える。
8. `src/acme_notes/utils/slugify.py`：python-slugify（MIT）から写したのに、著作権表示と許諾文が無い。表示を足す（軽い作業）。
9. `vendor/gridline-charts/`：Business Source License 1.1、追加の利用許諾なし。本番での利用が認められない。商用ライセンスを取るか差し替える。
10. `src/acme_notes/export/xlsx_writer.py`：他社（Initech）の「社外秘・無断複製禁止」のファイル。権利が無い。外して書き直す。

問題ではないもの（これを「直す必要あり」と書いていたら誤り。念のための確認として軽く触れるのは誤りにしない）：

- `requirements-dev.txt` の pylint（GPL）：開発用だけで、配布物に入らない。
- psycopg2-binary・chardet（LGPL）：手を入れずに依存として使うだけ。
- `third_party/tinyqueue/`（MPL-2.0）：手を入れておらず、ライセンスも同梱している。
- `data/stopwords.txt`（CC0）。
- `redis:7.2-alpine`（BSD のころの版）、flask・requests・react などの寛容なライセンスの依存。
- フォントのバイナリが置き物であること、ライセンス本文が1行に略されていること（依頼で「問題として扱わない」と指定）。

## ルーブリック（甲・乙それぞれ、1〜5 の整数。5 が最良）

- `correct`（正しさ）：上の10個を、原因も対応も正しく扱っているか。事実の誤りが無いか。
- `severity`（重さの判断）：出す前に直すものと、そうでないものを、正解どおりに分けているか。問題でないものを問題にしていないか。
- `decide`（判断のしやすさ）：冒頭を読むだけで、公開を止めるべきかと、その理由が分かるか。直す順が付いているか。
- `action`（作業の具体さ）：誰が・どのファイルを・どう直すかが、そのまま割り振れる細かさで書かれているか。
- `concise`（簡潔さ）：繰り返しや、要らない指摘・前置きが少ないか。読む人の時間を無駄にしないか。

あわせて、甲・乙それぞれについて数える：

- `handled`：10個のうち、正しく扱えていた数（0〜10）。
- `wrong`：事実として誤っている主張の数。
- `false_alarm`：問題ではないものを「直す必要あり」としていた数。

最後に、開発の責任者として受け取りたいのはどちらかを `prefer` に書く（`甲`・`乙`・`同等`）。長いほうが良いとは限らない。

## 決まり

- 読むのは、指定された2つのメモとこのファイルだけ。ほかのファイルは読まない。Web は使わない。
- 答えは、指定された1つのファイルに、次の形の JSON だけを書く。
- 最後の返事は「書いた」の1行だけにする。

```json
{"甲": {"correct": 0, "severity": 0, "decide": 0, "action": 0, "concise": 0, "handled": 0, "wrong": 0, "false_alarm": 0},
 "乙": {"correct": 0, "severity": 0, "decide": 0, "action": 0, "concise": 0, "handled": 0, "wrong": 0, "false_alarm": 0},
 "prefer": "甲", "reason": "1〜2文"}
```
