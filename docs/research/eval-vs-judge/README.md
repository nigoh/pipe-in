# eval と LLM as judge は、出力をどう変えるか

同じ指示で書かせた文に、機械の検査（eval）の結果と、審査役（LLM as judge）の採点を返したり返さなかったりして、出力がどう変わるかを比べた。4条件 × 50本＝200試行を流し、検定にかけた。

- 調べた日：2026-10-19
- 書き手：haiku。審査役：sonnet（どちらも下位のモデルで回した）
- 費用：本番 約 $16（予備実験・作り直し・難しさの調整を合わせて 約 $20）

## 問い

- 書き手に返すものが、eval の結果だけ・審査の採点だけ・両方・どちらも無し、で最終の出力はどう違うか。
- 差は偶然と言えない大きさか。
- 審査役（LLM as judge）は、合否の判定にどこまで頼れるか。

## 結論

1. **決まりを守らせるのは eval。** 最終版が eval に全部合格した割合は、どちらも無し 84%・eval だけ 100%・審査だけ 96%・両方 100%。eval を入れた効き目は +10 ポイント（p = 0.002）。どちらも無しと eval だけ、どちらも無しと両方の差は、6組を比べる補正（Holm）のあとも有意（p = 0.035）。
2. **審査を返すと、審査の点がわずかに上がる。** 審査を入れた効き目は +0.024 点（5項目の平均、p = 0.001）。ただし2条件ずつ比べると、補正のあとに有意な組は無く、効果の大きさは小さい（Cliff の δ ≈ 0.25）。
3. **その差は、審査そのもののぶれより小さい。** 同じ文を2回採点すると、総合点は平均 0.036 点ずれ、合否は 18.5% で食い違った（κ = 0.51）。点を測ったのも同じ型の審査役なので、上がった分には「採点者に合わせて書いただけ」が混ざりうる。
4. **審査は違反に気づいても通す。** eval で落ちた最終版を採点した20回のうち18回で「指示の順守」を下げたが、5項目の平均では8回（40%）が合格になった。
5. **審査の指摘で書き直すと、別の決まりが崩れる。** eval に合格していた文を審査の指摘で書き直すと、21% で決まりが崩れた。eval だけを返すと、字数を合わせるために事実に無い言葉が入る傾向があった（p = 0.058）。
6. **費用は約15倍。** 1試行あたり、どちらも無し $0.0032・eval だけ $0.0035 に対して、審査だけ $0.050・両方 $0.052。

## 方法

### 条件

| 条件 | 2回目以降に返すもの | 止める決まり |
| --- | --- | --- |
| A どちらも無し | なし（1回で終わり） | — |
| B eval だけ | 落ちた項目と実際の値、合格した項目 | eval が全部合格 |
| C 審査だけ | 5項目の点と、直すべき点（最大5つ） | 審査の総合が 0.8 以上 |
| D 両方 | B と C の両方 | 両方 |

- 1回目の指示は、全条件で一字一句同じ。違うのは2回目以降に返すものだけ。書き直しは最大2回（全部で3回）。
- 書き手は道具を使えない（字数は自分で数える）。
- 呼び出しは Claude Agent SDK から直接（道具なし・前置きは最小・設定は読み込まない）。

### 課題

SNS で道具を紹介する3文の短い文（[`topics.py`](topics.py)）。題材は3つで、各条件に 17・17・16 本ずつ割り振り、流す順は混ぜた。

| 題材 | 中身 | 必須語 | 使ってよい英字 | 数字 |
| --- | --- | --- | --- | --- |
| `pipein` | この pipe-in | 要件メモ・テスト先行・差し戻し・VSCode | pipe-in・VSCode | 3 |
| `nightjar` | 夜間バックアップの道具（架空） | 差分・世代・復元・SSH | nightjar・SSH | 7 |
| `leafnote` | 議事録アプリ（架空） | 議事録・決定事項・担当者・Slack | leafnote・Slack | 5 |

決まりは、字数 120〜124・ちょうど3文・1文 38〜44 字・常体・必須語はそれぞれちょうど1回・決めた英字だけ・数字はちょうど1回・読点は1文に2つまで・「！」「？」と絵文字なし・**ひらがなの「の」を使わない**。

### eval と審査

- **eval**（[`evalcheck.py`](evalcheck.py)）：上の決まりを14項目に分けて機械で数える。
- **審査**（[`run.py`](run.py) の `RUBRIC`）：sonnet が「指示の順守・事実の正確さ・分かりやすさ・構成・文体」の5項目を 0.0・0.25・0.5・0.75・1.0 で採点する。総合点と合否は、審査役に計算させず、5項目の平均からこちらで出す。

### 測るもの

1. 最終版が eval に全部合格したか。
2. **伏せた審査**の点：最終版を、条件を伏せて sonnet に2回採点させた平均。

### 検定

- 1 は Fisher の正確検定。2 は並べ替え検定（2万回）と、差のブートストラップ 95% 区間。どちらも6組の比較に Holm の補正をかけた。
- 主効果（eval を入れた効き目・審査を入れた効き目）と交互作用は、題材ごとの層の中でラベルを並べ替えて p を出した。
- 検定はすべて標準ライブラリで書いた（[`analyze.py`](analyze.py)）。数字は [`summary.json`](summary.json)。

## 結果

### 条件ごと

| 条件 | 1回目の eval 合格 | 最終の eval 合格 | 伏せた審査（95% 区間） | 伏せた審査で合格 | 書いた回数の平均 | 1試行の費用 |
| --- | --- | --- | --- | --- | --- | --- |
| A どちらも無し | 42/50 | 42/50 | 0.794（0.776〜0.812） | 32/50 | 1.00 | $0.0032 |
| B eval だけ | 40/50 | 50/50 | 0.801（0.786〜0.815） | 33/50 | 1.22 | $0.0035 |
| C 審査だけ | 41/50 | 48/50 | 0.823（0.810〜0.835） | 43/50 | 1.48 | $0.050 |
| D 両方 | 41/50 | 50/50 | 0.821（0.808〜0.835） | 38/50 | 1.52 | $0.052 |

1回目の合格は条件でそろっている（主効果の p = 0.85・1.0）。差は、返したもので生じた。

### 主効果と交互作用

| 測るもの | eval を入れた効き目 | 審査を入れた効き目 | 交互作用 |
| --- | --- | --- | --- |
| 最終の eval 合格率 | **+10.0 ポイント**（p = 0.002） | +6.0 ポイント（p = 0.10） | −12.0 ポイント（p = 0.10） |
| 伏せた審査の点 | +0.003（p = 0.73） | **+0.024**（p = 0.001） | −0.009（p = 0.58） |

| うち分かりやすさ | 0.000（p = 1.0） | +0.025（p = 0.031） | −0.010（p = 0.73） |

交互作用が負なのは、eval を入れると合格率が 100% に張り付き、審査を足しても上がる余地が無いため。

### 審査役を測る

同じ文を2回採点したときのぶれ（200本）：

| 測るもの | 値 |
| --- | --- |
| 総合点の相関 | r = 0.60 |
| 総合点の差の平均 | 0.036 点 |
| 総合点がぴったり同じ | 94/200（47%） |
| 合否が一致 | 163/200（81.5%）、κ = 0.51 |
| ループの中の最後の審査と、伏せた審査の相関（C・D の100本） | r = 0.39、合否の一致 81% |
| 5段階から外れた点・JSON の読み取りの失敗 | 0・0 |

審査は決まりの違反に気づくか（最終版×2回）：

| | 「指示の順守」を満点にした | 満点より下げた |
| --- | --- | --- |
| eval で落ちた最終版（10本×2回） | 2 | 18（90%） |
| eval に合格した最終版（190本×2回） | 351 | 29（7.6%） |

違反にはおおむね気づくが、違反は1項目の減点にしかならず、ほかの4項目の点で埋まる。eval で落ちた20回のうち8回（40%）は、総合が 0.8 に届いて合格になった。

書き直しで eval の合否がどう動いたか：

| 条件 | 不合格 → 合格 | 不合格 → 不合格 | 合格 → 不合格 | 合格 → 合格 |
| --- | --- | --- | --- | --- |
| B eval だけ | 10 | 1 | 0 | 0 |
| C 審査だけ | 10 | 0 | 3 | 11 |
| D 両方 | 12 | 1 | 3 | 10 |

審査の指摘でも違反はよく直るが、合格していた文を審査の指摘で書き直すと、14回中3回（21%）で決まりが崩れた（字数の超過・「の」の混入・必須語の脱落）。両方なら、崩れたものを次の回の eval が拾う。

英字を禁じた課題で「Claude Agent SDK を入れて」と勧める指摘が、150回中5回（3%）あった。どれも事実の欄に Claude Agent SDK が出てくる `pipein` の題材だった。

### 出力の例

**審査が違反を正しく指摘しながら、合格にした（C・`nightjar`）。** 1回目で止まった最終版。

> nightjarは、毎晩フォルダをSSHで別マシンへ写すコマンド型バックアップ道具だ。前回から変わった差分だけを送るため、二回目以降は初回より速く終わり、負担も小さい。既定で最大7世代まで残し、古い順に消して、日付を指定すればコマンド一つで復元できる。

eval：字数 126（上限 124 を超える）。審査役の理由は「総字数は 43+41+42＝126 字で、上限の 124 字を2字超えている」。指示の順守だけが下がり、総合は 0.80 でちょうど合格。伏せた審査では 0.70・0.75（不合格）。

**eval を通すために、事実に無い言葉を足した（B・`nightjar`）。** 1回目は 119 字で1字足りず、2回目で「別マシンへ**安全に**写す道具だ」と足して合格。「安全」は事実の欄に無い。

## 途中で作り直したこと

- **予備実験（4条件×1〜3本、4つの課題）。** 時間の文字列を秒に変える関数・SemVer の比較・長めの紹介文・短い紹介文。最初の3つは、どの条件も1回目で eval に全部合格し、差が出なかった。差が出たのは短い紹介文だけで、その差も「数字は 3 の1つだけ」という決まりのあいまいさによるものが半分だった。審査役が、英字を禁じた課題に「SDK を入れて」と勧める指摘も、5回中4回出た。そこで、決まりのあいまいさを直し、審査の「分かりやすさ」の観点を「どう始めるか」から「何がうれしいか」に変えた。
- **最初の本番（54本で止めた）。** 「の」の決まりを入れずに流すと、1回目に eval で落ちたのが54本中1本（2%）しかなかった。eval を返す意味が無く、効き目を測れないので止めた。この54本は、上の数字に入れていない。
- **難しさの調整。** 書き手の1回目だけを各30本試した（[`calib.py`](calib.py)）。字数の幅を狭めても、「ちょうど 123 字・1文ちょうど 41 字」にしても、haiku は 83% を守った。いちばん落ちたのは「の」を使わない版（30本中8本）で、これを本番に使った。本番の1回目の不合格は 200本中36本（18%）だった。

## 限界

- **伏せた審査も sonnet で、ループの中の審査と同じルーブリック。** C・D はこの採点者に合わせて書き直しているので、審査の効き目は大きめに出ている可能性がある。別のモデルや人の採点で確かめていない。
- **eval を返した条件は 100% に張り付いた。** eval と審査を組み合わせた上乗せ（交互作用）は測れていない。
- **課題は1つの型（短い紹介文）だけ。** コードや長い文章で同じになるとは限らない。予備実験では、コードの課題は1回目でほぼ全部合格した。
- **書き手は道具を使えない。** 字数を道具で数えられれば、eval で落ちる割合そのものが変わる。
- **難しさは結果を見ながら決めた。** ただし条件どうしの比較には、本番の200試行だけを使っている。

## pipe-in への示唆

- **合否は eval（機械の検査）で決め、審査は中身の指摘に使う。** 開発フローの「検証」の段が `test_command` を判定の裏付けにしている作りと、[D0015](../../decisions/D0015-rubric-judge.md) の「審査の合否は人が読む材料で、自動では直さない」という決め方は、どちらもこの結果と合う。
- **審査をループに入れるなら、eval と組む。** 審査の指摘による書き直しは決まりを崩すことがあり、それを拾えるのは eval。
- **審査で合否を出すなら、平均ではなく「決まりの違反は即不合格」の形にする。** 5項目の平均でしきい値を切ると、明らかな違反が通る。
- **審査の点を比べるなら、何回か採点して平均する。** 1回では合否が 18.5% の割合で入れ替わる。D0015 の残課題（同じ報告を2回採点したばらつき D0015-AC-28、人の採点と照らした確かめ）は、先にやる価値がある。

## やり直し方

Claude Code にログイン済みか、`ANTHROPIC_API_KEY` を設定した環境で、このフォルダから流す。結果は今いるフォルダに書かれる。

```bash
cd docs/research/eval-vs-judge
python3 calib.py nono 10                         # 難しさの確かめ（1回目だけ、題材ごとに10本）
python3 run.py --per-cond 50 --conc 10 --out /tmp/trials.jsonl   # 本番（止まっても続きから回せる）
python3 analyze.py /tmp/trials.jsonl /tmp/summary.json           # 集計と検定
```

- `run.py` は SDK を呼ぶので、利用料がかかる（本番は 約 $16）。
- 難しさは [`topics.py`](topics.py) の `LEVEL` で変える（`base`・`mid`・`hard`・`nono`・`exact`・`combo`）。本番は `nono`。
- 全試行の生のデータ（`trials.jsonl`）はリポジトリに置いていない。
