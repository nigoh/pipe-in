# D0097 プラグインのスキルとエージェントを蒸留して縮める（決まりを残して 26.5% 減・動きを支える理由の文を戻す・採点を振る舞いを見る形に・前後を haiku のラウンドで比べる）

## 目的

プラグイン（`plugin/`）のスキル 5 つ（pipe-build・pipe-eval・pipe-judge・pipe-run・pipe-live）・エージェント 4 つ（pipe-builder・pipe-judge・pipe-stage・pipe-probe）・`stage-rules.md` の文を、名前と呼び方を変えずに、決まりを落とさずに縮めた（合計 61,088 → 44,928 バイト、26.5% 減。監査で見つかった落ちた決まりを戻したあと）。要件メモは「プラグインを蒸留して、スキルやエージェントを濃厚なスキルに圧縮したい」。縮めた前後を、D0096 と同じ haiku（審査役も haiku）の eval のラウンドで比べた。結果の表は [docs/research/plugin-eval-rounds](../research/plugin-eval-rounds/README.md) の「### 蒸留の前後」にある。

### 要求と前提

- UR-01 プラグインを入れている人として、スキルとエージェントの文が短くなり、呼んだときに会話へ読み込まれる量と利用料が減ってほしい。
- UR-02 プラグインを直す人として、文を縮めても決まり（する・しない・止まる・聞く・返す形）が落ちず、haiku の eval の点が下がらないことを、テストと eval で確かめたい。
- UR-03 プラグインを入れている人として、スキルとエージェントの名前・呼び方（`/pipe-in:<スキル>` と引数）・フックの守りは、今のまま使いたい。
- UR-04 あとから読む人として、プラグインの文から外した理由・履歴・出典と、縮めた前後の大きさと点を、リポジトリの文書で読みたい。
- UR-05 プラグインを入れている人として、縮めた版を、更新で受け取りたい。
- UR-06 プラグインを直す人として、eval の点の前後の差が、採点の言い回しの揺れや回の数の違いでなく、文の違い（動きの違い）から来たと言えるようにしたい。（追記）

- 前提：スキルの本文は呼んだときに会話へ読み込まれ、その後のターンにも残る（圧縮のあとも頭の 5,000 トークンまでは付け直される）。エージェントの本文は呼ばれるたびに、新しく作るサブエージェントの文脈の頭（system prompt）に入る（メインの会話には入らない。そこには CLAUDE.md なども入るので、本文を縮めてもその分は減らない）。どちらも利用料になる（`/pipe-in:pipe-build` は `stage-rules.md` を Read して pipe-builder への依頼文に貼るので、`stage-rules.md` はメインの会話とサブエージェントの文脈の 2 か所に入る）。エージェントの `description` は、プラグインを入れた会話のエージェントの一覧に載る。`disable-model-invocation: true` のスキルの `description` は、skills の文書では会話に載らないが、measure の文書は「スキル・エージェントの名前と説明はどのセッションにも入る」と書いていて、公式の文書どうしが食い違う（`claude plugin details` で測れるが、流していない。実機は未確認）。そのため、スキルの `description` を縮めた訳には、`/` のメニューで読みやすくすることも入る（出典：https://code.claude.com/docs/en/skills ・ https://code.claude.com/docs/en/sub-agents ・ https://code.claude.com/docs/en/plugins/measure.md 。監査と助言の V-01・V-02）。崩れる（読み込まれる量が文の長さによらない）と、縮めても量と利用料は減らない。
- 前提：haiku（審査役も haiku）の eval の点は、同じプラグイン・同じコマンドでも回ごとに揺れる（D0096 の `--runs 3` で、judge-rejects-bad-runs が 3 回に 1 回落ちた）。1 回の比べでは、揺れと蒸留による崩れを分けきれない。
- 前提：蒸留の前と後の eval は、同じ Claude Code の版・同じモデルの版（別名 `haiku` が指す版。trace の頭で分かる）・同じケース（`plugin/evals/` に差分が無い）・同じ環境（D0096 と同じ root のコンテナ）で回す。どれかが変わると、点の差は比べられない。
- 前提：haiku は、手順から離れた所に書いた決まりを読み飛ばしうる（D0096 の前提）。縮めるときに、決まりを手順の外へまとめたり、使う場所ごとに置いた文を 1 か所に寄せたりすると、点が下がる。
- 前提：12 本のケースは、決まりの一部しか測らない（測らない枝の例：pipe-live の道具がある会話・pipe-run で段を流す所・pipe-builder の直すときの手順・pipe-stage と pipe-probe の守り）。eval の点が下がらないことは、決まりが落ちていないことの十分な証にならない。測らない決まりは、決まりの一覧のテストと監査で守る。
- 前提：プラグインを入れた人に届くのは `plugin/` だけで、`docs/` は届かない。プラグインの文から外した理由・出典は、入れた人の会話では、公開リポジトリ（github.com/nigoh/pipe-in）の URL で指すほかは読めない。
- 前提：（追記）理由・例・注意の文は、決まりの文と同じく、haiku の動き（どの手順に進むか・止まるか・何を試すか）を決めることがある。d1 で、pipe-builder の理由の 1 文「Bash の中からは書けなくても、Write では書けることがある」を削ると、`new` の失敗のあとに Write での手書きへ進まなくなった。決まりの語が残ることを見るテストだけでは、理由の文の欠けは見つからない。崩れる（理由の文が動きに効かない）なら、戻しても点は変わらず、大きさだけ増える。
- 前提：（追記）言い回しの語だけを見る採点は、正しく止まった・正しく聞いた返事でも、言い換え・英語・別の聞き方で落ちる（d2 の 03-first・04-asks、D0096 の 02-says-command・04-says-no-tools）。その落ちは文の崩れと見分けられないので、言い回しの採点のままでは、0.01 に満たない差を、崩れか揺れか決められない。
- 前提：（追記）前後の点の比べは、同じ採点・同じ回の数のときだけ意味がある。d0 は 3 回、d2 は 3 回と流し直しの 3 回（2 本だけ）で、回の数が前後でそろっていなかった。
- 前提：（追記）`git show HEAD:plugin/…` で取れる文が、蒸留の前の文である（10 のファイルのバイト数が NFR-01 の前の値と同じ・合計 61,088・版 0.6.1）。崩れると、前の写しは比べの基準にならない。
- 前提：（追記）`claude plugin eval` は、リポジトリの外に置いた `plugin/` の写しにも、`./plugin` と同じように当てられる。公式の文書（https://code.claude.com/docs/en/plugin-evals の対象の表）にあり、比べ直しの 3 回で確かめた（結果の既定の置き場所は、その写しの `evals/results/`。D0097 では `--output-dir` で外に向けた）。崩れたら、HEAD を別の作業フォルダに出して当てる（設計 13.6）。
### 状態の問い

答え：いいえ

（追記）FR-17〜20 も、プラグインの文・採点の正規表現・テスト・文書と、メインの測り方を変えるだけで、状態を足さない。
