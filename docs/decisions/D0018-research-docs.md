# D0018 調べた結果を docs/research/ に残す（最初は eval と LLM as judge の比較）

## 目的

実験や比較で確かめたことを、方法・結果・やり直すためのスクリプトと一緒にリポジトリに残し、あとから読む人が数字の出どころまでたどれるようにする。最初の1本は、書き手に eval の結果と審査（LLM as judge）の採点を返す・返さないで出力がどう変わるかを、4条件×50本で比べた調査。

## 機能要件と受け入れ基準

テストは `tests/test_research.py`（下では `::` からの名前だけを書く）。

- FR-01 `docs/research/` を作り、目次 `docs/research/README.md` から、すべての調査のフォルダを指す
  - D0018-AC-01 目次があり、`docs/research/` の下のフォルダをすべて表から指す（`::test_d0018_ac01_index_links_every_study`）
- FR-02 1つの調査を1つのフォルダにし、本文に「問い・結論・方法・結果・限界・pipe-in への示唆・やり直し方」の節を置く
  - D0018-AC-02 `docs/research/eval-vs-judge/README.md` に、その7つの節がある（`::test_d0018_ac02_study_has_sections`）
- FR-03 やり直すためのスクリプトと集計の結果を置き、本文の数と集計の結果を合わせる。生のデータは置かない
  - D0018-AC-03 `summary.json` が 4条件×50本＝200試行で、本文の eval の合格の数と同じ（`::test_d0018_ac03_summary_matches_design`）
  - D0018-AC-04 実験の eval（`evalcheck.py`）が、決まりを守った文を全部合格にし、「の」・字数・数字・英字の違反をそれぞれ見つける。SDK は呼ばない（`::test_d0018_ac04_eval_counts_rules`）
- FR-04 置き場所の表（`docs/development/design.md`）と、開発のルールのテスト一覧（`docs/development/README.md`）に1行ずつ足す
  - D0018-AC-05 design.md の表のパスが実物にある（既存の `tests/test_rules.py::test_place_tables_point_to_real_paths`）
  - D0018-AC-06 手元の事情（ユーザー名の入ったパス・メールアドレス）を載せない（既存の `tests/test_rules.py::test_no_local_info_in_tracked_files`）

## 決めたことと理由

- **置き場所は `docs/research/`。** 決定の記録は「何をなぜ作ったか」を書く場所で、調べた結果（作るものが無いこともある）とは分けた。利用者向けのガイド（`docs/guide/`）でも、開発のルール（`docs/development/`）でもないので、新しい場所にした。
- **スクリプトと集計の結果まで置き、生のデータは置かない（人の選択）。** 数字の出どころをたどれ、だれでもやり直せるようにする。全試行の出力（数 MB）はリポジトリを重くするので置かない。
- **スクリプトは `docs/` の下に置き、本体（`pipe_in/`）には入れない。** 調べるための使い捨ての道具で、利用者の pipe-in の動きには関わらない。`pytest` の対象（`tests/`）からも外れる。eval の数え方だけは、本文の結論の土台なのでテストで守る（D0018-AC-04）。
- **呼び出しは Claude Agent SDK から直接（道具なし・設定を読み込まない）。** サブエージェント経由より1回の費用が大幅に安く、200試行を回せた。
- **書き手は haiku、審査役は sonnet（人の選択）。** 回す数が多いので下位のモデルにした。書き手と審査役のモデルを分けたのは、自分の出力を甘く見るのを避けるため（D0015 の残課題と同じ考え）。
- **1条件 50本、伏せた審査は sonnet で2回ずつ、題材は3つ（人の選択）。** 審査そのもののぶれも測れるようにした。
- **難しさは、1回目だけを試して決めた。** 最初の版は1回目に eval で落ちるのが 2% で、eval の効き目を測れないので54本で止めた。難しさを調整して、本番の比較には調整後の200試行だけを使った。

## 対象外・残った課題

- 伏せた審査を、別のモデルや人の採点で確かめること（今は同じ sonnet で、審査の効き目が大きめに出ている可能性がある）。
- 「決まりの違反は即不合格」にした審査の形を試すこと。
- コードや長い文章の課題で同じ比較をすること。
- 調査の結果を受けて、`pipe-in-judge`（D0015）や開発フローの検証の作りを変えること。変えるときは、別の `/pipe-in` で決定の記録を書く。

## 確かめたこと

- `python -m pytest -q tests/test_research.py`：4 passed。先に書いたテストのうち、目次・本文・集計の3件は、文書が無いという期待した理由で落ちたあと緑になった。eval の数え方の1件は、置いたスクリプトの今の振る舞いを確かめるもので、はじめから通った。
- `analyze.py` を手元の全試行のデータで流し直し、`summary.json` と同じ数（各条件の eval の合格の数と伏せた審査の平均）が出ることを確かめた。
- 本体・拡張のコードは触っていないので、拡張のテストは流していない。
