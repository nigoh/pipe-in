# D0034 work_dir がまだ無いプロジェクトでも、最初の実行でパネルとステータスバーが進むようにする

## 目的

VSCode を開いた時点で work_dir（既定 `docs/pipeline/`）がまだ無いプロジェクトで、最初の実行（`pipe-in record start`・`pipe-in` の最初の段）を流しても、開いておいたパネルとステータスバーが、開き直さなくても進むようにする。この記録は、D0023 の「残った課題」に書いた拡張の不具合（「直すのは拡張のコードなので、別のイシューで扱う」）を扱う（D0023 は書き換えない）。

今までの拡張は、`retarget` で work_dir を基準に見張り（`createFileSystemWatcher` の `RelativePattern`）を 1 つ張るだけだった。D0023 の動画の録画では、基準のフォルダが無いまま張った見張りから知らせが届かず、パネルとステータスバーが進まなかった。公式の文書は「無いパスは、できるまで遅れて見張る」と書くので、録画で見た動きと食い違う。原因は確かめておらず（AC-49）、どちらでも確かに進む形にした。

## 決めたことと理由

### 人が決めたこと（要件定義で聞いた 9 点・設計で聞いた 2 点。どれも推しの案）

- **方式は、`stat` で有無を確かめ、できたら見張りを張る（B）。** 親のフォルダを見張って張り直す案（A）は、VSCode の見張りが親のパスで届くことに頼り、ワークスペースの外の絶対パスや、親が何段も無いときの場合分けが増える。両方（C）は、約 3 秒速くなるだけで部品が増える。B は、D0023 の「残った課題」の原因（見張りの遅れか、届かないのか）がどちらでも、確かに進む。
- **確かめの間隔は 3 秒で、work_dir が有るあいだも続ける。** 消えたことを、見張りの知らせに頼らずに見つけるため。`stat` が 3 秒に 1 回走るだけで、一覧は読まない（「そのまま」では読み直さない）。
- **別の worktree の見張り（`watchRemote`）は範囲に入れない。** 別の worktree が一覧に入るのは work_dir が実在するときだけなので、同じ穴は無い。別の worktree での最初の実行に気づかないのは、D0024 の受け入れたリスクのまま。
- **追い読みを入れる。** 見張りを張る間際に起きた変化を取りこぼさないように、張ったあとの次の確かめで 1 回だけ読み直す。
- **ワークスペースの外の work_dir で、深い場所の変化が届くかは限界として残す**（D0024 も、外の場所には再帰で見張りを張れないと書いた）。手で確かめて記録する（AC-53）。
- **確かめの間隔より短い間に消して作り直したときは対象外**にして、限界をガイドに書く。
- **手での確かめは、修正前の版での原因の切り分け（AC-49）を先に流す。**
- **`docs/assets/README.md` の「空の `docs/pipeline/` も作っておく」は、「以前は必要だった。いまは無くても進む」に直す。**
- **AC-09 の読み替え（設計）：** 最初の確かめの読み直しは、`retarget` ではなく確かめの手順がする。回数（合計 1 回）は要件と同じ。結果で読み直しを分ける判断を `extension.ts` に出さないため（AC-37）。
- **見張りを作るのが例外のとき（設計）：** 最初の確かめだけは 1 回読む（最初の表示を出すため）。2 回目以降は読まず、次の確かめでまた張る。

### 聞かずに決めたこと

- 判断は 2 つの純粋な関数に分けた：`decideWatch`（張る・外す・そのまま）と `finishStep`（読み直すか・次の追い読みの番か）。設計の下書きの 1 つの関数（`planStep`）は、「張れたか」を入力に持てず表と食い違うので、読み手の指摘でやめた。
- 「見張っているか」を知っているのは見張りを持つ部品（`createWatchHolder` の `active`）だけ。手順は「最初の確かめか」「追い読みの番か」の 2 つだけを持ち、読み直しを待つ前に更新する（読み直しが長引いても、次の確かめや `reset()` が前の状態を見ない）。
- 世代を進めるのは呼ぶ側（`retarget`・`deactivate`・購読の片付け）と、確かめを始めるたびの手順。`reset()` は世代を進めない。
- 「分からない」（権限・EIO など）は、見張りにも表示にも触れない。一時的な失敗で、生きている見張りを外さないため。`dirPresence` は、投げられた値が object で `code` が文字なら、`Error` かどうかを問わず `code` で分ける。
- `Presence` の型は app 層に置き、基盤が型だけを読む（`fsWorktrees.ts` が `Place` を読むのと同じ形）。
- 見張りを作る場所は、今までどおり 2 つ（いまの work_dir と別の worktree）。依存・設定・コマンド・メッセージの種類・CSP は足していない。
- 画面の AC は無い（パネルの見た目は変わらない）ので、Playwright での確認はしていない。
- 実装は `pipe-in-coder`、テストは `pipe-in-tester` が書いた。決定の記録はメインが書いた。
- 番号は D0032 → D0033 → D0034 と振り直した（作業のあいだに main に #61 の D0032 と、#65 の D0033（テストだけ先に入った）が入ったため）。README の表の位置を見るテストは、前の番号を決め打ちせず「番号の昇順の位置」を見る。

既存のテストは書き換えていない（`tests/test_guide.py` は末尾に足しただけ）。

### 受け入れたリスク

- **最初の表示が `stat` 1 回分だけ遅れる。** `retarget` は読み直しを直接呼ばず、最初の確かめ（`stat` のあと）で読み直す。work_dir が最初から有るときも同じ（AC-51 で手で見る）。
- **できてから進むまで、最大で確かめの間隔（約 3 秒）ほど遅れる。**
- **フォルダを開いているあいだ、pipe-in を使わないプロジェクトでも、約 3 秒ごとに `stat` が 1 回走る。**
- **確かめの間隔より短い間に消して作り直したときは、変わり目として見えない**（ガイドに書いた）。
- **ワークスペースの外の work_dir で、張った見張りが深い場所の変化を届けるかは確かめていない**（ガイドに書いた。パネルが見えていて、選んだ実行が動いている・確認待ちの間は、約 5 秒の読み直しが補う）。
- 「分からない」が続くあいだは、見張りも表示も変わらない。
