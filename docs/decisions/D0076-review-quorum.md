# D0076 同じ指示の2体の共通部分（`pipe-in-gen quorum`・ひな形 `review-quorum`）を足し、比較実験 R7〜R14 の目安を入れる

## 目的

段の組み方の比較実験の続き（R7〜R14、[docs/research/harness-compare/](../research/harness-compare/README.md)）で、指摘の精度を上げる型として「同じ指示の2体に解かせ、両方が挙げた指摘だけを残す」（2体の共通部分）が、3回解かせて票を数える型と同じ精度を、少ない費用で出した。D0053 で「あとで足す候補（まだ仕組みが無い）」とした票を数える仕組みを、この型として、LLM を呼ばない部品 `pipe-in-gen quorum` と、ひな形 `review-quorum` で足す。あわせて、組み方の目安の文書と調査の文書に R7〜R14 の結果を入れる。

## 機能要件と受け入れ基準

### 機能要件

- FR-01 `pipe-in-gen quorum <指摘のファイル>… --out <書き出す先>` を足す。入力は指摘の形 v1（D0043）のファイルを2つか3つ。LLM も SDK も呼ばず、標準ライブラリだけで動く（`generator/quorum.py`）。
- FR-02 一致のキーは、指摘の `location.source` と `location.section` の組（`findings_check.normalize` でそろえる）。`kind`・`statement`・`quote` は見ない。
- FR-03 2つのときは、1つ目の指摘のうちキーが2つ目にもあるものを残す。3つのときは、キーが2つ以上のファイルにあるものを残す。
- FR-04 書き出すのは指摘の形 v1 のまま。`id` は `F-001` から振り直す。票と一致の数は標準出力に出す。
- FR-05・06 2つのときのキーの集合の Jaccard が基準（既定 0.8）より小さければ「3体目が要る」。終了コードは 0＝書いた・3＝書いたが3体目が要る・2＝入力を受け取れない。`--no-third` で、3体目が要るときも 0 にする。
- FR-07 入力を受け取れないときは、理由を標準エラーに出し、何も書かない。入力は書き換えない。
- FR-08 ひな形 `review-quorum`：`review-a`・`review-b`（同じ指示ファイル・同じ `group`・`findings-check` で自分へ戻す）→ `quorum`（`check.command` が `pipe-in-gen quorum … --no-third && pipe-in-gen findings-check …`、`on_fail = "review-a"`）。
- FR-09 目安の3文書（`generator/design_rules.md`・`plugin/skills/pipe-build/references/stage-rules.md`・`docs/guide/pipes.md`）に「2体の共通部分」の項を足す。
- FR-10 調査の文書に R7〜R14 を足し、結論 4 を書き直す。
- FR-11 D0053 の記録は書き換えない。D0053 のテストのうち食い違うものを直す。
- FR-12 `docs/development/design.md` の置き場所の表に `generator/quorum.py` の行を足す。プラグインの版を 0.5.2 に上げる。
- FR-13 （検証の前に人が決めて足した）警告 W5 は、検査の `command` が戻り先の段の `output` を名指しするときは出さない（`pipe_in/pipe/lint.py`）。

## 決めたことと理由

### 人に聞いて決めたこと

- 一致のキーは「出典＋節」だけ。実験で測った「同じ節」に合わせた。`kind` を足す案・節の包含を同じとみなす案は、実験で測っていないので採らない。
- 3体目はパイプでは流さず、部品が終了コード 3 で知らせるだけにする。今の定義では「`check.command` の結果で次の段を選ぶ」が書けない（`routes` は LLM の選択、`next` は決め打ち）。定義の形を変えるのは重く、実験でも3体目まで流れたのは 60 課題のうち数本だけだったため。
- ひな形は新しく `review-quorum` を作り、`spec-review` は変えない。
- 共通部分を取る段は、モデルを1回呼ぶ軽い段（Haiku・`max_turns` 小）にする。段の間にコマンドだけの段は無く、共通部分は `check.command` で取るため。
- プラグインの版は 0.5.2（`references/stage-rules.md` の中身が変わったので、GitHub から入れた人にも届くように。D0053 の前例）。
- 実装の段で、承認したテストと今の決まりが2か所ぶつかった。段の名前に `_` は使えない（`definition.py` の NAME_RE）ので `review-a`・`review-b` にした。共通部分の段の戻り先を `review-a`（`read` の段）にすると W5 が誤って出るので、人が「W5 を直す」を選び、AC-23 を足して `pipe_in/pipe/lint.py` を直した。`read` の段でも、検査がその段の成果物そのものを確かめているなら、成果物を書き直せば直せるため。D0038-AC-05 のテストは変えていない。

### D0053 との関係

- D0053 の記録の本文は書き換えない。D0053 の「あとで足す候補」のうち、票を数える仕組みを、2体の共通部分として足した。3回解かせて票を数える型そのものは足さない（同じ精度で費用が高いため）。
- D0053 のテストのうち、新しい文書と食い違う2つ（AC-18 の「3体」を書かない・AC-21 の「4 に仕組みが無い」）は、D0076 に合わせて直した（「3体」は「3体の実装」に狭め、仕組みが無いのは 6 と 8 だけにした）。

### 監査と助言で直したこと（人が「全部直す」と承認）

- 監査 A-01：`findings-check` を組み込んでいるひな形に `review-quorum` を足した（`pipes.md`）。
- A-02：`/pipe-help` に `pipe-in-gen quorum` の行を足した。
- A-03：プラグインのガイドの「`pip install -e .` をやり直す」に、`quorum`・`review-quorum`・W5 の例外を足した。
- A-04：調査の文書の「目安に入れた番号」に 4 を足した。
- A-05：`pipe-build` の SKILL.md のひな形の例を5つにした（前からの食い違い。0.5.2 に同乗）。
- A-06：`lint.py` の冒頭の説明に D0076 を足した。
- A-07：`quorum` に3つ渡したときの出力の説明を、実物に合わせた。
- 助言 V-02：プラグインのガイドの見出しを「0.5.0・0.5.1 から更新するとき」にした。
- V-03：自動の更新は公式のマーケットプレイスのほかは既定で切れている、と足した。
- V-04：ひな形の `model = "haiku"` は別名で、指す版は実行時の版で変わりうると、ひな形のコメントに足した。
- 文書係：README と guide の目次の「パイプ」の行に「2体の共通部分」を足し、調査の目次の行を直した。
- 審査（助言の報告の採点）：overall 0.75・verdict pass。Agent SDK の `model` が別名を受けるかを確かめられなかったことで、網羅性が下がった。

### 受け入れたリスク

- 実験は Claude Haiku 中心（R11・R13 は Sonnet も）、生成器で作った課題、方式ごとに 20 課題での結果。R8・R9・R14 の 60 課題をまとめた数字は、事前登録していない事後の解析。ほかのモデルや実際のプロジェクトでは確かめていない。目安の文書にはこの限界を添えた。
- 強いモデルでは逆効果だった（Sonnet で F1 −0.019）。ひな形は `haiku` を指定し、README と目安に「強いモデルでは使わない」と書いた。
- 3体目を流さないので、2体が大きく食い違う課題では、共通部分が正しい指摘まで落としうる。部品は終了コード 3 と標準出力でそれを知らせる（パイプでは `--no-third` で通す）。

## 対象外・残った課題

- 本体の段の流れ・記録・ガード・拡張。
- 3体目を条件つきで流す仕組み（`check.command` の結果で次の段を選ぶ）。
- 実装の複数案を並べて選ぶ仕組み（R10・R12 は調査の文書に書くだけ）。
- 実行をまたいで教訓のメモを持ち越す仕組み。
- Agent SDK の `model` に別名を渡したときの解決先の確かめ。

## 確かめたこと

- テスト先行：新しいテスト 145 件と、設計どおり直した既存のテスト 8 件が、期待した理由（`quorum` がまだ無い・ひな形と文書がまだ無い・版が古い）で落ちた。直し：段の名前のぶつかりを直し、W5 のテスト3件（AC-23）を足し、新しい W5 の1件とそれに依るひな形の3件が期待どおり赤だった。
- 検証（1回で合格）：worktree を入れた環境で `pytest -q` が、この記録を待つ2件のほか通った。手で、一時フォルダにひな形を写して `pipe-in-gen check` が誤り・警告 0 件、`pipe-in-gen quorum` を見本の2ファイルで流し、共通部分・`id` の振り直し・全角と半角の同一視・終了コード 3・`--no-third` で 0・ファイル1つで 2 を確かめた。拡張は変えていないので流していない。
- 調査の文書の数字は、実験の集計と突き合わせた。
- 実機で `pipe-in --pipe` でひな形を流すことは、まだ。
- 公開してよいか：変えたファイルに、秘密・ユーザー名の入った絶対パス・メールアドレス・`docs/pipeline/` の中身は無い。
