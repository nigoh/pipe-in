# D0024 ステータスバーに、並列で動いている実行と確認待ちの件数を出す

## 目的

パイプを並列で流す人が、今見ている実行のほかに、動いている実行や確認待ちの実行があることを、パネルを開かなくてもステータスバーで気づけるようにする。実行が1つのときは、今の出し方（段の名前と状態）を変えない。イシュー #44。`docs/roadmap.md` 段階1「見る」。D0021 の「対象外」にあった「状態バーの件数（#44）」は、この記録が扱った。

## 機能要件と受け入れ基準

拡張（`vscode/`）だけを変える。本体（`pipe_in/`）・記録の形・`pipeline.toml`・`pipe.toml`・パネルのスクリプト・CSP・メッセージの種類・`infra/` は変えない。要件定義では「状態バー」と書き、利用者向けの文書・設定の説明・テストの題では「ステータスバー」と書く（同じもの）。テストは `vscode/src/` の中（ID の頭で探せる）と `tests/test_guide.py`。AC に添えた略称は次のファイル（パスは `vscode/src/` から。`TG` だけリポジトリの直下から）。

#### 数える範囲
- FR-01 件数は、実行の一覧の行から数える（ステータスバーのために新しく読む場所を増やさない）

  - D0024-AC-02 `archive/` の行（前の実行）と、`final` のある実行の行は数えない。（DOM）
- FR-02 いまの work_dir の行と別の worktree の行を、同じ数え方で数える。入る範囲は一覧と同じ
  - D0024-AC-03 いまの work_dir の行と、別の worktree の行（`other` が真）を同じに数える。（DOM）
  - D0024-AC-04 設定 `pipe-in.showOtherWorktrees` が false のとき、一覧に別の worktree の行は無く、数えない。8個を超えて省かれた別の worktree（`omittedWorktrees`）の実行は数えない。（APP）
- FR-03 行の状態は、一覧と同じ判定を使う（図・状態のタブと食い違わない）
  - D0024-AC-05 動いている段と確認待ちの印（`pending_review`）が同じ記録にある行は、行の状態（`'running'`）のとおり「動き」にだけ数え、「確認待ち」には数えない。ボタンの「確認待ちを先に出す」もこの行を拾わない。（DOM）
  - D0024-AC-06 止まっているかもしれない実行（D0021）も「動き」に数える。件数を作る関数は目安（`pipe-in.staleAfterMinutes`）を受け取らず、`quietSec` の値が違っても件数は同じ。（DOM）

#### 件数の形に切り替える条件
- FR-04 選んでいる実行のほかに、数える行があるときだけ、件数の形にする。無いときは今の出し方のまま
  - D0024-AC-07 選んでいる実行のほかに数える行が1つも無いとき、`text` も `tooltip` も今の出し方と1文字も変わらない（実行が1件だけ・ほかが全部終わった・archive だけ・一覧が空・一覧を読めなかった）。`statusBar.test.ts` の既存のテスト（D0006-AC-21・D0019-AC-07）は変えずに通る。（VIEW）
  - D0024-AC-08 選んでいる実行のほかに数える行が1つ以上あるとき、件数の形になる（例：選んでいる実行が動いていて、別に確認待ちが1つ → `$(comment-discussion) pipe-in: 動き 1・確認待ち 1`）。（VIEW）
  - D0024-AC-09 選んでいる実行が終わった実行（合格など）で、別の worktree に確認待ちが1つだけあるとき → `$(comment-discussion) pipe-in: 確認待ち 1`。「合格」で隠さず、説明の `選んでいる実行：` の行に結果が出る。（VIEW）
  - D0024-AC-10 選んでいる実行が記録なし（いまの work_dir の直下に何も無い）で、別の worktree に確認待ちが1つあるとき → `$(comment-discussion) pipe-in: 確認待ち 1`。説明に `記録がありません（<work_dir>）` は出さず、`選んでいる実行：記録なし` が出る。（VIEW）
  - D0024-AC-11 選んでいる実行が数える行かは、件数と同じ一覧の行（選びと同じ key の行）で決める。図の状態では決めない。一覧に行が無い選びは、数える行でない。（DOM・VIEW）

#### 手で・実機
ステータスバーは VSCode 自身が描くので、確認用ページ（`npm run preview`）には出せない。ステータスバーの（画面）の AC は置かず、次の（手で）（実機）で確かめる。（手で）は SDK を呼ばない。
- D0024-AC-50（手で）：2つの worktree A（VSCode で開く）・B で、先に B、次に A で `pipe-in record start` を流す → `$(clock) pipe-in: 動き 2`。`record begin` → `$(sync~spin) pipe-in: 動き 2`。B で `record done`・`record wait` → `$(comment-discussion) pipe-in: 動き 1・確認待ち 1`、説明に実行ごとの行と `選んでいる実行：` と「（確認待ちの実行を先に出す）」。ボタンで B の確認待ちが選ばれる。B で `review approved` → `動き 2`。両方 `finish PASSED` → 今の出し方に戻る。吹き出し・音は出ない。
- D0024-AC-51（手で）：パネルを閉じたまま、B の変化を約10秒以内に拾う。設定を切ると B の分が消え、入れ直すと戻る。B に行がまだ1つも無いあいだは拾わない。
- D0024-AC-52（手で）：改行・ESC・`$(zap)`・`**太字**`・`<b>`・61文字以上の名前が、1行のプレーンな文字として出る。
- D0024-AC-53（手で・画面）：タブや絞り込みを入れたままボタンを押すと、詳細は確認待ちの実行になり、一覧の選んだ行は隠れていてよい。
- D0024-AC-54（実機）：実際の VSCode で、2つの worktree にパイプと開発フローを流して、上と同じ動きになる。利用料がかかるので、人に言われたときだけ流す。

## 決めたことと理由

### 人が決めたこと（要件定義で聞いた 6 点。どれも推しの案）

- **件数の形に切り替えるのは、選んでいる実行のほかに、動き・確認待ち・待ちの行が1つでもあるとき。** 要件メモの文のとおり「2件以上のとき」にすると、選んでいる実行が合格のとき別の worktree の確認待ちが1つだけだと「合格」のままで見えない（#44 が直したい状況）。「一覧の行が2件以上」は、archive や終わった実行が残ると常に件数の形になり、結果が消える。
- **止まっているかもしれない実行（D0021）は「動き」に数える。** 別に数えるには、パネルが閉じていても時間で描き直す仕組みと、拡張ホストでの「更新なしか」の判断が要る。入れないと、静かな長い段で「何も動いていない」と読める。
- **別の worktree の行があるあいだは、パネルが閉じていても隠れていても約5秒ごとに読み直す。** 足さないと、いまの work_dir に変化があるかパネルを開くまで、別の worktree の確認待ちに気づけない。登録されているだけで読み直す案は `infra/` を変え、pipe-in を使っていない人にも読み取りが増える。worktree ごとの監視は、外の場所に再帰で張れず重い。間隔は `POLL_MS`（5秒）のまま。
- **ボタン（とコマンドパレットの「pipe-in: 実行を見る」）は、選んでいる実行が確認待ちでなければ、一覧の先頭の確認待ちを選んで覚えてから開く。** パネルが開いていても同じ。別のコマンドを足す案は、コマンド・`names.ts`・`package.json` が増える。
- **待ち（idle）は「動き」に数える。** 一覧のタブ「動いている」と同じで、段の合間で数が揺れない。
- **件数の形を切る設定は足さない。** 別の worktree の分は `pipe-in.showOtherWorktrees` で外せる。実行が1つのときは今の出し方なので、困る人は少ないと見た。

### 設計で人が決めたこと（3 点。どれも推しの案）

- **件数の形の説明には、確認する文書の場所を出さない。** 要件定義に「段の名前と文書の場所は、説明の実行の行に移る」の1文があったが、承認された AC-16 の行の形には文書の場所が無く、`RunRow` にも無い。AC-16 を優先した。文書の場所はパネルの詳細で見る。`RunRow` に足す案は、記録の写しと確認用ページに触れる。
- **利用者向けの言い方は「ステータスバー」。** 今の文書・`statusBar.test.ts` に合わせた。AC-48 の実際の文は上に書いた。

### 聞かずに決めたこと

- 文字は要件メモの例のとおり「動き → 確認待ち」の順。0 の項目は出さない。アイコンは今の出し方で使っているものから、優先の高い状態のもの（確認待ち ＞ 動いている ＞ 待ち）。新しいアイコンも色も足さない。
- 件数の形になると、選んでいる実行の段の名前や結果は `text` から消えるので、説明に `選んでいる実行：…` の1行を必ず出す（不合格で終わった実行がどこにも出なくなるのを防ぐ）。
- 確認待ちを先に出すときの「先頭」は、一覧の並び（新しい順）の先頭。いちばん長く待っている行ではない（パネルの一覧と食い違わないため）。
- 行の状態は一覧と同じ判定（final → 動いている → 確認待ち）。選んでいる実行が数える行かも、図でなく一覧の行で決める（件数と同じ読み取りから決めるため）。
- 置き場所：数え方・並べ方・先に出す確認待ちは `domain/runList.ts`（`isCounted`・`statusCounts`・`countedRows`・`hasOtherCounted`・`frontWaitingKey`。`RunRow` だけを受ける）。文字と説明と `plainLine` は `view/statusBar.ts`。世代の部品 `createGeneration` と `shouldPoll` の新しい入力は `app/refreshPolicy.ts`。旗は `RunList.hasOtherWorktree`。`view/` は `app/` を import しないので、判断は `domain/` に置いた。新しいソースのファイルは足していない。
- `statusCounts` は `countStates` を呼んで写す（「動き」と「確認待ち」の数え方を2か所に書かない）。
- `plainLine` は制御文字などを空白に替えてから `normalizeName` に通す（上限と規則を二重に書かない。`normalizeName` と本体の `session.py` の規則は変えない）。今の出し方の利用枠の名前は素のまま（出力を1文字も変えない約束のため）。
- 古い読み込みは「最後に始めたものだけ」を使う。`lastList`・`lastListView`・`shown`・`lastLive` への代入を `adopt` 1 か所にまとめ、`retarget()`・`deactivate()` でも世代を進めて途中の結果を捨てる。
- ボタンの順は「選ぶ → `render()` → 開く」。書き込みが失敗してもパネルは開く。
- `extensionStale.test.ts` は触らず、同じ補助（コメントを除く・呼び出しの引数を取る）を `test/sourceText.ts` に置いた（承認済みのテストを書き換えないほうを選んだ。まとめるのは別の整理）。

### 実装でのずれ（設計と違う形）

- `isCounted` は型の述語（`row is …`）にした。`statusCounts` の `top` を絞るため。呼び方・結果は同じ。
- `plainLine` の空白に替える範囲は、16 進の範囲の表と1文字ずつの判定で書いた（ソースに制御文字を生で書かないため）。範囲のすぐ外の文字（U+00A0・U+200D など）は替えない。

### 受け入れたリスク

- 別の worktree に行がまだ1つも無いあいだは、パネルが閉じていると読み直しが動かない（work_dir の無い worktree は場所に入らないため）。新しい worktree で最初の実行を始めたときは、いまの work_dir に変化があるか、パネルを開くまで拾わない。
- 別の worktree の `state.json` を一時的に読めなかったとき（ファイルを書いている最中など）や、`git worktree` の追加・削除の最中に登録が読めなかったときも、行が無いものとして、パネルが閉じていれば読み直しが止まる。いまの work_dir の変化・設定の変更・パネルを開くと戻る。
- 別の worktree に行があるあいだは、VSCode を開いている間ずっと、約5秒ごとに別の worktree（最大8個）の `state.json`・動いている実行の段のログ・選んだ実行の成果物を読む。パネルを見ているときと同じ重さ。終わった記録が残る worktree が1つあるだけで続く。止めるのは `pipe-in.showOtherWorktrees`。
- 読み込みが長く、始まりが読み終わりより頻繁に続くと、途中の結果は捨てられ反映が遅れる（200ms のまとめと読み直しの直列で起きにくい）。
- 行を押した直後、その `render()` が終わる前にボタンを押すと、先に出す確認待ちが押した行を上書きしうる（1秒に満たない間で、次の `render()` で直る）。ボタンで選びが変わったときは、一覧を2回読む。
- 件数（一覧の行）と選んでいる実行の図は別に読むので、境目で一瞬ずれうる（D0021 と同じ）。
- 並列の段が動いているあいだ、その記録の人の確認は件数の「確認待ち」に出ない（一覧の行の状態と同じ）。
- 途中で止まって放置された記録や壊れた `state.json`（待ちになる）も「動き」に数えられる。説明の行で正体は見える。
- ボタンで先に出した行が、パネルの絞り込みやタブで隠れうる（パネルのスクリプトは変えない）。
- `plainLine` はゼロ幅の文字（U+200B など）を残す。説明はプレーンな文字列なので害は無い。
