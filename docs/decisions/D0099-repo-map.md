# D0099 リポジトリの地図を作り、品ごとに整理する（README・英語版・design.md の冒頭に日英×明暗の SVG 4枚と箇条書き、置き場所の表を5つの見出しに分け、/pipe-help に開発用・プラグインの印）

## 目的

このリポジトリには、4つの品（アプリ・作る・プラグイン・開発用）が入っている。それが分からず「プラグインとアプリでリポジトリを分けたほうがよいか」と迷った。壁打ちで、分けたい訳は「頭の中の整理」だと分かったので、リポジトリは分けず、地図・印・品ごとの表で整理する。README と `docs/development/design.md` の冒頭の地図（手書きの SVG と箇条書き）で品と依存の向きをひと目で分かるようにし、置き場所の表を品の見出しで分け、似た名前の開発用とプラグインを印で見分けられるようにする。名前・リポジトリ・`generator/` の中は変えない。

### 要求と前提

- UR-01 pipe-in を GitHub で初めて見る人として、README の短い節で、このリポジトリにどんな品（アプリ・作る・プラグイン・開発用）があり、どれが配られていて、どれが何に頼っているかを、ひと目で分かる図で知りたい。
- UR-02 pipe-in を直す人（人と Claude Code）として、design.md の冒頭の地図と、品ごとに分かれた置き場所の表で、直す部品がどの品のどこにあるかを早く引きたい。
- UR-03 Claude Code のコマンドとエージェントを使う人として、同じ名前のもの（`/pipe-judge` と `/pipe-in:pipe-judge`、`pipe-in-*` と `pipe-*` のエージェント）が開発用かプラグインかを、名前を変えずに見分けたい。
- UR-04 並列で作業する人（夜のまとめ実行を含む）として、表を品ごとに分けたあとも、行の足し先が決まっていてぶつからず、今ある文書の検査も今までどおり働いてほしい。

- 前提：README は主に GitHub の画面で読まれる。今の README は、明暗の画像の組（`pipe-in-logo.svg` と `pipe-in-logo-dark.svg`、`*-light.png` と `*-dark.png`）を `<picture>` と `<source media="(prefers-color-scheme: dark)">` で出し分けていて、GitHub は見る人の明暗の設定に合わせて出す。崩れると、暗い表示の人に明るい版の図が出る。
- 前提：ブラウザは、`<img>` で出した SVG の中のスクリプトを動かさず、外の資源（書体・画像）も読まない。だから、図の文字は見る人の機械の字で描かれ、字の幅は機械によって少し変わる。
- 前提：`tests/test_english_docs.py` は、日本語版と英語版の README の `<picture>` の画像のファイル名の並びが同じことを見ている（`_image_names`。D0072-AC-16）。人と決めたとおり英語の文字の SVG を別のファイルにするので、この検査を、言語の印だけが違う名前を同じとみなす形に直す（FR-17）。見出しの数と深さ（D0072-AC-14）・コードの囲みの数と言語の並び（D0072-AC-15）の検査は、そのまま通す。

## 決めたことと理由

- **リポジトリは分けない。** 分けると、スキルと `pipe-in-gen` を 1 つの PR で直す場面（D0096 など）で版がずれやすくなり、文とコマンドを突き合わせるテストと守りのテストが割れ、`generator/` が真ん中で割れる（作る側と、プラグインの裏の道具の2役がある）。迷いの元は「品の地図が無い」「似た名前が2か所」「置き場所の表が1本」で、どれも文書で解ける。`generator/` を2つの下位パッケージに分けるかは、地図を見てから計画ボードで決める。
- **地図は手書きの SVG。日英×明暗の4枚**（人の希望。Mermaid と文字の図はやめた）。今のロゴや画面の画像と同じ `<picture>` と `prefers-color-scheme: dark` で出し分ける。文字は `<text>` で書き（テストで抜いて実物と突き合わせられ、手で直せる）、外から何も読み込まない。色は `docs/design/README.md` の色の表の値だけで、文字は地と面の両方にコントラスト比 4.5 以上。許す要素と属性の一覧から外れたものは `tests/test_repo_map.py` が止める。
- **品は「使う入口の品」で決める。** 例外は3つ：本体（`pipe_in/engine/`・`pipe_in/pipe/` など）は、ほかの品から読まれても「アプリ」。拡張の中の開発用の道具（`vscode/scripts/` の確認用ページ）は「アプリ」。見本のパイプ（`examples/`）は「作る」。2つ以上の品の入口から使い、本体の外にあるもの（記録の土台・本体と拡張を結ぶ表・テストの補助・利用者向けの文書・CI など）は「共通」。`findings_check.py`・`quorum.py` はひな形の段が呼ぶので「作る」、`pipe_in/dev/` の5段の開発フローは「アプリ」、`/pipe-in` のスキルが使う道具（record・worktree など）は「開発用」。
- **置き場所の表は、87 行の文字を変えずに5つの `###` に分けた**（アプリ 34・作る 5・プラグイン 11・開発用 13・共通 24）。design.md を読む今のテストは、見出しを見ずに行の頭の文字で行を探すので、行の文字を変えなければ壊れない。足し先（D0075 の決まった足し先）は「その品の表の、近い部品の隣に 1 部品 1 行」にした（workflow.md の「8.」）。品の列を足す案は行の頭が変わり、品ごとに別のファイルにする案は今の検査が新しいファイルを見ないので、取らなかった。
- **名前は変えず、印を付ける。** /pipe-help の表の各行の頭に **開発用**・**プラグイン** を付け、表の下に、似た名前の組が別物で、プラグインのものには `pipe-in:` が付くので名前がぶつからないことを書いた（公式の文書：プラグインのスキルとエージェントは名前空間 `plugin-name:` の下に入る）。
- **前の決定の受け入れ基準の置き換え。** 前の記録は書き換えない。

## 対象外・残った課題

- `generator/` を「作る」と「プラグインの裏の道具」の2つの下位パッケージに分けるか（地図を見てから決める。計画ボードに置く）。
