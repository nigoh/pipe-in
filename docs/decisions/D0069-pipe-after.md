# D0069 パイプの成果物を次のパイプへ渡す（--after）

## 目的

作った物を次のパイプで検査したい（例：diagrams で図を作る → spec-qa で図とソースを突き合わせる）。どちらのパイプも単独で使えるまま、組み合わせて使い回せるようにする。パイプとパイプのあいだに、受け渡しだけの仕組みを足す。GitHub の issue #101（段階2の一部）を扱う。

## 機能要件と受け入れ基準

- FR-01 受け取りと断り
  - D0069-AC-01 前のパイプが PASSED で終わっているとき、`--after` 付きで始めると、後ろの最初の段の指示文に、前の段の成果物（存在するもの）の場所が入る。
  - D0069-AC-02 前の記録が途中・確認待ち・失敗のときは、種類と直し方つきで断る。
  - D0069-AC-03 この実行の work_dir に前の記録が無いとき（前と後ろで `--project`・`--config` が違う、など）は、見た場所と直し方つきで断る。
  - D0069-AC-04 前の `pipe.toml` が読めない・前の `state.json` が JSON として読めない・記録の `pipe` が前の名前と違う・開発用スキルの記録、のときは断る。
  - D0069-AC-05 前の成果物が1つも無いときは、PASSED でも断る。
  - D0069-AC-06 `--after` が名前でない値・2つ以上のときは断る。
  - D0069-AC-07 後ろのパイプと同じ名前（自分自身）は断る。
  - D0069-AC-08 `--pipe` なし・名前 `dev`・後ろが `kind = "dev"` のときは断る。
  - D0069-AC-18 断るときは、どの場合も、後ろの記録を作らず・書き換えず、段を流さず、終了コード 1 で止まる。
- FR-02 渡すもの
  - D0069-AC-09 流す前に、前の名前・結果・終わった日時を出す。古さは判定しない（日時が無ければ「不明」）。
  - D0069-AC-10 渡す場所は、linear なら `<work_dir>/<前の名前>/<成果物>`、dev 種なら `<work_dir>/<成果物>`。
  - D0069-AC-11 依頼メモは引き継がない。後ろの `input`（required・optional・none）の決まりに従う。
- FR-03 記録と続き
  - D0069-AC-12 受けた元を、後ろの `state.json` の `received_from`（`pipe`・`kind`・`updated_at`・`dir`・`artifacts`）に書く。受けていない実行には書かない。
  - D0069-AC-13 `--review`・`--from` で続けるときは、自分の `received_from` をそのまま使い、前の記録を読み直さない。続きの画面に受けた元を1行出す。
  - D0069-AC-14 `--review`・`--from` と一緒に `--after` を付けたときは断る。
  - D0069-AC-16 `received_from` の無い古い `state.json` は、受けた元の無い実行として今までどおり読む。
  - D0069-AC-17 `99_summary.md` の「パイプ」の行の次に、受けた元を1行出す。
- FR-04 守り
  - D0069-AC-15 後ろの段は、前の記録（`state.json`・`00_input.md`・`logs/`・成果物）へ、Write・Edit・Bash のどの形でも書けない。記録を含むフォルダの消去・移動も止める。後ろ自身の成果物と、今までどおり書ける範囲は変えない。

## 決めたことと理由

- 形は受け渡しだけにする。パイプを呼ぶ段や繋ぎ方の定義ファイルは作らない。前のパイプは流すときの旗 `--after <名前>` で指し、`pipe.toml`・`pipeline.toml` には書かない。
- 人と決めたこと：`--after` に指せるのは1つだけ。前と後ろで work_dir が違うときは、理由と直し方を出して断る（この実行が見る work_dir に前の記録が無いこととして扱う）。依頼メモは引き継がない。`--review`・`--from` は `state.json` に書いた受けた元をそのまま使い、受け直さない。拡張は変えない。
- 新しい部品は `pipe_in/pipe/after.py` に集める（依存は `pipe_in.pipe` → `pipe_in.engine` の向き）。`Config` には足さず、`LinearPipeline.receive()` で受けた元を渡す。
- 前の記録を書けなくする守りは、`pipe_in/pipe/specs.py` の `build_pipe_specs` で、`can_write` に1段かぶせる（`_outside_pipe` と同じ形）。`guard.py`・`bashwrite.py` は変えない。止める範囲は広がるだけで、狭めていない。Write・Edit・Bash は同じ `can_write` を通る。
- 要件定義・設計の決めきれない点は、人に聞けない夜の実装で、推しの案で決めた：組み込みの開発フロー（名前なし）は前に指せない（名前 `dev` も断る。組み込みの記録と区別できない）／`99_summary.md` に受けた元を1行出す／断るときの終了コードは 1（今ある断りと同じ）／`received_from` の `artifacts`・`dir` は work_dir からの相対／MCP の道具は `can_write` を通らないので文書に書く／記録を含むフォルダ（祖先）の操作も後ろの段は止める。
- 前のパイプが `kind = "dev"` の名前つきパイプのときは、記録が `<work_dir>` 直下なので、そこを前の記録として読む（後ろが dev のときは、記録が前と重なるので断る）。

## 受け入れたリスク

- 段に `mcp` を書いたサーバーの道具は `can_write` を通らないので、後ろの段が前の記録を書けてしまう（既存の `protected_paths` と同じ穴）。文書に書く。
- 祖先のフォルダ（`docs`・`docs/pipeline`）への操作を、後ろの段は一律に止める。`docs` 段の `find docs -delete` のような、記録と関係ない削除も止まる（狭い影響）。
- 既存の穴（今回は直さない）：`code` 段の `find docs/pipeline -delete` は、フォルダの中を見ない判定のため、後ろ自身の記録を消せる。

## 対象外・残った課題

- VSCode の拡張の変更（受けた元の表示）。`received_from` は今の拡張が知らない項目として読み捨てる。
- 組み込みの開発フローを前にすること、前を複数指すこと、前の記録が後から変わったことの検出。
- 監査の報告（A-01〜A-10）は直していない。全文は PR の本文の「朝に見ること」にある。大事なのは A-01（MCP の穴を文書に書く）・A-02（断る一覧が文書とコードで合わない）・A-05（書けない範囲の文書が狭い）。
- 文書係の案（`.claude/skills/pipe-help/SKILL.md` と CLAUDE.md への1行）は、書けないので案のまま（PR の本文）。
- 助言（公式の文書との照らし合わせ）と審査は、`.claude/`・plugin・guard・runner を触らないので流していない。
