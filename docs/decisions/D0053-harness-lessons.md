# D0053 段の組み方（ハーネス）の比較実験で分かったことを、パイプを作る側の目安と `pipe-in-gen check` の警告 W6 に入れる

## 目的

段の組み方を比べた実験（pipe-in の外で行った。[docs/research/harness-compare/](../research/harness-compare/README.md)）で分かったことを、パイプを作る人（`pipe-in-gen design` の設計の決まり・`/pipe-in:pipe-build` の `stage-rules.md`・パイプのガイド）が組む前に読めるようにする。形と指示文の言葉で見分けられる損な組み方は、`pipe-in-gen check` の警告にする。本体の流し方（段の流れ・記録・ガード）は変えない。

## 機能要件と受け入れ基準

### 機能要件

- FR-01 警告 W6 を `pipe_in/pipe/lint.py` の `lint_pipe` に足す。`access` が `read` か `docs` の段で、指示文に指摘を出す言葉（`FINDING_WORDS`：指摘にし・指摘を出・指摘を挙げ・指摘を探・findings）があり、引用の言葉（`QUOTE_WORDS`：引用・逐語・そのまま写・quote）が無く、パイプのどの段の `check.command` にも `findings-check` が無いとき、段ごとに1件、「段 {i}（{name}）: 」で始まる文を返す。文には、指摘ごとに原文を逐語で引かせること、`pipe-in-gen findings-check` を `check.command` に組むこと、ほかの照合を使うなら引用の指示を書けば警告は出ないことを書く。

## 決めたことと理由

### 人に聞いて決めたこと

- W6 は、指示文に引用の指示があれば出さない（`findings-check` が無くても）。`findings-check` が無ければ必ず出す案は、指摘の形 v1 と出典の台帳が要り、案内が重くなるため。
- 実験のあらましと全部の数字は `docs/research/harness-compare/` に新しく置く。実験のスクリプトと課題の生成器は pipe-in の外にあるので、`docs/research/` の「やり直すためのスクリプトと一緒に残す」を満たせない。このことは本文の「やり直し方」に書き、この調査だけの例外とする（監査 A-05）。
- 知識の 1・2・3・5・7 を手引きに入れ、4（3回解かせて票を数える）・6（3体の実装から選ぶ）・8（教訓のメモ）は手引きに書かない。pipe-in にまだ仕組みが無く、書くと設計役の Claude が指示文で真似をして、確かめていない形ができるため。調査の本文に「あとで足す候補」として残す。
- 重ねがけと偵察の並びは警告にしない。形で拾うと、今の決まりがすすめる `verdict`・`command`・`judge` の組み合わせ（diagrams・video の `verify`）や、diagrams の survey→draw に誤って当たり、偵察は文書レビューでは効いたので「明らかに損」と言えないため。
- spec-review の `verify`（`findings-check` に加えて LLM が根拠を確かめる）は、重ねがけに当たらないとみなし、ひな形は変えない。LLM は印を付けるだけで、指摘を落とさないため。
- 指摘の言葉に英語の `findings` を含める。英語の指示文の指摘の段を見逃さないため。言葉だけで拾うので、`09_findings.json` を読んでまとめる段にも当たりうる（ガイドに書いた。引用の指示があれば出ない）。
- 調査の目次の日付は「2026年10月」（実験を行った月）。欄の名前を「日付（調べた日か月）」にした（監査 A-11）。

### 監査と助言で直したこと（人が「推しどおり全部」と承認）

- A-01：手引き3か所で、重ねがけで下がった比較の元を「同じ課題を何回か解かせて多く出た指摘を残す方式に、道具での確かめなどを重ねた組」に直した（初めは「引用の照合・検証の質問を重ねると」と書いていたが、引用の照合と票の組は上がっており、検証の質問は比べていなかった）。目次の要約もそろえた。
- A-02：手引き3か所に「設計レビューでは、引用の照合だけでは上がらなかった」を足した。
- A-03・A-04：ガイドと W6 の文を実物に合わせた（「などの照合」をやめ、ほかの照合なら引用の指示を書けば出ないと書く。`findings` がまとめる段にも当たりうると書く）。
- A-06：「下見」に「（偵察）」を添えて、調査の本文の呼び名とつないだ。
- A-07・V-01：`stage-rules.md` の中身が変わったので、プラグインの版を 0.5.1 に上げた。GitHub からマーケットプレイスを足して 0.5.0 を入れている人には、版が変わらないと届かないため（公式の文書 plugins/loading.md・host-marketplace.md）。目安の文を足しただけで、スキル・エージェント・フックの動きは変えないので、minor でなく patch にした。版を決め打ちしていた `tests/test_plugin.py::test_plugin_version` と `tests/test_plugin_evals.py::test_D0045_AC_14_plugin_version_stays_0_5_0` を 0.5.1 に直した（D0045 の「evals/ を足しても版を上げない」はそのまま。上げた理由は evals/ ではない）。マーケットプレイスの項目には `version` を足さない（V-03）。
- V-02・V-05：`docs/guide/plugin.md` に「0.5.0 から更新するとき」を足し、手元のフォルダから足した人と GitHub から足した人で更新のしかたを分け、更新のコマンドと自動の更新の入れ方を書いた。
- V-06：`stage-rules.md` の調査の本文への案内を、公開リポジトリの URL にし、入れたプラグインからは読めない、人が見る参考だと添えた。
- A-08：`plugin/skills/pipe-build/SKILL.md` と `docs/development/design.md` の `stage-rules.md` の要約に「比較実験から分かった組み方の目安」を足した。
- A-09：`/pipe-help` の `pipe-in-gen check` の行に、警告も出て、警告だけなら終了コード 0 だと足した（文書係の案）。
- A-10：この記録に AC-01〜24 を書いた。AC-11 は D0038-AC-09 の既存のテスト、AC-15 は既存のテストと手の確かめで見る。
- A-12：テストのファイルの冒頭の説明に D0053 を足した。
- 審査（助言の報告の採点）：overall 0.81・verdict pass。結論の言い方が強すぎた（GitHub から新しく入れる人には届く）こと、出典の節の名前の1つが見出しでなかったこと、references/ の読まれ方の答えが薄かったことで下がった。

### 受け入れたリスク

- 実験は Claude Haiku だけ、生成器で作った課題（方式ごとに 20〜30）での結果で、ほかのモデルや実際のプロジェクトでは確かめていない。手引きには決まりでなく目安として書き、どこにも限界の一文を添えた。
- W6 は言葉で見分けるので、言い換えた指示文は見逃し、`findings` を含む読む段には当たりうる。警告は誤りではなく、流すのも止めない。

## 対象外・残った課題

- 本体の段の流れ・記録・ガード、拡張。
- あとで足す候補（まだ仕組みが無い）：同じ段を何回か流して指摘の票を機械で数える仕組み、同じ書き込み範囲に複数の実装を並べてテスト事例で選ぶ仕組み、実行をまたいで教訓のメモを持ち越す仕組み。
- 実験のスクリプトと課題の生成器をリポジトリに置くこと。

## 確かめたこと

- テスト先行：足したテスト 69 件のうち 48 件が、期待した理由（W6 がまだ無い・文書の節や目印がまだ無い）で落ちることを確かめた。21 件は出さない側・書かない側を守る検査で、今の作りのままで通った。
- 検証（1 回で合格）：worktree を入れ直した環境で `pytest -q -p no:cacheprovider` を流し、この記録を待つ 1 件のほかが通った。拡張は変えていないので、拡張のテストは流していない。
- 監査と助言の直しのあと、もう一度全部を流した（この記録を書いたあと）。
- 数字の突き合わせ（手で）：手引き3か所（0.86 → 0.94・−0.024・−0.071・2勝15敗）と調査の本文と実験の集計が合う。
- ひな形と見本で警告が 0 件であることはテストで確かめた。実際のパイプを `pipe-in` で流しての確かめは、まだ。
- 公開してよいか：変えたファイルに、秘密・ユーザー名の入った絶対パス・メールアドレス・`docs/pipeline/` の中身は無い。
