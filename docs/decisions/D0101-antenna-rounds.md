# D0101 antenna の回：公式の文書が根拠の小さな変更だけを、判定の道具が merge と言ったときに、定期の回が自分で main に入れる（守りの仕組みと本体は PR どまり）

## 目的

Claude Code の決まり（スキルやプラグインの書き方）は、公式の文書と更新履歴で少しずつ変わる。今は、人が気づいたときにだけ追っている。持ち主は、別のリポジトリの道具 antenna に、朝に公式の情報を取らせ、夕にこのリポジトリへの変更を作らせ、条件を満たした物は人を待たずに main に入れると決めた（2026-11-20）。

このリポジトリには「無人の実行は、開始の指示に書かれていても main に入れない」という決まりがある。この記録は、その決まりに例外を1つ足し、例外の範囲を、守りの仕組みと本体に届かない所に絞る。

### 要求と前提

- UR-01 持ち主として、プラグインのスキルと `plugin.json` を、Claude Code の公式の決まりの変更に、人の手を待たずに追わせたい。
- UR-02 pipe-in を使う人として、自動で入る変更が、自分のプロジェクトを守る仕組み（書き込みの範囲を絞るフックとエージェントの定義）を変えないでほしい。
- UR-03 pipe-in を直す人（人と Claude Code）として、どの変更が自動で入り、どの変更が PR で止まるかを、1つのファイルと決まりの文で読みたい。

- 前提：antenna の判定の道具（`antenna_gate.py`）は、作業中の枝ではなく origin の main の `.antenna.json` を読む。枝の中で範囲を広げても効かない。`.antenna.json` そのもの・`.github/`・`.claude/`・`CLAUDE.md`・フック・`settings.json`・検査の命令が指すファイルは、道具の中の定数で止まり、購読では緩められない。
- 前提：判定の道具は判定を出すだけで、PR を main に入れる操作は、回を動かす Claude Code がする。「`VERDICT: merge` でなければ入れない」は、決まりの文で守る。機械で止める本当の関所は、GitHub のブランチ保護である（`docs/development/workflow.md` の「6. CI」）。
- 前提：`.claude/settings.json` の `ask` に入っているのは、`git merge`・`gh pr merge`・main へ届きうる `git push` の形などの Bash の命令である。回が使うのは GitHub の道具（PR を main に入れる）で、`ask` には当たらない。`ask` は書き換えない。
- 前提：一次情報かどうかは、antenna の道具がカードの URL から決める。`.antenna.json` の `primary` の下の URL だけが、main に入れる根拠になる。
- 前提：このリポジトリは公開している。回が作る変更も PR の本文も、誰でも読める。

## 決めたことと理由

- **例外は、範囲を絞って1つだけ足す。** 「無人の実行は main に入れない」は、夜の実行で何度も確かめて決めた決まりで、理由（人が見ないまま守りが変わる・公開のリポジトリに確かめていない物が入る）は今も成り立つ。だから決まりは消さず、成り立たない所だけを例外にした：公式の文書が根拠で、プラグインのスキルの文と `plugin.json` とテストの追加に限り、60 行までで、テストが全部通る変更。
- **エージェントの定義と `pipe-run` は自動にしない。** エージェントの定義の `tools` は、審査役や段の実行役が使える道具を絞っている。`pipe-run` は、流す前に守りを確かめる手順を持つ。どちらも文のファイルだが、守りの範囲そのものなので、`guard.py` と同じ扱いにした。
- **本体は自動にしない。** 本体の変更は、決定の記録とテスト先行で進める決まりである。60 行の自動の変更では、その決まりを満たせない。SDK の版が上がった知らせは受け取り、変更は PR で人が見る。
- **テストは足すだけ。** 判定の道具は、テストの行を消した変更を PR どまりにする。今あるテストを直さないと通らない変更は、振る舞いを変える変更なので、人が見る。
- **`ask` は書き換えない。** 回が main に入れる道（GitHub の道具）は、もともと `ask` に入っていない。`ask` を緩めると、ほかの無人の実行の道まで開く。
- **選ばなかった形：全部を PR どまりにする。** 安全だが、持ち主が毎日 PR を見ることになり、追わせたい理由が消える。カードの質が悪い・自動で入った変更を戻すことが続いたときは、`.antenna.json` の `apply.mode` を `pr` にすれば、この形になる。
- **受け入れたリスク。** (1) 最後の1歩（PR を main に入れる操作）は文の決まりで、機械では止まらない。ブランチ保護で必須の検査を決めれば、機械の関所になる。(2) スキルの文は、プラグインを入れた人の会話で読まれる。公式の文書が根拠でも、文の直し方を誤ることはある。行数の上限・テスト・版の上げで小さく保ち、入った変更は PR として残るので戻せる。(3) 拡張のテスト（`vscode/`）は回の検査に入れていない。自動で変えてよい範囲に拡張が無いためである。

## 対象外・残った課題

- 判定の道具そのもの（antenna のリポジトリにある）の作りと確かめは、この記録の対象外。
- ブランチ保護で、回の検査を必須の検査にすることは、していない（GitHub の設定で、人が決める）。
- 回が作った変更で、プラグインの eval（`plugin/evals/`）は流さない（利用料がかかるので、人に言われたときだけ流す決まりのまま）。スキルの文が自動で変わったあと、eval の結果が動く可能性は残る。
- 拡張と本体を自動の範囲に入れるかは、回を何週間か動かしてから、あらためて決める。
