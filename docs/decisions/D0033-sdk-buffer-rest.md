# D0033 パイプと pipe-in-gen design でも、SDK の受信バッファの上限を超えたら止める（D0026 の残り）

## 目的

段が大きい画像を読んで SDK の受信バッファの上限（D0026 の `[pipeline] max_buffer_mb`、既定 32MB）を超えたとき、開発フローと同じく、パイプ（`--pipe`）と `pipe-in-gen design` でもトレースバックで落ちずに止まり、直し方が分かるようにする。前の版で落ちた人が、入れ直せばよいと分かるようにする。

## 機能要件と受け入れ基準

- FR-01 パイプで段が上限を超えた失敗を返したら、その段で止め、終了コード 3 にし、`state.json` にその段の実行と案内を残す
  - D0033-AC-01 ふつうの段で上限を超えると終了コード 3 になり、`state.json` に残る（`tests/test_sdk_buffer.py::test_D0033_AC_01_パイプのふつうの段で上限を超えると終了コード3になりstate_jsonに残る`）
  - D0033-AC-02 検証つきの段で上限を超えても差し戻さず、終了コード 3（`::test_D0033_AC_02_検証つきの段で上限を超えると差し戻さず終了コード3`）
  - D0033-AC-03 グループの片方で上限を超えると終了コード 3 で、後の段に進まない（`::test_D0033_AC_03_グループの片方で上限を超えると終了コード3で後の段に進まない`）
- FR-02 パイプを流すときの設定でも、`pipeline.toml` の `max_buffer_mb` が段に効く
  - D0033-AC-04 `max_buffer_mb = 64` なら 64MB、書かなければ 32MB が段に渡る（`::test_D0033_AC_04_パイプの段の上限はpipeline_tomlのmax_buffer_mbで決まる`）
- FR-03 `pipe-in-gen design` で設計の段が上限を超えたら、やり直さずに案内を出して止め、パイプを作らない（終了コード 1）
  - D0033-AC-05 設計の段は1回だけ呼ばれ、案内が出て、何も作らない。前の回で検査に落ちていても作業用フォルダが残らない（`::test_D0033_AC_05_designで上限を超えるとやり直さず案内を出して何も作らない`・`::test_D0033_AC_05_前の回で検査に落ちたあと上限を超えても作業用フォルダが残らない`）
- FR-04 上限超え以外の失敗では、`pipe-in-gen design` は今までどおりやり直す
  - D0033-AC-06 ほかの失敗では `max_rounds` 回までやり直す（`::test_D0033_AC_06_designは上限超え以外の失敗では今までどおりやり直す`）
- FR-05 前の版の設定ファイルのままでも、同じように止まる
  - D0033-AC-07 `max_buffer_mb` の無い `pipeline.toml` と上限の項目の無い `pipe.toml` でも終了コード 3（`::test_D0033_AC_07_前の版のpipeline_tomlとpipe_tomlでも上限超えは終了コード3`）
- FR-06 ガイドに、前の版で落ちたときの入れ直しを書く
  - D0033-AC-08 `docs/guide/config.md` の `max_buffer_mb` の行のあとに、`1048576 bytes` のトレースバックで落ちたら入れ直す説明がある（`tests/test_guide.py::test_D0033_AC_08_設定のガイドに古い版で落ちたときの入れ直しの説明がある`）
  - D0033-AC-09（手で）D0026 の入った pipe-in を入れ直した環境で、動画のパイプを原寸 1080×1920 の PNG を読む段まで流し、トレースバックで落ちない

## 決めたことと理由

- **始まりは、動画のパイプを実機で流したときに `maximum buffer size of 1048576 bytes` のトレースバックで落ちたこと。** 調べると、上限の設定（D0026）はすでに main に入っていた。1048576 は SDK の既定の 1MB で、流した pipe-in が D0026 より前の作業コピーだった。そのため、この機能では D0026 の残りの穴だけを扱った（人が案 A を選んだ）。
- **本体（`pipe_in/`）は変えない。** パイプの道は、段が `is_error` を返すと検証より前に段の失敗になり、グループも同じ道を通り、`for_pipe` も上限を保つので、今のコードで要件どおりに動く。テスト（AC-01〜04・07）で固めて守り続けるだけにした。
- **`pipe-in-gen design` はやり直さずに止める（D0026 の残った課題をここで閉じる）。** やり直しても同じものを読んで同じように超え、利用料だけがかかるため。終了コードは、`pipe-in-gen` のほかの失敗と同じ 1 にした（人が推しのまま承認）。止まる文は、同じ関数のほかの誤りと同じ形（字下げ・「✗」・「- 」）にし、案内の文が空でも代わりの1行を出す（監査 A-01・A-02）。案内は、runner が出す分と design の止まりの文で2回出る。止まる理由を最後に読めるほうを取った。
- **既定の上限は 32MB のまま。** D0026 で決めた値で、16MB だと大きい画像を3枚まとめて読むだけで超えうる。段の始まりに上限は出さない。超えたときの案内に、効いていた上限がもう入っている。
- **ガイドの入れ直しは `git pull` してから `pip install -e .`。** 古い作業コピーのままだと入れ直しても直らないため、`docs/guide/plugin.md` の入れ直しと同じ形にした（監査 A-04）。版の番号は前と同じなので、どこから読んでいるかを `python -c "import pipe_in; print(pipe_in.__file__)"` で確かめる、と書いた。
- **番号を2回付け直した。** 進めるあいだに main に D0031（live-watch）と D0032（guard-fail-closed）が入ったため、D0031 → D0032 → D0033 にした。先に足したテストは #65 で、実装は #67 で main に入り、この記録で閉じる。
- 監査で直した項目：A-01・A-02（止まる文の形と、案内が空のときの1行）、A-03（テストの補助の名前から別の番号 `d32_` を外した）、A-04（入れ直しの形）、A-05（D0026 の残った課題をこの記録で閉じる）、A-06（pipes.md に「案内を出して」と設定へのリンク）、A-07（テストの補助は実物の形 `design_with(tmp_path, monkeypatch, runner, max_rounds=3)`）、A-08（テストのファイルの説明に D0033）。
- 助言（`pipe-in-advisor`）と審査は流さなかった。`.claude/`・`plugin/`・`runner.py`・guard を変えていないため。

## 対象外・残った課題

- 本体の上限の値や案内の文の見直し（D0026 のまま）。
- 先に足したテストが実装より前に main に入り、main が一時赤になった（#65）。テスト先行の途中のブランチは、決定の記録までそろってからマージする。

## 確かめたこと

- 先に足したテストのうち AC-05（2件）と AC-08 は、作る前に期待した理由で落ちた（「設計の段が 3 回呼ばれた」・ガイドに `1048576` が無い）。ほかの AC は今のまま通った。
- 実装と監査の直しのあと、`pytest -q` は全件通った。
- AC-09（手で）はまだ。利用料がかかるので、人が決めてから流す。
