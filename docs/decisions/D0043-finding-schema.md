# D0043 仕様書レビューの指摘を、決まった形（指摘の形 v1）で受け渡し、形と出典と引用を機械で検査する（案）

> この記録は **案** です。`/pipe-in` の要件定義に渡す前の下書きで、まだ作っていません。受け入れ基準のテストの名前は、テスト先行の段で決めます。

## 目的

受け取った仕様書・要求書をレビューする役割（品質・網羅・視点別・素人質問・根拠の確認・まとめ）が、同じ形で指摘を受け渡せるようにする。あわせて、出典の無い指摘や、仕様書に無い文を引いた指摘を、LLM に頼らず機械で見つけられるようにする。確定した指摘は、あとで要件（FR・AC）へ結び、テストと納品物まで1本の鎖で追えるようにする。

## 機能要件と受け入れ基準

- FR-01 指摘の形 v1 を JSON Schema で定める。置き場所はジェネレーターのひな形（`generator/templates/spec-review/schema/finding.schema.json`）。1つの指摘は次の欄を持つ。
  - `id`（`F-` と3けた以上の数字。1回の実行の中で重ならない）
  - `role`（出した役割。`quality`・`gap`・`perspective`・`naive` のどれか）と、`role` が `perspective` のときの `perspective`（`user`・`tester`・`designer`・`operations`・`security`・`legal`）
  - `location`（`source`＝仕様書の出典 ID、`section`＝章・節、`quote`＝仕様書からそのまま引いた文）
  - `kind`（`missing` 不足・`ambiguous` 曖昧・`inconsistent` 不整合・`unverifiable` 検証不能・`excess` 過剰／要否の論点・`risk` リスク）
  - `statement`（指摘の内容）・`rationale`（なぜ問題か）
  - `sources`（裏付けの出典 ID の並び）と `guess`（真偽値。出典が無い＝推測）
  - `confidence`（`high`・`medium`・`low`）・`severity`（`critical` 致命・`major` 重大・`minor` 軽微）
  - `question`（顧客への質問案。`text` と `type`＝`yes_no`・`choice`・`free`、`type` が `choice` なら `choices`）
  - `risk`（`kind` が `risk` のときだけ。`condition` 発生条件・`impact` 影響・`estimate` 見積・契約への波及）
  - `verification`（根拠の確認役が足す。`verdict`＝`supported`・`rejected`・`needs_human` と `reason`）
  - `status`（`open`・`confirmed`・`rejected`。人が CP2・CP3 で変える）
  - `links`（`status` が `confirmed` のときだけ。`requirements`＝`FR-xx` の並び、`acceptance`＝`AC-xx` の並び）
  - D0043-AC-01 欄が全部そろった指摘は通り、必須の欄が1つでも欠けた指摘・決まった値の外の `kind`・`severity`・`role` は、欄の名前を添えて落ちる
  - D0043-AC-02 `id` が `F-` の形でない・同じ実行の中で重なると落ちる
- FR-02 出典の台帳（`sources.json`）の形を定める。1件は `id`（`SRC-` と3けた以上の数字）・`kind`（`spec` 対象の仕様書・`customer` 顧客の資料・`law` 法令・`standard` 標準・`public_spec` 公開の仕様書・`past_case` 社内の過去事例）・`title`・`version`・`where`（章・条・URL）を持つ。
  - D0043-AC-03 指摘の `sources` と `location.source` が台帳に無い ID を指すと、その ID を添えて落ちる
  - D0043-AC-04 `sources` が空なのに `guess` が偽、または `sources` があるのに `guess` が真だと落ちる
- FR-03 引用の一致を確かめる。`location.quote` は、`location.source` が指す仕様書の本文に含まれていなければならない（空白と改行の違いは無視する）。
  - D0043-AC-05 本文にある文を引いた指摘は通り、本文に無い文・一部を言い換えた文を引いた指摘は落ちる
  - D0043-AC-06 `kind` が `missing`（書かれていないものの指摘）のときは、`quote` を空にしてよい。その代わり `section` は要る
- FR-04 役割ごとの決まりを検査する。
  - D0043-AC-07 `role` が `naive`（素人質問者）の指摘は、`sources` に `spec` 以外の出典を持てない（知識ベースを読んでいない役のため）
  - D0043-AC-08 `kind` が `risk` なのに `risk` が無い・`kind` が `risk` でないのに `risk` があると落ちる
  - D0043-AC-09 `links` は `status` が `confirmed` のときだけ持てる。`FR-xx`・`AC-xx` の形でない値は落ちる
- FR-05 検査はジェネレーターの決まった手順で行い、LLM を呼ばない。`pipe-in-gen findings-check <指摘のファイル> --sources <台帳> --spec <仕様書の本文>` で流し、誤りを1行ずつ出して、誤りがあれば終了コード 1 で止まる。パイプの検査の段（`check`）から呼べる。
  - D0043-AC-10 誤りの無い見本では終了コード 0 で「誤りなし」、誤りのある見本では誤りの数だけ行を出して終了コード 1 になる
  - D0043-AC-11 テストは SDK を呼ばず、リポジトリの実物（`pipes/`・`.pipe-in/`・`docs/pipeline/`）に書かない
- FR-06 形の版を持つ。指摘のファイルの頭に `"v": 1` を書く。
  - D0043-AC-12 `v` の無いファイル・知らない版のファイルは、例外でなく「版が分からない」で落ちる

## 決めたことと理由

- 前提（決定のページで決めたこと）：まず自分が職場の案件で使い、チーム、外部の順に広げる。レビューと納品物は並べて作り、この形で結ぶ。役割は資料Bの7役割をすべて作る。作る場所は pipe-in のパイプ（決定のページで未決。会話で推しのまま進めると合意した）。ロジックは公開の pipe-in、知識・事例・評価は職場の非公開リポジトリに置く。
- 指摘の形は、資料A（Round 1 の設計）の `finding-schema` と資料B（専門家エージェントの設計レポート）の9項目を合わせ、確定後に要件へ結ぶ `links` を足した。選ばなかった形：資料Bの9項目だけ（機械で検査しにくい）、資料Aの形だけ（要件へ結ぶ欄が無い）。
- 出典を必須にせず、「出典なし＝推測」を `guess` で明示させる。LLM の一般知識からの指摘を消すと網羅が落ち、出典を捏造させる圧にもなるため（資料B 3・6）。
- 引用の一致は機械で確かめ、LLM には「根拠が主張を支えているか」だけを任せる（資料A S7、資料B A6）。言い換えた引用は落とす。言い換えは、仕様書に無いことを書いた指摘と見分けられないため。
- 要・不要は判定させず、`kind` の `excess` で論点として出すだけにする。必要性は文書の外の情報（事業の目的・契約）で決まるため（資料B 3 の A7）。
- 欄の名前は英語、値の説明は日本語にする。CSV（Excel）に出すときに列の見出しを日本語に置き換える。
- 人が承認したこと：言い換えた引用も落とす（FR-03）・素人質問者は仕様書以外の出典を使わない（FR-04）・欄の名前は英語で CSV では日本語の見出しにする（上の行）の3点。
- 受け入れたリスク：重大度の基準（`critical`・`major`・`minor` の分け方）は、根拠となる研究が薄い。実験（E1〜E4）と実案件1件で見直し、変えるときは新しい記録で v2 にする。

## 対象外・残った課題

- 役割（エージェント）とパイプそのもの（`spec-review` のひな形の段の並び・指示文）は、別の記録にする。
- 質問票の CSV の列と並び（決定のページの段9）は、別の記録にする。
- 知識ベース（用語集・ドメインモデル・法規の候補）の形は、知識ビルダーの記録にする。
- 素人質問者に知識ベースを読ませない仕組み（読める範囲の絞り）は、ガードの変更になるので別の記録にし、すり抜けの道をテストで示す。
- 指摘の重なりをまとめる手順（位置と種別で集める）は、まとめ役の記録にする。
