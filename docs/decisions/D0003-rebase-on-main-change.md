# D0003 main が進んだら、機能のブランチを載せ直す

## 目的

複数の会話を並列で動かしても、機能のブランチがいつも新しい main の上にあり、新しい main の上で確かめたうえで、早送りで main に入れられるようにする。

## 機能要件と受け入れ基準

- FR-01 `docs/development/workflow.md` に、載せ直す時（段の区切り・検証の段の前・main に入れる直前）と方法（`git rebase --autostash main`）、載せ直したあとにすること、main へは早送り（`git merge --ff-only`）で入れること、worktree で気をつけることを書く
  - D0003-AC-01 workflow.md にそれらが書いてある（`tests/test_rules.py::test_workflow_documents_rebase`）
- FR-02 `/pipe-in` は、段の区切りで main が進んだかを見て、検証の段の前と main に入れる直前には必ず載せ直す
  - D0003-AC-02 `/pipe-in` にその手順がある（`tests/test_rules.py::test_pipe_in_rebases_when_main_moves`）

## 決めたことと理由

- **worktree は、1人で1つだけ進めるときも切る。** このリポジトリは複数の会話を並列で動かすのがふつうなので、例外を作らないほうが迷わない（人の判断）。
- **載せ直しは rebase で、main へは早送りで入れる。** マージのコミットを作らず、1つの機能が1つのコミットのまま main に並ぶようにするため。
- **段の区切りごとに見て、検証の前と入れる直前は必ず載せ直す。** 古い main の上で作り続けると、最後にまとめてぶつかり、テストも古い main で確かめたことになる。毎回の載せ直しは手間なので、段の区切りでは「進んでいれば」にした。
- **`--autostash` を使う。** /pipe-in では最後までコミットしないので、途中の変更をよけてから載せ直す必要がある。よけるのは、その worktree の中の自分の変更だけで、ほかの会話の作業には触れない。
- **push したブランチは載せ直さず、main を merge で取り込む。** 履歴を書き換えると、ほかの人の手元とずれるため。このリポジトリの機能のブランチは、ふつう push しない。
- **main に入れるとき、ほかの会話のまだコミットしていない変更とぶつかっても、その作業を stash しない。** D0002 を main に入れたとき、`vscode/src/app/pipeEditor.test.ts` がほかの会話の作業と重なり、自分のブランチ側からその変更を外して入れた。stash すると、その会話の作業を壊すおそれがある。
- `devpipe-gen` などのコマンドは `pip install -e .` を入れたフォルダ（ふつうは main）のコードを動かすので、worktree では `python -m …` で確かめる、と書いた。

## 対象外・残った課題

- 載せ直しが要るかどうかを、仕組み（フックなど）で知らせること。今は /pipe-in の手順として、メインの会話が見る。
- main の作業フォルダで、worktree を切らずに作業している会話を止めること（ルールで頼むだけ）。

## 確かめたこと

- `tests/test_rules.py` の2件は、文書を書く前に、書いていない言葉の名前で落ちた。書いたあと通った。
- 載せ直しの手順そのものは、D0002 で実際に行った（`49041c0` の上に載せ直し、`CLAUDE.md` と `/pipe-in` のぶつかりを合わせ、テストを流し直してから早送りで入れた）。
