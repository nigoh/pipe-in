# D0075 並列の作業でぶつかる文書とテストの形を、書き足しが別々の場所に入る形に直す

## 目的

件ごとに同じ所の末尾へ書き足す形を、書き足しが別々の場所に入る形に直す。直すのは、決定の記録の一覧・置き場所の表の長い行・guide の節・`tests/test_architecture.py`・確認用ページと `screen-check.md` の結びつきの5つ。読む人に要ること（一覧で決定を引ける・置き場所を表で引ける）と、今ある検査（D0002・D0039 など）の意味は残す。あわせて、秘密・手元の事情の検査が、まだ追跡していない新しいファイルを見落とす穴を直す。

2026-11-02 の夜は 12 件を件ごとの枝で流し、最後に1本の枝へ cherry-pick で集めた。そのときのぶつかりは、どれも「両方が同じ所に書き足した」ものだった：`docs/decisions/README.md`（一覧の行）・`docs/guide/usage.md` と `vscode.md`（節）・`docs/development/design.md`（置き場所の表の同じ行に、両方が部品を書き足していた）・`tests/test_architecture.py`（末尾に両方が検査を足した）。確認用ページを足した件のあとは、`.claude/skills/pipe-in/screen-check.md` に頭の行を足すまで D0039-AC-17 が落ち続けた。D0074 の PR では、新しいテストの偽の URL がメールアドレスの形に見え、手元では（まだ追跡していないので）通り、CI で落ちた。

## 決めたことと理由

- **一覧は手書きのまま、`merge=union` と検査で守る**（人が決めた）。記録の頭から一覧を作る案は取らなかった。題は手で磨いてあり、生成にしても同じファイルが変わるので、ぶつかりは残る。`union` は、別々の枝が末尾に足した行どうしを、手元の載せ直し・cherry-pick・merge で両方残す。壊れ（重なり・並び違い・ぶつかりの印・行の欠け）は `tests/test_doc_shape.py` が見つける。
- **design.md の表は1行 800 字まで。** 今の表で 800 字を超えていたのは4行だった（1,347・1,862・1,078・1,020 字）。上限を 800 字にすると、今のテストが読む行の先頭を変えずに割れる。拡張の層の行は短い要約にして、部品の説明は新しい小節「層ごとの部品」の表に 1 部品 1 行で移した（第1列は完全なパスにして、D0002-AC-04 が実在を見る）。
- **`tests/test_architecture.py` は1字も変えない。** 新しい検査は `tests/test_architecture_<名前>.py` に置き、共有の部品は `from test_architecture import …` で使う。今ある検査を移すと名前と履歴が追いにくくなるので、移さない。
- **screen-check.md は1行1頭に**（人が決めた）。「README の一覧を全部開く」の一文にする案は、D0039-AC-17（種類を書き落とさない）の意味を弱めるので取らなかった。ページを足す件は、頭の行を1行足すだけで済み、ほかの件の行とぶつからない。落ちたときのメッセージに、足す頭と足す場所を出す。
- **guide の節の足し先には検査を付けない。** 節の位置は意味で決まるので、機械では見られない。決まりの文だけを workflow.md に書いた。
- **秘密・手元の事情の検査は、まだ追跡していない新しいファイルも見る**（人が決めた）。追跡しているファイルしか見ないと、コミットの前の手元では通り、CI で初めて落ちる。`.gitignore` の中（`docs/pipeline/` など）は見ない。部品は設計どおり `tests/test_rules.py` に置いた。実装係はテストを書けない決まりで、段のフックがその書き込みを止めたので、人の承認を得てメインが入れた（フックは変えていない）。
- **監査と助言で直したこと**（人が承認した項目）：
  - 監査の A-05：AC-07 の検査が短いファイル名をバッククォートで探していたので、design.md の約 30 行が説明に自分のファイル名を括弧で繰り返していた。検査を「バッククォートで囲んだ完全なパスの末尾の名前でもよい」形にし（途中の名前や名前の一部では通らないことも確かめる）、繰り返しの括弧を消した。
  - 監査の A-01：秘密の検査が未追跡の新しいファイルも見ること、`.gitignore` の外に置いた手元だけのファイルで落ちうることと直し方を、`principles.md` の「7. 公開する前提で書く」に書いた。
  - 監査の A-04：確認用ページの README の表の足し忘れを知らせるのは `tests/test_guide.py` で、D0039-AC-17 は screen-check.md の側だけを見る。`workflow.md`・`docs/assets/README.md`・`screen-check.md` の文を分けて直した。
  - 監査の A-06〜A-09・A-11：`extension.ts` だけ役割ごとに複数行であること、D0051 の検査が層の行で読む語は残すこと、`run-panel-check-*` の頭、CLAUDE.md の表の workflow.md の要約、800 字の上限が効くのは design.md と CLAUDE.md の表であること、を書いた。
  - 監査の A-02・A-03・A-10・A-12：テストの説明文とコメントを、赤の段の頃の言い方から今の形に直した。必ず通る assert を1つ消した（判定は変わらない）。
  - 助言の V-01〜V-07：直す所は無かった。スキルの補助ファイルの指し方は公式の勧めと合い、SKILL.md は 183 行（目安は 500 行）。枝の土台は `worktree.py`（D0074）が自前で決めていて、Claude Code の worktree の仕組みと重ならない。
- 助言の報告の審査（ルーブリックの5項目）は、総合 0.85（合格の線 0.70）で合格。減点は網羅性で、git の union の働きと GitHub の画面の merge で効くかは、助言係の読める場所の外で確かめられなかった。

## 対象外・残った課題

- 拡張（`vscode/`）のコード・確認用ページの作り方・画面。
- D0074 の夜のまとめ実行の流れ・`worktree` のコマンド。決定の記録の書き方（`specs.md` の形）。
- guide の本文の整理（節の足し先の決まりだけを書いた）。
- `merge=union` が GitHub の画面の merge でも効くかは、確かめていない（git と GitHub の公式の文書でも照らせていない）。入れる直前に手元で載せ直す手順（`worktree sync`）なら、解けたものを GitHub に出せる。
- 秘密の検査は、`.gitignore` の外に置いた手元だけのファイル（作業の残り・覚え書き）でも落ちる。落ちたら、公開してよいかを確かめて直すか、`.gitignore` 済みの場所へ移す（`principles.md`）。
