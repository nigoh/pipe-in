# D0085 /pipe-in の要件定義と設計に、要求・前提・非機能要件・状態の問いを足し、ID のつながりを検査する

## 目的

`/pipe-in` の要件定義と設計に、「誰の何の望みか」「世界はこう動くという前提」「速さや安全のような性質」「状態を持つか」を書く欄を足し、人が確認の段で、抜けや食い違いに気づけるようにする。あわせて、つながらない ID と、基準の無い状態遷移のマスを数える小さな検査（`python -m pipe_in skill spec-check`）を足す。

### 要求と前提

- UR-01 開発者として、要件定義の確認のときに、書かれていないこと（前提・性質・状態）に気づきたい。
- UR-02 開発者として、要求から受け入れ基準・テストまで、つながっているかを機械で確かめたい。
- UR-03 開発者として、小さな直しでは、書くものが増えてほしくない。
- UR-04 開発者として、守りの仕組み（フック・書ける範囲）は、今のままであってほしい。
- 前提：人は段の区切りで、成果物を読んで答える。問いが具体的なら、読む量が増えても気づきが増える。
- 前提：サブエージェント（`pipe-in-analyst`）は、指示文に書かれた形のとおりに書く。形が崩れたら、検査が数えて知らせる。
- 前提：決定の記録は、5つの見出しのまま、追跡して残る。
- 状態を持ち、操作や出来事で移り変わるか
  - 答え：いいえ
  - 理由：足すものは、文書の形（指示文・ひな形）と、文書を読んで数える関数だけ。段の順番や記録の状態には手を入れない。

## 決めたことと理由

- **まず開発用のスキル `/pipe-in` だけで試す**。本体の dev パイプ（`pipe_in/pipe/`・`generator/templates/dev/`）へ広げるのは、何件か流して効果を見てから。「設計を細かく書くと実装の精度が上がる」は、まだ確かめていない仮説のため。
- **厚くするのは設計書の量でなく、人が確認する1点の質**。設計の段は1つのまま。足したのは、リポジトリを読んでも分からない決めごと（要求・前提・非機能の条件・状態の移り変わり）と、検査に変えられるものだけ。今ある構造を説明する図（クラス図・コンポーネント図）は足さない。
- **状態遷移の表は、要件定義の問いが はい のときだけ書く**。要件定義の段が答えと理由を書いて提案し、人が要件定義の確認で承認か修正をする。小さな直しでは、UR 1つ・前提「無し」・非機能要件「無し」の3行で済む。
- **表の網羅は、すべてのマスを1回（起きないマスも含む）**。続けて2手の組み合わせは、テストの数が掛け算で増えるので足さない。
- **ID の決まり**：番号は付け直さず欠番にする（付け直すとテストの名前と記録の ID がずれる）。記録の番号 `Dnnnn` を付けるのは、テストの名前に出る受け入れ基準だけで、UR・FR・NFR・DS は短いまま（記録の中でしか読まれないので、ぶつからない）。製品コードには ID を書かない（UR・FR・NFR・DS と受け入れ基準の ID。直すたびにずれる。コードとの対応はテストの名前で取る）。決定の記録の番号 `Dnnnn` は、理由の指し先としてコメントに書いてよい（今のコードの実態に合わせて、人が決めた）。鎖は決定の記録まで（コミットと PR には伸ばさない）。
- **決定の記録の見出しは5つのまま**。要求と前提は `## 目的` の中の `### 要求と前提`、非機能要件は `## 機能要件と受け入れ基準` の中の `### 非機能要件` に書く。`## ` の見出しを足すと、前からある記録が全部落ちるか、検査に例外が要るため。
- **前からある記録と文書は検査しない・書き換えない**。鎖の検査は、この記録の番号以降の決定の記録だけにかける（始まりの番号は `tests/test_rules.py` の定数 `CHAIN_FROM` 1つ。製品コードには置かない）。要求（UR）が1つも無い要件定義は「前の形」として、数だけ出して終了コード 0 にする。
- **検査の中身は `pipe_in/dev/spec_check.py` の1か所**。段の途中の文書（`spec-check`）と決定の記録（`tests/test_rules.py`）が同じ関数を使う。変わりそうなのは「検査が読む書き方」なので、正規表現と問題の種類の定数をこのファイルに閉じ込めた。標準ライブラリだけで、読むだけ（書かない・子プロセスを起こさない）。
- **守りの仕組みは変えない**。`spec-check` は旗も引数も取らず、今のフォルダの `docs/pipeline/` の2つだけを読む（任意のファイルを読む道を開かない）。検証役 `pipe-in-verifier` の Bash の許す一覧には足さず、親が流して出力を指示に入れ、検証役が報告に写す。許す一覧に足す形より、守りの範囲が広がらないほうを選んだ。
- **新しい形の要件定義に `答え：` の行が無いと問題にする**（設計で足した）。問いに答えないと、人が確認で気づけない欄が空になるため。
- **段の区切りで「見てほしい問い」を2〜3個添える**。人の確認は量が増えると形だけになりやすいので、確認点は増やさず、読む観点を渡す。
- **`SKILL.md` の字数の上限を 12,300 字から 12,500 字に上げた（人が決めた）**。元が 12,220 字で余裕が 80 字しか無く、足す4つの文をいちばん短くしても 12,498 字になる。既存の文を削る形は、別のテストが守る語や、意味のある注記が消えるので選ばなかった。受け入れたリスク：要約のあとに戻るスキルの先頭の量が少し増える。
- 受け入れたリスク：検査が見るのは形のつながりだけで、要求が本当に望みを表すか・前提が成り立つかは見ない。そこは人が確認で読む。
- 受け入れたリスク：指示文の文の有無を見るテスト（`tests/test_spec_depth_docs.py`）は決まった語を見るので、言い回しを直すとテストも直すことになる。
- 考え方の出どころ（記憶から挙げたもので、原典とは照らしていない）：要求の追跡（Gotel・Finkelstein 1994）、要求と要件と前提の区別（Zave・Jackson 1997）、状態機械からのテスト設計（Chow 1978）、品質特性シナリオ（Bass たち）、変わりそうな決定を隠す分け方（Parnas 1972）。

## 対象外・残った課題

- 画面遷移・取り決めの定義・シーケンス・コンポーネント・クラスの節、設計の図とソースの突き合わせ、仕事の種類（不具合の修正・リファクタリング）の見分け、教訓の持ち越し、本体の dev パイプへの展開。残った問いと合わせて issue #146 に控えた。
- 設計の段を、基本設計・外部の詳細設計・内部の詳細設計に分けること。
- 状態遷移の表を実際に書く機能は、まだ流していない（この機能自身は、問いの答えが いいえ）。表の読み方は、偽の文書のテストで確かめただけ。
- `pipe_in/pipe/lint.py` のコメントに、受け入れ基準の ID が1件ある（前からのもの。別の直しで外す）。
- `docs/decisions/README.md` の一覧で、D0080 以降の行がひな形の後ろに離れていて、表として描かれない（前からの状態。この記録の行もそこに足した。別の直しで表へ移す）。
- 助言の任意の改善（分析役の指示文が増えたらスキルに切り出す・`spec-check` を流す行をスキルの冒頭にまとめる）は見送った。後者は字数の上限に入らない。
- 効果（差し戻しが減るか）は、まだ分からない。下の「確かめたこと」の1行を、これからの記録に残して振り返る。
