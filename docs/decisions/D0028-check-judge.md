# D0028 段の検証で、ルーブリックの審査から合否をエンジンが出す（[stages.check.judge]）

## 目的

パイプの検証で、合格・不合格の2つだけでなく、ルーブリックの項目ごとの点と「必ず守る決まり」（must）の違反から合否を決められるようにする。合否の計算はエンジンがし、審査役（LLM）には平均も合否も計算させない（[docs/research/eval-vs-judge/](../research/eval-vs-judge/README.md) の「平均でしきい値を切ると違反が通る」に合わせる）。

## 機能要件と受け入れ基準

### 書き方と計算

- FR-01 `[stages.check]` の下に入れ子の表で審査を書ける：`[stages.check.judge]`（`threshold`、既定 0.7）、`[[stages.check.judge.criteria]]` と `[[stages.check.judge.must]]`（どちらも `name`・`description`）。ルーブリックは `pipe.toml` の中に書く。
- FR-02 審査の段は、構造化出力で、項目ごとの `reason`（理由）と `score`（0.0・0.25・0.5・0.75・1.0 か null）、must ごとの `violated`（true / false / null）と `evidence`（根拠）を返す。
- FR-03 合否はエンジンが計算する。must に `violated` が true か null が1つでもあれば不合格。無ければ、null でない点の平均（小数2桁・四捨五入）がしきい値以上で合格。
- FR-04 採点できた点が1つも無いときは不合格。
- FR-05 審査役の返りが決まりに合わないとき（5段階以外の点・理由なし・項目や must の欠け・知らない名前・違反なのに根拠なし・型違い）は、段のエラーにせず不合格にして差し戻す。
- FR-11 計算の決まりは `generator/judge_score.py`（D0022）と同じにする。計算は `pipe_in/pipe/judge.py`（標準ライブラリだけ）に持つ。重みは入れない。
- D0028-AC-01 must の違反が無く平均がしきい値以上なら合格する（`tests/test_check_judge.py`・`tests/test_judge_calc.py`）。
- D0028-AC-02 must の違反が1つあれば、平均が 1.0 でも不合格（同上）。
- D0028-AC-03 must が null でも不合格で、直す点に「確かめられませんでした」と根拠が出る（同上）。
- D0028-AC-04 null の点は平均から外れ、全部 null なら不合格（`tests/test_judge_calc.py`）。
- D0028-AC-05 平均は小数2桁に四捨五入して比べる（0.745 は 0.75、0.744 は 0.74）。浮動小数の誤差で境が逆にならない（同上）。
- D0028-AC-06 平均がしきい値に届かなければ不合格で、しきい値の既定は 0.7（同上）。
- D0028-AC-07 審査役の返りに合否や平均が入っていても使わない（`tests/test_check_judge.py`）。
- D0028-AC-08 返りが決まりに合わないときは段のエラーにならず、不合格で `on_fail` へ戻る（同上）。
- D0028-AC-20 同じ入力（境の 0.745・0.744、must の null、全部 null を含む）を `pipe_in.pipe.judge` と `generator/judge_score.py` に通すと、合否と平均が一致する。`judge_score` が受け取らない入力は、こちらでは `valid=False` の不合格になる（`tests/test_judge_calc.py`）。

## 決めたことと理由

### 人が決めたこと

- `pipe.toml` の書き方は入れ子の表（`[stages.check.judge]` と `[[…criteria]]`・`[[…must]]`）。1行の形より項目が多いときに読みやすく、`verdict`・`command` と並べやすい。ルーブリックは `pipe.toml` の中に置く（別ファイルにすると置き場所が増える）。
- 複数回の採点（runs）はエンジンには入れない。利用料を抑え、まず形を入れる（プラグインの `/pipe-in:pipe-judge --runs` はある）。
- 審査役の返りが崩れていたら、不合格にして差し戻す（段のエラーで止めない）。`verdict` の崩れた返りと同じ扱いにそろえる。
- 作業台の保存で `judge` が消える危なさを、要件定義の段で見つけた（`pipeModel.ts` は check を `verdict`・`command`・`max_retries` だけで書き直していた）。編集画面は作らず、「消さずに残す」だけをこの機能に入れた。
- 承認したテストの1件（AC-11）に、終了コードの書き間違い（`TEST_FAILED` を 2 としていた。正しくは 1）があり、人の了解を得て直した。要件と設計の文の「終了コード 2」も同じ書き間違いで、この記録では 1 と書く。

### 聞かずに決めたこと

- 計算は `pipe_in/pipe/judge.py` に持ち、`generator/judge_score.py` と当面2か所にする。`judge_score.py` は D0022 で「本体を読み込まない」と決めてあるため。2つがずれないことは AC-20 のテストで守る。
- 記録は `history` の `check` に `judge` を足すだけ（別ファイルにしない）。項目の理由は記録に残さず、must の根拠は残す。
- 重みは入れない。
- 判定は verdict → judge → command の順に3つとも見て、問題をまとめて返す（どれかで打ち切らない）。直す点を一度に渡せる。

### main に合わせたこと

- 作業のあいだに main に D0022（プラグインの採点）と、別の5つの機能が入ったので、2回載せ直した。重なったのは `docs/development/design.md` の置き場所の表だけで、そのまま合わせた。
- その5つの機能が決定の記録の D0023〜D0027 を使っていたので、この記録は **D0028** にした（作業中は D0023 と呼んでいた。テストの AC の ID も `D0028-AC-xx` に置き換えた）。監査（A-01）で見つかった。

### 受け入れたリスク

- 古い版の pipe-in では `judge` は知らないキーとして黙って無視される。`verdict` や `command` と併記していれば、審査なしで合格しうる。`judge` だけだと、検証が無いのと同じになる。ガイド（`docs/guide/pipes.md`）に書いた。
- 計算を2か所に持つ。どちらかだけを直すとずれるが、AC-20 のテストが落ちて気づける。
- 審査は1回の採点で合否を出すので、ぶれがある（研究で、同じ文の採点し直しで合否が 18.5% 入れ替わった）。合否を確かにしたい段では、`command`（機械の検査）と組むことを勧める。

### 監査

- 監査（8件）：A-01（番号の重なり）・A-02（直す点に入る理由の条件）・A-03（検証のスイッチを切ると judge も書き出されない）・A-04（テストの説明の終了コード）・A-05（記録に must の根拠は残る）・A-06（戻し先は `on_fail`）を直した。
- 助言と審査は流さなかった（`.claude/`・`plugin/`・`pipe_in/engine/runner.py`・`pipe_in/engine/guard.py`・`generator/guard_hook.py` のどれも変えていないため）。

## 対象外・残った課題

- 作業台で審査を表示・編集する画面。今は、審査がある段でも「判定」の欄に何も出ない。作業台に出る依頼文の写しにも審査の節は出ない（監査 A-07）。
- `pipe-in-gen design` が組む設計図と、プラグインの pipe-build の「段の決め方」は `judge` を知らない（監査 A-08）。次の機能（pipe-build で検査と審査の段を組めるようにする。番号は D0029 の予定）で扱う。
- 複数回の採点（runs）をエンジンに入れること。
- 計算を1か所にまとめること（generator が `pipe_in.pipe.judge` を使う形）。
