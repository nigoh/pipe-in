# ロードマップ

pipe-in をどこへ向けて育てるかと、その順番を書きます。中身の進み具合は GitHub のイシュー（段階ごとの親イシューと、その下の子イシュー）で追います。決めたことの理由は、機能ごとに決定の記録（`docs/decisions/`）に書きます。

## 目指す姿

> **AI に任せる作業の流れを、図で組んで、図で見て、図で口を出せる道具。**

- **組む**：作業台で段の並びを描く。Claude も一緒に描く。
- **見る**：流れている様子をフローチャートで追える。どこで止まったか、なぜ戻ったか、いくらかかったかが分かる。
- **口を出す**：確認や差し戻しを、図の上で見つけて答えられる。

### 主役はパイプ

開発フロー（要件定義 → 設計 → テスト先行 → 実装 → 検証）は、パイプの1つとして並べます。図を作る・仕様とソースを突き合わせる・調べものをまとめる、といったパイプが横に並ぶ形にします。

### 使う人と、届ける順番

| 順番 | 使う人 | 要るもの |
| --- | --- | --- |
| 1 | システムの開発者 | CLI と VSCode で動く。パイプを自分で組める。守りと記録が信頼できる |
| 2 | 一般の人 | 入れるのが簡単。コマンドを打たずに、作業台と図だけで組む・流す・答える。見本のパイプから選べる。費用が先に分かる |

### 変えないこと

- 守りは緩めない。許すものの一覧で書く・書ける範囲を絞る・テスト先行（`docs/development/principles.md`）。
- 利用料が見えること。
- 公開できる形を保つこと。

## 段階

| 段階 | 主題 | 中身 | 主に誰向け | イシュー |
| --- | --- | --- | --- | --- |
| 0. 足場 | 残りを片づける | 名前の変更と監査・助言の手での確認、会話を開かずに監査を流す呼び方、作業台と実行パネルの決定の記録 | 開発者 | #3 |
| 1. 見る | 実行のフローチャートを充実させる | 差し戻しの矢印と理由、パイプの判定とやり直し、並列の枠、確認待ちの通知（VSCode の知らせと `/pipe-in` の PushNotification はできた。音・OS の通知・ベルはまだ）、前の実行の一覧 | 開発者 | #4 |
| 2. 組む | 作業台と Claude Code をつなぐ | 作業台から Claude に作図を頼む、外で書き換わったパイプを読み直す、検査の結果を CLI とそろえる | 開発者 | #5 |
| 3. 口を出す | 図から操作する | 拡張が書く「返事のファイル」、パネルから承認・修正の依頼・中止、作業台から流す、流す前の費用の目安 | 開発者 → 一般 | #6 |
| 4. 一般の人へ | 入口を低くする | Marketplace に出す、Python を手で入れずに動く形、見本のパイプ集、初めての人向けの案内と英語の文書、フックを速くする | 一般 | #7 |

- 「見る」を「組む」より先に置くのは、組んだものが思いどおりに流れたかを図で確かめられるようにしてから、組む側を広げるためです。
- 段階3では「拡張は work_dir を読むだけ」の決まりを変えます。拡張が書くのは決まった返事のファイル1つだけにし、それを読んで動くのは pipe-in 本体だけにします。決まりを変える理由とすり抜けの道が無いことは、その機能の決定の記録とテストで示します。

## 直すとき

- 目指す姿・段階・順番を変えたら、この文書と親イシューを一緒に直します。
- 段階に入らない思いつきは、まずイシューにして、どの段階に入れるかをあとで決めます。
