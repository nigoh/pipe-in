# 仕様の書き方と決定の記録

## 要件定義の形

機能を足す・直すときは、作り始める前に次のものを書き、人の確認を取ります（`/pipe-in` の「1. 要件定義」）。

| 項目 | 書くこと |
| --- | --- |
| 目的 | 誰の何が良くなるかを1〜2文で |
| 要求 `UR-xx` | 誰の何の望みか。`- UR-01 <誰>として、<何>したい。` を1行ずつ |
| 前提 | 世界はこう動くという決めつけ。崩れると、要件を満たしても役に立たないもの。`- 前提：…` を1行ずつ（番号は付けない）。無ければ `- 前提：無し` |
| 機能要件 `FR-xx` | すること。1つの FR に1つのこと。`（UR-xx）` で、どの要求から来たかを書く |
| 非機能要件 `NFR-xx` | 速さ・安全・読みやすさなどの性質。きっかけ・状況・応答・測り方の4つを書き、そのまま受け入れ基準にする。`（UR-xx）` で要求につなぐ。無ければ `- 無し` |
| 状態の問い | 「状態を持ち、操作や出来事で移り変わるか」。行頭に `答え：はい` か `答え：いいえ`、次の行に `理由：…`。はい のときは、設計で状態遷移の表（状態 × 出来事 → 次の状態。行の頭のセルを `DS-xx` にして、同じ行に受け入れ基準の ID を書く）を書く |
| 受け入れ基準 `Dnnnn-AC-xx` | 1つずつテストで確かめられる形で。「〜のとき、〜になる」。`（FR-xx）` で、確かめる FR・NFR（状態遷移の表があれば DS）を指す。画面に関わるなら、見た目と操作を分けて `（画面）` を付ける。手で・実機で確かめるものは `（手で）`・`（実機）` を付ける |
| 対象外 | しないこと。あとで足すかもしれないこと |
| 触る側 | 本体（`pipe_in/`）・ジェネレーター（`generator/`）・プラグイン（`plugin/`）・拡張（`vscode/`）のどれか |
| 決めきれない点 | 人に聞くこと。聞かずに決めたことは、そう書く |

受け入れ基準の書き方の目安:

- 「正しく動く」「適切に」のような、確かめ方が決まらない言葉を使わない。入力と、期待する結果を書く。
- 守る仕組みの変更では、許すものと止めるものの両方を書く（止めるほうは、すり抜けの道を並べる）。
- 古い形のもの（前の版の記録や置き場所）をどう扱うかを、1つは入れる。
- 小さな直し（状態を持たない・記録の要らない大きさ）では、欄を増やさない：UR は1つ、前提と非機能要件は `- 無し` の1行ずつ、状態の問いは `答え：いいえ` と理由1行で、設計に状態遷移の表を書かない。

ID の決まり（`python -m pipe_in skill spec-check` が読める形。D0085）：

- 番号は付け直さない。消した要件の番号は欠番のままにする（欠番は問題にしない）。同じ ID を2回定義しない。
- `Dnnnn` を付けるのは、記録の外（テストや文書）に出る受け入れ基準だけ。UR・FR・NFR・DS は短いままにする。
- 製品コードには ID を書かない（UR・FR・NFR・DS と受け入れ基準の ID。直すたびにずれるため）。決定の記録の番号 `Dnnnn` は、理由の指し先としてコメントに書いてよい。
- 各行の頭は `- ` と ID（半角）。指し先は ID の直後の `（…）` に、`・` などで区切って書く。範囲（`FR-01〜03`）は読めないので1つずつ書く。

## 決定の記録（docs/decisions/）

機能ごとに1つ、`docs/decisions/Dnnnn-<名前>.md` を作ります。番号は4けたで、origin の main の最新の記録の次の番号にします。`python -m pipe_in decision-number` が出します（origin から取って見るので、手元の古い main の枝は見ません。今いる作業フォルダの `docs/decisions/` に、もっと大きい番号があればその次にします。夜のまとめ実行では `--branch night/<名前>` で、まとめの枝に積まれた分も見ます。出すだけで、予約はしません。D0074）。名前は英小文字・数字・`-` です。
`/pipe-in` では、要件定義で番号を決め、検証の段で書き上げます。

段の成果物（`docs/pipeline/`）は手元の作業の記録で、追跡しません（[workflow.md](workflow.md) の「段の成果物と決定の記録の分け方」）。追跡して残すのは、**あとから読む人が知りたいこと**だけです。

| 見出し | 書くこと |
| --- | --- |
| `# Dnnnn <題>` | 1行目。何ができるようになったか |
| `## 目的` | 要件定義の目的。D0085 以降は、この中に `### 要求と前提`（UR を1行ずつ・前提・状態の問いの答え）を書く |
| `## 機能要件と受け入れ基準` | FR と AC を1行ずつ。AC には、確かめたテストの名前を添える。D0085 以降は、この中に `### 非機能要件`（NFR）を書き、AC の行に `（FR-xx）` を付ける |
| `## 決めたことと理由` | 選んだ形と、選ばなかった形と、その理由。受け入れたリスク |
| `## 対象外・残った課題` | しなかったこと・あとでやること |
| `## 確かめたこと` | テストの結果の要約と、手で・実機で確かめたこと（確かめていないものは、そう書く）。D0085 以降は、足した欄と差し戻しの回数を1行（検査はしない） |

ひな形は [../decisions/README.md](../decisions/README.md) にあります。形は `tests/test_rules.py` が検査します。
一覧（`docs/decisions/README.md`）には、表の最後の行の下に 1 記録 1 行を足します。`.gitattributes` の `merge=union` で、別々の枝が足した行どうしは自動で解けます。番号の昇順・重複・リンク先は `tests/test_doc_shape.py` が検査します（[workflow.md](workflow.md) の「8. 並列の作業でぶつからない書き方」。D0075）。

- 決めたことを後から変えたときは、前の記録を書き換えず、新しい記録を作り、「Dnnnn を置き換える」と書きます。
- 小さな直し（誤字・文書だけ・テストの足し）には、記録は要りません。
- 流れ・依存の向き・段や状態の移り変わりは、Mermaid の図（```` ```mermaid ````）で示してかまいません（任意。[workflow.md](workflow.md) の「7. PR と issue」）。見出しの決まりは変わりません。

## 受け入れ基準の ID とテストの名前

- AC の ID は `Dnnnn-AC-xx`（記録の番号＋その中の通し番号。通し番号は 2 桁で、100 以上は 3 桁）です。機能をまたいでも重なりません。
- テストの名前（拡張）か docstring（Python）の頭に、その ID を書きます。
  - 拡張：`test('D0002-AC-07: 層ごとに、…', …)`
  - Python：`def test_xxx(): """D0002-AC-01: …"""`、またはテストの並びの見出しのコメント `# ---- D0001-AC-06: … ----`
- テストに書いた ID は、記録の中に無ければなりません（`tests/test_rules.py` が検査します）。
- 前からあるテストの `AC-xx`（番号だけのもの）は付け直しません。新しく書くテストから、この形にします。
