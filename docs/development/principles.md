# 原則

迷ったら、ここに戻ります。下のほかの文書は、この原則を具体的にしたものです。

## 1. テストを先に書く

- 赤 → 緑 → 整理 の順に進めます。製品コードより先に、仕様（受け入れ基準）をテストにします。
- 赤は「落ちた」だけでは足りません。**期待した理由で落ちた**ことを、失敗の文まで読んで確かめます（[testing.md](testing.md) の「赤の確かめ方」）。
- 承認されたテストは、実装のあいだに書き換えません。テストのほうが違うと思ったら、理由を書いて人に判断してもらいます。

## 2. 関心を分ける

- **判断**（何をどう決めるか）と、**外とのやり取り**（ファイル・SDK・`vscode`・時計・環境変数・ネットワーク）を分けます。
  判断は純粋な関数にして、外とのやり取りは口（`runner`・`PipeStore`・`WorkDirSource` など）の向こうに置きます。
- こうしておくと、判断は偽物を使わずにテストでき、外とのやり取りは差し替えられます。
- 依存は一方向にします（[design.md](design.md) の「依存の向き」）。共通の仕組みは、それを使う側を知りません。

## 3. 変えやすくしておく

- **1つの知識は1か所に置きます。** 記録の形は拡張の `runRecord.ts` など、パイプの形は `devpipe/pipe/definition.py`。同じ判断を2か所に書かない。
- **小さく変えて、そのたびにテストを通します。** 大きな書き換えは、小さな段に分けます。
- **形を変えても、古いものを読めるようにします。** 記録（`state.json` など）・設定（`pipeline.toml`）・パイプ（`pipe.toml`）・置き場所を変えるときは、前の版で作ったものが読めること、または読めないときに何をすればよいかが分かることを、テストで示します。
- 名前は、何をするかが分かる日本語の説明と一緒に付けます。コメントは「なぜ」を書き、「何を」はコードに語らせます。

## 4. 安全側に倒す

- 利用者のプロジェクトを守る仕組み（`devpipe/engine/guard.py`・`generator/guard_hook.py`）と、このリポジトリの /pipe-in のサブエージェントを絞る仕組み（`.claude/hooks/pipe_in_guard.py`）は、**許すものの一覧**で書きます。止めるものの一覧では、新しい道具やすり抜けの道を見落とすためです。
- 読めない入力・分からない相手は、止めます。
- 守る範囲を狭める（緩める）変更は、理由をコミットと決定の記録に書き、すり抜けの道（PowerShell・MCP・サブエージェント・パスの `..`・Bash の記号など）が開かないことをテストで示します。
- 失敗したときに素通りになる所（例：`devpipe-gen` が無いとフックが効かない）は、隠さずに決定の記録に書き、ほかの所で補います。

## 5. 明示する

- 既定の値、探す順番、優先の順番は、文書とテストの両方に書きます（例：パイプは 対象の `.devpipe/pipes/` → 今までの場所 の順に探す）。
- エラーの文は日本語で、何が起きたかと、何をすればよいかを書きます。

## 6. 利用料のかかることは、言われてから

- SDK を呼ぶこと（devpipe を流す・`devpipe-gen design`）は、人に言われたときだけにします。
- テストは SDK を呼びません。runner を差し替えて確かめます。

## 7. 公開する前提で書く

このリポジトリは公開します。書いたもの・コミットしたものは、誰でも読めるものとして扱います。

- 秘密を書かない・コミットしない：API キー（`ANTHROPIC_API_KEY` など）、トークン、`.env`、鍵ファイル。設定の見本には値を入れない。
- 手元の事情を書かない：ユーザー名の入った絶対パス（`C:\Users\…`、`/Users/…`、`/home/…`）、社内や私的なプロジェクトの名前、メールアドレス。
- devpipe を実際に流した記録（`docs/pipeline/`、とくに `logs/*.jsonl` と `state.json`）は、プロンプト・読んだコードの中身・セッション ID・手元のパスを含みます。サンプルとして載せるときは、中身を読んで手元の情報を消してから `examples/` に置きます。
- 手元だけの設定は `.claude/settings.local.json` と `CLAUDE.local.md` に書きます（どちらも `.gitignore` 済み）。
- 決定の記録にも、手元の事情は書きません（「手元の Windows で確かめた」のように書き、パスやユーザー名は書かない）。
