# 記録と使用量

[ガイドの目次](README.md) · [README](../../README.md) — 流したあとに残るファイル・使用量のまとめ・終了コードの説明です。

## 作られるファイル

対象プロジェクトの `docs/pipeline/` に置かれます（`work_dir` で変更可）。

| ファイル | 中身 | 書く段 |
|---|---|---|
| `00_input.md` | 渡した要件メモ | パイプライン |
| `01_requirements.md` | 要件定義書（機能要件 FR、受け入れ基準 AC） | 要件定義 |
| `02_design.md` | 設計書（ドメインモデル、層ごとの置き場所、入口の型、AC とテストの対応、テストの実行方法） | 設計 |
| `03_red_tests.md` | テスト先行の記録（AC とテストの対応、落ちたことの確認） | テスト先行 |
| `04_implementation.md` | 実装の記録（回ごとに追記） | 実装 |
| `05_test_report.md` | 検証報告（AC ごとの結果） | 検証 |
| `99_summary.md` | 全体の結果、受けた元（`--after` で受けた実行だけ。「パイプ」の行の次に1行）、段ごとのターン数・費用・時間、トークンの内訳、モデル別、環境、利用枠 | パイプライン |
| `state.json` | 実行の記録（機械向け）。段の並び（`stages`：名前・表示名・成果物・確認の有無）、段ごとの `metrics`、全体の `usage_summary`、注意（`warnings`）、確認待ち（`pending_review`）、端末で人の入力を待っているあいだの印（`reply_wait`）を含む | パイプライン |
| `logs/*.jsonl` | 各段のやり取りの全記録 | パイプライン |

審査（`[stages.check.judge]`、[パイプ](pipes.md#ルーブリックで審査するstagescheckjudge)）を使った検証は、`state.json` の `history` の `check` に `judge`（`status`・`overall`・`threshold`・`scores`・`must`・`valid`。項目の理由は残さず、must の根拠は残す）を足し、`99_summary.md` の検証の行の下に審査の 1 行を出します。審査を使わない検証と古い記録には、どちらも出ません。

`state.json` には、実行を見分けるための項目があります（どれも足しただけで、無い古い記録もそのまま読めます）。

| 項目 | 中身 | 付け方 |
|---|---|---|
| `schema` | 記録の形の版（今は `1`）。新しく書く記録の最初の鍵 | 本体が自動で書きます（端末で流した記録・`pipe-in record start`・`pipe-in-gen chat start`）。鍵の無い古い記録は、読むだけで書き換えません（`--review` や `record` で続けても付けません）。読む側はこの値で読み分けず、`1` 以外の値でも落ちずに読みます |
| `total_cost_usd`・`usage_summary` | 費用と使用量。**2通りだけ**：測れた記録は、`total_cost_usd` が数、`usage_summary` が集計の辞書。取れない記録は、`total_cost_usd` が `null`、`usage_summary` が `{"available": false, "reason": "…"}`（理由は空にしません） | 端末で流した記録は測れた記録です。会話の中で流した記録（下）と、開発用スキルの記録（`pipe-in record`。段を会話の中で進めるため）は取れない記録です。開発用の記録の `runs[]` の `cost_usd` も `null` で、`metrics` の鍵はありません。`schema` の無い古い開発用の記録は `0.0`・`null`・`{}` のままで、変換しません |
| `name` | セッション名。VSCode の実行の一覧の太字の名前 | `pipe-in --name "…"`、`pipe-in record start --name "…"`。付けなければ、要件メモ（`00_input.md`）の最初の行から作ります（先頭の `#` を取り、中の連続する空白を 1 つにし、60 文字を超えるときは 59 文字＋`…`）。取れなければ書きません。確認待ちからの再開（`--review`・`--from`）でも変わりません（`--review` に `--name` は付けられません。名前は始めるときだけ付けます） |
| `session_id` | Claude Code の会話の ID（開発用スキルが残す） | `pipe-in record start --session-id <ID>`。付けなければ書きません。空白や改行を含む値、100 文字を超える値は断ります。パイプの記録には書かず、拡張が `runs[]` の `session_id` のうち、最後に動いた段のものを使います |
| `at`（`runs[]` の `review` の要素） | 人の確認の結果（`approved`・`revise`・`quit`）を書いた時刻（UTC からのずれつき） | `pipe-in record review` が書きます。`pipe-in record check` が、次の段の `begin` との前後を比べるのに使います。項目の無い古い記録は、検査で「判定できなかった」として読みます（ほかの読み手は使いません） |
| `agent`（`runs[]` の要素と `Prompt` 行） | その段を受け持ったエージェントの名前 | `pipe-in record begin <段> --agent <名前>`。付けなければ書きません。SDK で流す段には書きません。VSCode の時系列の行の名前と、エージェント・スキルの表のエージェントの行に出ます |
| `max_budget_usd`（`runs[]` の要素） | その実行に効いた費用の上限（ドル。0 より大きい数） | SDK で流す段のうち、上限が効いた実行にだけ書きます（`pipeline.toml` の `[stages.<段>]` か `pipe.toml` の値。[設定](config.md)）。上限が無い実行には書きません（`null` も書きません）。項目の無い古い記録は、上限なしとして読みます。VSCode の図は 0.001〜10000 ドルの範囲だけを上限として読みます。VSCode の図が、費用を上限と比べるのに使います |
| `resumed`（`runs[]` の要素） | 会話の続きの印 | 上限が効いた実行のうち、`resume` を渡した実行にだけ `true` を書きます（偽は書きません）。続きの会話の費用は前の回からの累計（Claude Code v2.1.277 以降の動き）なので、図は金額の対を出さず、止まったときだけ言葉を出します。項目の無い記録は、続きでないものとして読みます |
| `check`（`stages[]` の要素） | 段の判定の設定：`on_fail`（不合格のとき戻す段の名前。自分をやり直すなら `null`）と `max_retries`（戻す上限） | 判定（`[stages.check]`）のある段にだけ書きます。判定の無い段・開発フローには書きません。項目の無い古い記録は、判定の無い段として読み、VSCode の図は判定の節を出しません |
| `group`（`stages[]` の要素） | 並列の枠（作業台の枠。`pipe.toml` の `[[stages]]` の `group`）の名前 | 枠の中の段にだけ書きます（`check` の後ろ）。枠の外の段・開発フローには書きません。項目の無い古い記録は枠なしとして読み、VSCode の図は段を一列に出します。拡張は、空・空白だけ・65 文字以上・`/` や `\` を含む・文字でない値を、枠なしとして読みます |
| `attempt`（`runs[]` の `check` の中） | その段の何回目の検証か（1 から） | パイプの検証のたびに書きます。確認待ちで止めて再開しても、同じ段の前の検証の続きの番号になります。項目の無い古い記録は、同じ段の並びの番号で読みます |
| `reply_wait` | 端末の `pipe-in` が確認の段で人の入力を待っているあいだの印：`stage`（段の名前）・`id`（待ちごとの識別子。10 文字の 16 進）・`since`（待ち始めた時刻。UTC からのずれつき） | 本体が、待ち始めに書き、待ちが終わると（承認・修正の依頼・中止・例外・中断のどれでも）消します。`pending_review`（`--pause` で止めた印）とは別の項目です。標準入力が端末でない実行・`--yes`・`--pause` では書きません。待っていないときは鍵ごと書きません。強制終了すると印が残り、次の流し始め・再開（`--from`・`--review`）で外します（それまで、VSCode の実行の一覧は「確認待ち」のままです）。項目の無い古い記録は、印なしとして読みます |
| `flow` | 流れの回数：`steps`（段を流した回数）と `retries`（不合格になった段の名前 → 戻した回数。合格しても 0 に戻しません） | パイプ（`pipe-in --pipe`）だけが、保存のたびに書きます。開発フロー・会話の道には書きません。確認で止めて `--review` で続けるときに回数を引き継ぎ、`max_steps`・`max_retries` が確認をはさんでも実行全体で効きます。人の `revise` で流し直す1回は `steps` に数えません。`--from` で流し直すときは 0 から数えます。項目の無い記録・壊れた部分は 0 として読みます。VSCode の拡張は読まずに捨てます |
| `received_from` | 受けた元（前のパイプの記録から渡したもの）：`pipe`（前の名前）・`kind`・`updated_at`（前の終わった日時）・`dir`（前の記録の場所。作業フォルダからの相対。`linear` は前の名前、`dev` は `.`）・`artifacts`（段の表示名 `stage` と作業フォルダからの相対パス `path`。段の順） | `pipe-in --pipe <後ろ> --after <前>` で始めた実行にだけ書きます。受けていない実行には書きません。確認待ちからの続き（`--review`）と途中からの再開（`--from`）は、この項目をそのまま使い、前の記録は読み直しません。項目の無い古い記録は、受けた元の無い実行として読みます。VSCode の拡張は、この項目を読まずに捨てます |

名前の取り方は、本体（`pipe_in/engine/session.py`）と拡張（`vscode/src/domain/sessionName.ts`）で同じ規則で、`tests/fixtures/session_names.json` の同じ表で確かめています。`name`・`session_id` は、前の開発フローを `archive/` へ移すときも `state.json` ごと一緒に移ります。`max_budget_usd`・`resumed` の鍵は、本体が書く鍵と拡張が読む鍵を `tests/fixtures/budget_record.json` の同じ表で確かめています。`stages[]` の `check` と `check` の `attempt` の鍵も、同じ作りで `tests/fixtures/check_record.json` の表で確かめています。`stages[]` の `group` の鍵も、`tests/fixtures/group_record.json` の表で確かめています。

時刻は、`logs/*.jsonl` の `Prompt` の行の `at`（段の始まり。同じログに何度か流したときは最後の `Prompt` の行）と、`state.json` の `pending_review.since`（確認を待ち始めた時刻）に、UTC からのずれつきで書きます（例 `2026-10-17T10:00:00+09:00`）。VSCode の拡張が、動いている段・確認待ちの時間を出すのに使います。`started_at`・`updated_at` は今までどおりずれのない書き方です。どちらも無い古い記録も、そのまま読めます。`runs[]` の `review` の要素にも、確認の結果を書いた時刻 `at` を同じ書き方で書きます。`pipe-in record check` が、確認のある段の承認より前に次の段の `begin` が書かれていないかを、この `at` と `Prompt` の行の `at` で比べます（読むだけ。`at` の無い古い記録は、違反ではなく「判定できなかった」として出します）。

新しい開発フローを始めるとき、前の終わった記録は `archive/<開始日時>/`（例 `archive/20261017-100000/`。同じ日時が重なると `-2` が付く）に、`state.json`・各段の成果物・`logs/` ごと移されます。形は `docs/pipeline/` の直下と同じです。VSCode の拡張は、この `archive/` の中の記録を「前の実行」として実行の一覧に出します（読むだけで、移すのは本体です。くわしくは [VSCode の拡張](vscode.md#実行の一覧)）。端末で流したパイプの実行（`docs/pipeline/<パイプ名>/`）は `archive/` へ移されません（会話の中で流したパイプの実行だけは、次を始めるときに移します。下の「会話の中で流した記録」）。

### 返事のファイル（`reply.json`）

VSCode の実行パネルのボタン（[VSCode の拡張](vscode.md#確認待ちをパネルのボタンで答える)）が置くファイルです。実行のフォルダ（work_dir の直下か、直下 1 段のパイプのフォルダ）の `reply.json` で、読むのは `pipe-in` 本体だけです。

```json
{"version": 1, "stage": "requirements", "id": "0a1b2c3d4e", "action": "revise", "feedback": "AC-03 を分けて"}
```

- 鍵は `version`（`1`）・`stage`・`id`・`action`・`feedback`（`revise` のときだけ、必ず付ける）です。余計な鍵は断ります。
- `action` は `approve`・`revise`・`quit` です（`--review` と同じ）。`pipe-in record review` の `approved` とは別の言葉で、`approved` と書いた返事は断ります。
- `stage` と `id` は、そのとき待っている `reply_wait` と同じでなければ断ります（古い確認への返事を通さないため）。
- `feedback` は前後の空白を取って 1〜1,000 文字（コードポイントで数える）。制御文字・書式文字・行区切りは断ります（改行とタブは通ります）。ファイル全体は 16,384 バイトまでです。
- 本体は、標準入力と一緒に 0.5 秒ごとに見て、読んだ返事は消します。断った返事も消し、理由だけを端末に出します（返事の文字は出しません）。待ち始め・流し始め・再開では、残っていた返事を消します。
- `reply.json` は予約名で、パイプの段の `output` に使えません。

`examples/truncate/` に、小さなプロジェクトで実際に流した結果があります（要件メモから合格まで、4段で約2分・約$0.85）。これはテスト先行の段を足す前（v0.1）の結果なので、ファイル名と段の数が今と違います。

## 会話の中で流した記録

`/pipe-in:pipe-run`（[プラグイン](plugin.md#pipe-inpipe-run)）で流したパイプの記録は、置き場所（`docs/pipeline/<パイプ名>/`）も、`00_input.md`・`state.json`・`logs/`・成果物・`99_summary.md` の形も、端末で流した記録と同じです。違いは次のとおりです（どれも足すだけで、古い記録は今までどおり読めます）。

- `state.json` の `driver` が `"pipe-chat"` です。`chat` の節に、司会役の覚え（始めたときのパイプの指紋・守りの確かめの状態・段を流した回数・検査の戻りの回数・次の段・人の差し戻し）が入ります。拡張や本体のほかの読み手は、この節を読みません。
- **使用量は取れません。** 会話の中で流したため、費用とトークンが分かりません。`total_cost_usd` は `null`、`usage_summary` は `{"available": false, "reason": "…"}` で、`by_model` などの表はありません。0 とは書きません。`99_summary.md` にも合計の行は出ず、「使用量は取れません」と書かれます。
- 段の実行の `cost_usd` は `null`、`num_turns` は 0 です。
- `99_summary.md` の表の列は `# | 段 | 回 | 結果 | 時間` で、費用・ターンの列がありません。守りが止めた操作は「止めた操作」の節に、効かない設定は「注意」に出ます。
- 実行のフォルダの中に、`hook/`（フックが書く守りの跡 `trace.jsonl` と、`bash = true` の段のための `bash_state.json`）と `probe/`（守りの確かめ用の範囲外のパス）ができます。段のエージェントは、どちらも書けません。終わった記録を `archive/` へ移すときは、一緒に移ります。
- VSCode の拡張では、図と段の流れ・検証の戻り・確認待ちは端末の記録と同じ形で出ます。費用だけが違い、パネルの上のバーと実行の一覧の費用は「取れない」、ウィンドウ下のステータスバーは「費用は取れません」と出て、段の 2 行目から `$` の数が消え、使用量のタブに「使用量は取れません」と理由が出ます（[VSCode の拡張](vscode.md)）。
- `pipe-in --review` では続けられません（`driver` があるため）。「会話の中で流した記録です。`pipe-in-gen chat next --pipe <パイプ名>` で続けてください」と出して止まります。

## アーティファクトに出す写し

`pipe-in live snapshot`（[使い方](usage.md#進み具合を-claude-のアーティファクトで見るpipe-in-live)）が、記録から作る小さな JSON です。リポジトリにも `docs/pipeline/` にも残らず、Claude の会話のアーティファクトのデータに入ります。ページ（`pipe-in live page`）がそれを読んで描きます。

`pipe-in live watch`（[使い方](usage.md#ターミナルで流している実行を見るpipe-in-live-watch)）は、同じ記録を読むだけで書き換えず、この写しが変わったときだけ `--out` に書きます。標準出力の行は `event`・`seq`・`final`・`empty` の4つだけで、写しに入らないもの（結果の本文・エラー・直してほしい点・`session_id`・パス）は行にも入りません。

最上位のキー（この順。記録が無いときも同じキーで、`empty` が `true`・`name` と `final` が `null`・`stages` が空になります）：

| キー | 中身 |
|---|---|
| `schema` | 写しの形の版（今は `1`） |
| `generated_at` | 写しを作った時刻（UTC、秒まで） |
| `empty` | 記録なしの形なら `true` |
| `name` | セッション名（掃除して 60 文字まで） |
| `final` | 最後の結果（終了コードの名前。終わっていなければ `null`） |
| `stages` | 段の一覧（最大 24） |
| `review` | 確認待ちの段の `{"stage": 段の名前, "id": 識別子}`。ページのボタンが答えの文を作るための値で、ないときは `null` |

`review` は、`final` が入っていなくて、確認待ちの段が `stages` にあり、段の名前が英数字・`-`・`_` の40文字までで、確認待ちの時刻（`since`）が読めるときだけ入ります。`id` は段の名前と `since` から作る小文字の16進10文字で、時刻そのものは入りません（`since` のない古い記録や `archive/` の記録は `null`）。キーを足しただけなので `schema` は `1` のままで、前の版のページは `review` を無視して見るだけで描きます。

`stages` の要素のキー：`name`・`label`（段の名前と表示名。40 文字まで）、`status`、`attempt`（最後の回。1〜999）、`started_at`（動いている段だけ）、`pending_since`（確認待ちの段だけ）、`verdict`（`test` の段だけ。`pass`・`fail`・`blocked`）、`cost_usd`・`turns`・`duration_sec`（同じ段の回の合計）。時刻はどれも UTC のずれつき（例 `2026-10-17T01:00:00+00:00`）で、ずれのない昔の書き方は、書いた機械の時刻帯と見なして直します。

`status` は次の6つです。上から最初に当てはまるものになります（ページは、写しに知らない値があれば「不明」と点線の丸のアイコンで出します）。

| 値 | 当てはまるとき |
|---|---|
| `running` | `state.json` の `open` がその段 |
| `review` | `pending_review` がその段 |
| `revised` | その段の最後の記録が「修正を依頼」（やり直しの前） |
| `failed` | その段の最後の実行がエラー |
| `done` | 実行や確認のあとで、上のどれでもない |
| `waiting` | まだ何も記録がない |

- **入れるもの**：上の表のキーだけです。知らないキーは、`state.json` にあっても入りません。
- **入れないもの**：要件メモの本文、`session_id`、読み先のフォルダのパスや手元の絶対パス（名前に混じっていれば `…` に置き換えます）、段の要約・差し戻しの理由・エラー文・`warnings` などの自由な文、ログの中身（読むのは、動いている段のログの最初の `Prompt` 行の `at` だけ）。セッション名は入ります。
- **上限**：写し全体は 32 KiB まで（超えるときは末尾の段から落とします）。読む `state.json` は 4 MiB まで（超えると「記録なし」の形）。ログは先頭 64 KiB の中の最大 50 行だけを見ます。文字の制御文字・方向を変える記号・ゼロ幅の文字は取り除きます。
- **同じ記録なら同じ中身**：「今」は引数で受けるので、同じ記録と同じ時刻なら、バイト列まで同じです。
- **`schema` の約束**：キーを**足す**だけなら `schema` は 1 のままです（ページは知らないキーを無視します）。意味を変える・消すときは `schema` を上げ、ページは版が違う写しを「この写しの版には対応していません」と出して描きません。

## まとめに出る使用量

各段の最後に Claude Code が返す結果（`ResultMessage`）と、途中の利用枠のイベント（`RateLimitEvent`）、開始時の環境（`SystemMessage` の `init`）から集めます（`pipe_in/usage/metrics.py`、表は `pipe_in/usage/report.py`）。`99_summary.md` に、次の節が出ます。

<details>
<summary>節ごとの中身</summary>

| 節 | 中身 |
|---|---|
| トークンの内訳 | 段ごとの入力・キャッシュ書き込み・キャッシュ読み込み・出力・うち thinking・キャッシュ再利用率・API 待ち時間と合計 |
| モデル別 | モデルごとのトークンと費用 |
| 環境 | 使われたモデル、Claude Code の版、認証の出どころ、許可のモード、費用の根拠、途中で止まった段 |
| 利用枠 | 5時間枠・7日枠の使用率（開始 → 終了。途中で枠が戻ったときは最大値も）、枠が戻る時刻、超過利用の可否 |

</details>

> [!NOTE]
> 費用は定価での概算（`costBasis: list`）です。サブスクリプションでログインしている場合は、利用枠の使用率のほうが実際の負担に近い値です。

## 終了コード

| コード | 意味 |
|---|---|
| 0 | 検証まで合格（パイプは最後の段まで終わった） |
| 1 | 差し戻しの上限までテストが通らなかった（パイプは検証に通らなかった） |
| 2 | 確認の段階で中止した |
| 3 | 段の実行が失敗した（文書が作られない、上限に達した、テストのない AC が残った、パイプの分岐先が返らない・max_steps を超えた、SDK の受信バッファの上限を超えた（検証の段でも）など） |
| 4 | テストを実行できなかった（環境の問題など。差し戻しはしない） |
| 5 | 人の確認を待っている（`--pause` のとき。`--review` で続ける） |
| 130 | Ctrl+C で中断（`--from` で再開できます） |
