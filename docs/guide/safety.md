# 安全のしくみ

[ガイドの目次](README.md) · [README](../../README.md) — 段ごとに書ける範囲と、どの段でも止める操作の説明です。

## 段ごとの役割と書き込める範囲

| 段 | できること | 書き込める範囲 |
|---|---|---|
| 要件定義 | コードを読む | `01_requirements.md` だけ |
| 設計 | コードを読む | `02_design.md` と、`domain_dir` を設定していればドメインの文書 |
| テスト先行 | 読む・書く・コマンド実行 | テストファイルと `03_red_tests.md`。**製品コードは書けない** |
| 実装 | 読む・書く・コマンド実行 | 製品コードと `04_implementation.md`。**テストファイルとドメインの文書は書けない** |
| 検証 | 読む・書く・コマンド実行 | テストファイルと `05_test_report.md`。**製品コードは書けない** |

`.claude/`・`.git/`・`.pipe-in/`・`pipeline.toml`・前の版の置き場所（[移行](migrate.md)）は、設定なしで、どの段も書けません（D0084）。`protected_paths` は、そこに足して守りたいパスを書くものです（外す設定はありません）。`work_dir` をこれらの中や `.`（プロジェクトそのもの）にすると、段が成果物を書けなくなるので、流す前に直し方つきで止まります。`--after` で受けた前のパイプの記録（前の `state.json`・`00_input.md`・`logs/`・成果物）も、どの段も書けません（[パイプをつなぐ](pipes.md#パイプをつなぐ--after)）。実行パネルのボタンの返事を置くファイル `reply.json`（実行のフォルダの直下）も、どの段も書けません（[下](#vscode-の拡張から返事を置くときの守り)）。

書き込める範囲は、`Write`・`Edit` だけでなく `Bash` にも掛かります（D0036）。コマンドの文字列から書き込み先が読める形、つまりリダイレクト（`>`・`>>`）・`tee`・`sed -i`・`perl -i`・`cp`・`mv`・`ln`・`install`・`touch`・`rm`・`truncate`・`dd of=`・`find -delete`・`git restore`/`rm`/`mv`・`python -c`（とヒアドキュメント）・`node -e` の中の書き込みは、先が範囲の外かプロジェクトの外なら止めます。`bash -c`・`$(...)`・`;`・`&&`・`|` で続くコマンドや、`cd` で移った先も読みます。

- `/dev/null`・`2>&1` などの付け替えと、`/tmp`・`$TMPDIR` の下への書き出しは通します（例：`pytest -q 2>&1 | tee /tmp/out.log`）。
- 書き込みの形なのに先が変数や `$(...)` で読めないときは止めます。先を文字で書いてください。
- 先の最後に glob（`*`・`?`・`[`）を含むもの（`rm *.py`）も、どのファイルか決まらないので止めます（`/tmp` の下は通します）。`find . -delete`・`git restore .` のように根や上のフォルダを指す操作は、その下に実際にあるファイルを見て、1つでも範囲の外があれば止めます。
- プロジェクトの中の `mkdir` と、テストを流すコマンド（`pytest`・`npm test` など）が書く副作用は止めません。
- **サンドボックスではありません。** `python file.py`・`make`・`sh script.sh`・`| sh` のように、書くコードが別の所にあるものは見分けられず、通ります。段の指示文で「Bash で範囲の外を書かない」と書き、批評や検証で差分を見てください。残る道の一覧は決定の記録 `docs/decisions/D0036-bash-write-guard.md` にあります。

実装とテストの担当を分けているのは、実装の担当が「テストを都合よく直して通す」ことを防ぐためです。実装の担当はテストに不満があれば、実装の記録に「テストへの異議」として書き、次の検証の段がそれを判断します。

テスト先行の段は、判定（`red` / `blocked`）と「AC とテストの対応」を構造化出力で返します。パイプラインは要件定義書から `AC-数字` を拾い、テストのない AC があれば同じ会話で一度だけ補わせ、それでも残れば止めます（終了コード 3）。`test_command` があれば、テスト先行のあとにも実行し、通ってしまったら「赤になっていません」と注意を残します（止めはしません）。

テストファイルの判定は、`tests/`・`test/`・`__tests__/`・`spec/`・`specs/` の中にあるか、`test_*.py`・`*_test.py`・`*_test.go`・`*.test.*`・`*.spec.*`・`*_spec.rb`・`conftest.py` の名前かで行います。足りなければ `extra_test_globs` に追加してください。

## どの段でも止める操作

`git push`、`git reset --hard`、`git clean -f`、ブランチの切り替え、再帰的な削除（`rm -r`）、`sudo`、`curl`・`wget`・`ssh` などの外部通信、パッケージの公開、プロジェクトの外への書き込み、Web 検索と Web 取得（パイプでは、`web` を書いた段を除く）。

また、段ごとに許したツール（`pipe_in/dev/specs.py`・`pipe_in/pipe/specs.py` の `allowed_tools`）と、読むだけの道具（`Read`・`Glob`・`Grep`・`Skill`・`ToolSearch`・`TodoWrite`）と構造化出力を返す道具（`StructuredOutput`）以外は、すべて止めます。PowerShell・MCP のツール・サブエージェント（`Agent`・`Task`）などから、書き込み範囲や危ない操作の判定をすり抜けられないようにするためです。PowerShell は最初から使えないツールにも入れています。

次のものも止めます。段の中でサブエージェントの呼び出しが回り続けたり、段のあとに作業が残ったりしないようにするためです。

- `Bash` の、裏で動かす形（`run_in_background` に `false` 以外の値）の呼び出し。どの段でも止めます（パイプの段も、`/pipe-in` の開発の段も）。`Bash` は `run_in_background` を書かなければ待つ形です。
- サブエージェント（`Agent`・`Task`）の、`run_in_background: false` を付けない呼び出し。メインから呼ぶと、書かないときは裏で動くためです（[公式の文書](https://code.claude.com/docs/en/agent-sdk/python)）。段は応答が終わると結果を待てないので、`run_in_background: false` を付けて呼び直させます。`isolation`（worktree などで動かす）を付けた呼び出しも止めます。
- サブエージェントの中からのサブエージェントの呼び出し（入れ子）。フックの入力の `agent_id` で見分けます（この印は、同じプロセスの中で動くチームの仲間にも入るので、それも止めます）。SDK にもサブエージェントの道具から `Agent`・`Task` を外すよう渡し、環境変数 `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1` で深さを 1 に絞ります。
- 1回の実行での、`max_agent_calls`（既定 20）回を超えるサブエージェントの呼び出し。止めた呼び出しは数えず、超えたあとは何度呼んでも止めます。上限の無いガードは作れません（[パイプの書き方](pipes.md#agent-sdk-の設定)）。

あわせて、段の SDK には環境変数 `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` を渡し、裏で動く作業そのものを切ります。`Bash` は時間切れになったコマンドを裏に回すことがあり、これはフックでは止められないためです。

止めた操作はその場で表示され、`99_summary.md` にも残ります。仕組みは `pipe_in/engine/guard.py` の PreToolUse フックで、すべてのツールに掛かり、自動承認したツールにも効きます。

## 会話の中で流すときの守り

`/pipe-in:pipe-run`（[プラグイン](plugin.md#pipe-inpipe-run)）で流す段には、SDK のガードが使えません。代わりに、プラグインのフック（`pipe-in-gen guard-hook`）が、段を受け持つ `pipe-stage` の道具の呼び出しを 1 つずつ見て、止めるかを決めます。

- **範囲は今の段の定義から決まります。** フックは記録（`state.json`）で「いま開いている段」を探し、その段の `access`・`writes`・`bash` を、本体の SDK の道と同じ部品（`guard.check_tool`）に渡して判断します。結果は本体と同じです（上の「段ごとの役割と書き込める範囲」「どの段でも止める操作」がそのまま掛かります）。
- **会話の道だけ足して止めるもの。**
  - 実行の記録（`state.json`・`logs/`・`hook/`・前のパイプの記録・`archive/`）への書き込み。`access = "docs"` で `docs_dir` が記録の場所を含んでいても止めます。成果物だけは書けます。
  - 流しているパイプのフォルダ（定義と指示文）への書き込み。置き場所によらず、本体の道と同じく書けません。`.claude/`・`.git/`・`.pipe-in/`・`pipeline.toml` は、D0084 から本体の道でも設定なしで止めます（上）。
  - `Skill`（範囲外の操作をする道を残さないため）。
  - 段が開いている間の、`pipe-stage` と `pipe-probe` 以外のエージェント。pipe-builder や pipe-judge も、会話の道の段の間は止まります。`agent_type` が文字でない呼び出しも止めます。
  - 確かめ役 `pipe-probe` の、読む道具（Read・Glob・Grep）以外。
- **止める側に倒します。** 記録が読めない・壊れている、開いている段が無い・2 つある、`pipe.toml`・`pipeline.toml` が始めたときから変わった（指紋が違う）、段の名前が定義に無い、フックが判断中に例外を出した、のどれでも、`pipe-stage` の呼び出しをすべて止めます。名前の判定は完全一致だけです（`pipe-stage-x`・`my-pipe-stage` は `pipe-stage` ではありません。プラグインの名前つきの `pipe-in:pipe-stage` は同じに扱います）。
- **`bash = true` の段** の Bash は、本体と同じ書き込みの判断（`bashwrite.py`）に掛けます。`cd` をまたいだ覚えは、フックの呼び出し（別のプロセス）をまたぐので `hook/bash_state.json` に残し、読めないときは相対パスの書き込みを止めます。
- 止めた操作は `hook/trace.jsonl` に残り、`99_summary.md` の「止めた操作」に出ます。

**流す前の守りの確かめ（`chat probe`）。** フックが入っていても、使う環境でフックに `agent_type` が届かなければ、段の守りは効きません。そこで、流す前に毎回確かめます。司会役が乱数入りの範囲外のパス（どの `access` の範囲にも入らない場所）を決め、確かめ役 `pipe-probe` にそこへ `Write` を 1 回だけ試させます。そのあとで司会役が、(1) そのパスにファイルができていないこと、(2) フックの跡に「`pipe-probe` の `Write` をそのパスで止めた」行があること、の両方を自分で読み、そろったときだけ「確かめ済み」にします。確かめ役やサブエージェントの返事は信じません。**そろわなければ、段は流しません。** フックが起動できない・時間切れのとき、Claude Code はその呼び出しを止めずに進めます（公式の文書）。確かめは、この場合も跡が残らないので通らず、流しません。確かめのあとの段の途中でフックが動かなくなった場合は防げません。 守りなしで流す道はありません。確かめ済みの印は、その実行だけに効き、始め直せば消えます。

使える場所と、確かめられなかったときの扱いは[プラグイン](plugin.md#使える場所と使えない場所)にあります。SDK のガードと同じく、`python file.py` のように書くコードが別の所にあるものは見分けられません（上の「段ごとの役割と書き込める範囲」の注意）。

## 4つの守りの比較

同じ道具の呼び出しを、守りごとに通すと結果が違います。違いを `tests/guard_matrix.py` の表に実測で書き、`tests/test_guard_matrix.py` が 1 行ずつ 9 列に流して固定しています。守りが変わって結果が動くと、このテストが落ちるので、意図した変更かをそのとき確かめられます。

列は、SDK の道（既定の守りだけ／同じ場所を `protected_paths` にも書いたとき）、会話の道、プラグインの作る役 `pipe-builder` と審査役 `pipe-judge`、開発用フックの 4 つの役（`analyst`・`tester`・`coder`・`verifier`）です。SDK と会話の道は、段の種類（`access`・`bash`・`agents`）で結果が変わるので、行ごとにその種類の段で流しています。守りごとの差が出る行は次のとおりです（○ 許す、× 止める、－ その守りでは呼べない組み合わせ）。

| 呼び出し | SDK（既定） | SDK（同じ場所も書いた） | 会話 | 作る役 | 審査役 | analyst | tester | coder | verifier |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `.claude/`・`.git/` への書き込み（相対・`..`・MultiEdit・Bash の `>`・`tee` なども同じ） | × | × | × | × | × | × | × | × | × |
| `.pipe-in/`・`pipeline.toml` への書き込み | × | × | × | × | × | × | × | ○ | × |
| 流しているパイプのフォルダへの書き込み | × | × | × | ○ | × | × | × | ○ | × |
| ふつうのコードへの Write | ○ | ○ | ○ | × | × | × | × | ○ | × |
| 成果物への Write | ○ | ○ | ○ | × | × | × | × | × | × |
| `git add`・`git commit` | ○ | ○ | ○ | × | × | × | × | × | × |
| `git push` | × | × | × | × | × | × | × | × | × |
| `pipe-in-gen list` | ○ | ○ | ○ | ○ | × | × | × | × | × |
| `pytest` | ○ | ○ | ○ | × | × | × | ○ | ○ | ○ |
| `Skill` | ○ | ○ | × | × | × | × | × | × | × |
| `Agent`・`Task`（`agents` に書いた段） | ○ | ○ | － | × | × | × | × | × | × |

4 か所（`.claude/`・`.git/`・`.pipe-in/`・`pipeline.toml`）は、設定なしで、どの守りでも止めます。開発用の `coder` だけ `.pipe-in/`・`pipeline.toml` に書けます。SDK の道の 2 つの列（既定／同じ場所も書いた）が同じなのは、`protected_paths` に既定と同じ場所を書いても結果も説明も変わらない（重なりは 1 回だけ数える）ことを示します。PowerShell・MCP・Bash の `$(…)` は、どの守りでも道具ごと止めます。

**Skill と Agent の差。** `Skill` は SDK のガードの「いつも許す」一覧に入っていて、`allowed_tools` に書かなくても通ります。スキルの読み込みは別の道で、それ自身には書き込みも Bash の範囲もなく、中で呼ぶ道具は、このフックをあらためて通るからです。`Agent`・`Task` は、サブエージェントが別の道具の組で動き、段の範囲とは別に書き込めてしまうので、`allowed_tools` に書いた段で、裏で動かさず・`isolation` なし・入れ子でなく・回数が上限内のときだけ通します。会話の道は、スキルの範囲の外に出る道を残さないため `Skill` を止め、`agents` を持つ段はそもそも会話の中で流せません。この表は今の結果を固定するだけで、`Skill` を SDK の道でも止めるかは別に決めます。

**リンクを経た道で、今は通る組が 2 つあります。** 書いてよい場所の中のリンクが `.claude/settings.json` を指すとき、SDK の道と会話の道は `Path.resolve()` でリンクの先をたどって止めます。いっぽう、プラグインの作る役（パイプの `prompts/` の中のリンク）と開発用の `coder`（`src/` の中のリンク）は、パスの文字を整えるだけ（`normpath`）でリンクをたどらないので、通ります。今の動きとして表に固定してあり、直すかは別の件で決めます。

## VSCode の拡張から流すときの守り

VSCode の拡張の作業台にある「流す」（[作業台から流す](vscode.md#作業台から流す)）は、段の外の入口です。段の中の守り（上の SDK のガード）とは別に、拡張の側で次を守ります。

- **起こすのは決まった形の `pipe-in` 1つだけ。** 拡張が起こしてよい子プロセスは、作業台の「流す」が起こす `pipe-in` だけです。VSCode の Tasks API の `ProcessExecution` で起こし、シェルを通さず、実行ファイルと引数の配列で渡します（`child_process`・`ShellExecution`・端末への文字送りは使いません）。環境変数は足しません。
- **実行ファイルは絶対パス。** 拡張が絶対パスに決めてから起こします。PATH の相対の項目や、作業フォルダの下の同名のファイルは使いません（Windows は `.exe`・`.com` だけ）。
- **引数は決まった形。** `--pipe=<パイプのフォルダ>`・`--project=<プロジェクト>`、依頼メモがあるときだけ `--text=<依頼メモ>`。依頼メモは `--text=` の中の1つの要素なので、旗やシェルの文字として読まれません。依頼メモは空（`required` のとき）・4,000 文字超・NUL・壊れた文字なら流しません。
- **パネルから来る値は依頼メモだけ。** パイプのフォルダとプロジェクトは、開いたパイプとワークスペースから拡張が決めます。流してよいかは、パネルの判断を信じず、拡張が自分の持つ値でもう一度判断します。
- **設定 `pipe-in.command` はユーザーの設定だけ。** ワークスペースの設定（`.vscode/settings.json`）では決められません（`"scope": "machine"`）。絶対パスだけ通し、相対パス・`-` で始まる値・`pipe-in` のほかの名前だけの値は断ります。値は丸ごと 1 つのファイルの場所として扱い、引数には分けません（引数を付けた値は、その名前のファイルが無いので流れません）。
- **信頼していないワークスペースでは動きません。** 拡張が `capabilities.untrustedWorkspaces` で対応しないと宣言し、流す前にも `vscode.workspace.isTrusted` を見ます。
- **二重に流しません。** 同じパイプは、実行中の記録（メモリだけ）がある間は流せません。作業台を閉じても外れません。

`guard.py` 系（SDK のガード・プラグインのフック）は、この機能のために狭めていません。くわしい形は `docs/decisions/D0078-run-from-editor.md`、拡張の説明は [VSCode の拡張](vscode.md) にあります。

## VSCode の拡張から返事を置くときの守り

実行パネルの確認待ちの帯のボタン（[確認待ちをパネルのボタンで答える](vscode.md#確認待ちをパネルのボタンで答える)、D0079）は、拡張が work_dir に書く、ただ 1 つの例外です。それ以外は今までどおり、拡張は work_dir を読むだけです（作業台の「保存」でパイプの置き場所の決まったファイルを書くことと、拡張の保存場所・`workspaceState` に書くことは別の決まりです）。

- **書くのは返事のファイル 1 つだけ。** 実行のフォルダ（work_dir の直下か、直下 1 段のパイプのフォルダ）の `reply.json` を、新しく作ります。上書きしません。すでにあるもの（ファイル・リンク・フォルダ）は断ります。一時ファイルは作りません。`..`・絶対パス・2 段・`archive`・`.` 始まりの名前や、`reply.json` 以外のファイル名を渡す道はありません（`vscode/src/infra/fsReplies.ts` が絞ります）。
- **段を流さず、判断も持たない。** 返事を読んで動くのは `pipe-in` 本体だけで（`pipe_in/engine/reply.py`・`checkpoint.py`）、段と識別子の照合も本体がします。拡張が子プロセスを起こすのは、これまでどおり作業台の「流す」だけです。
- **パネルから来る値は、動作と直してほしい点の文字だけ。** 置く場所は拡張が作った実行の一覧から、段と識別子は拡張が読み直した記録から決めます。書く直前に記録を読み直し、見ていた確認と同じときだけ書きます。
- **見ていた確認にだけ答える。** 本体は、待っている段と識別子（待ちごとの乱数）と合わない返事を断って消します。待ち始め・流し始め・再開では、残っていた返事を消します。返事の場所がリンクなら、先を読まずにリンクだけを消します。
- **段のエージェントは書けない。** `reply.json` は、開発フローのどの段の書ける範囲からも、パイプのどの段の書ける範囲（`access`・`writes`・`docs_dir` が何でも）からも外してあります（`pipe_in/engine/spec.py` の `protect()`）。`Write`・`Edit`・Bash の書き込みの形が止まります。
- **標準入力が端末のときだけ受け付ける。** パイプ・ファイルで答えを渡す実行は、今までの道のままで、返事のファイルを読みません。
- **守りの限界。** Bash を許した段で、書ける場所が実行のフォルダを含むとき（パイプの `access = "docs"` で `docs_dir` が work_dir を含む、など）は、フォルダごとの写し（`cp -r`・`rsync`）やスクリプトの実行（`python x.py`）で、返事のファイルを書けてしまうことがあります。これは、前のパイプの記録や `protected_paths` の守りと同じ、今の守りの限界です（[上](#段ごとの役割と書き込める範囲)の「サンドボックスではありません」）。人の確認を固い関所にしたい段には、Bash を許さないでください。人の確認は、悪意のあるエージェントに対する固い境界ではなく、進め方の関所です（今までと同じです）。
- SDK のガード（`pipe_in/engine/guard.py`）とプラグインのフック（`generator/guard_hook.py`）は、この機能では変えていません。段の書ける範囲から `reply.json` を外しただけなので、止める範囲は増えるだけです。

## フックの入力が読めないとき

プラグインのフック（`pipe-in-gen guard-hook`）は、止める側に倒れる作りです。会話の道のフックも同じ入口を通ります。

- **入力が読めなければ止めます。** 標準入力が読めない・UTF-8 でない・壊れた JSON・入れ子が深すぎる・JSON の最上位が辞書でない、のどれでも、理由つきで止める返事を出します（終了コードは 0）。標準入力は 16 MiB（`MAX_STDIN_BYTES`）までしか読まず、超えたら読めない入力として止めます。
- **止める返事を書き出せなければ、標準エラーと終了コード 2 で止めます。** 標準出力が閉じている・いっぱいなどで返事を書けないとき、理由を標準エラーに書いて終了コード 2 にします（Claude Code は 2 を操作の中止として扱います）。標準エラーも書けなければ、理由は出せませんが、終了コード 2 は変えません。本物の起動のときだけ、書けなかった出力を捨て先に付け替えて、終了コードが別の値（120）に化けないようにします。
- **文字列でも null でもない `agent_type` は、読む道具以外を止めます。** 呼び出したのがだれか分からないので、読む道具（Read・Glob・Grep）だけ通し、ほかはすべて止めます。理由に入れるのは型の名前だけです。`agent_type` が無い・null・空文字・ほかの名前の文字列には何もしません（メインなどに今までどおり）。

## アーティファクトに送る写し

`/pipe-in --artifact` を使うと、進み具合の写しが Claude のアーティファクトのデータ（クラウド上）に書かれます。入るのはセッション名・段の名前と状態・回数・時刻・費用/ターン/時間の数字などだけで、要件メモの本文・`session_id`・パス・自由な文は入りません（[アーティファクトに出す写し](records.md#アーティファクトに出す写し)）。セッション名には、要件メモの最初の行から作った名前が入るので、名前に載せたくない言葉があれば `--name` で付け替えてください。使わなければ何も送りません。

## ページから送る答え

`/pipe-in --artifact` で新しく公開したページは、確認待ちの行のボタンから、アーティファクトのコメントで「承認・差し戻し・中止」を Claude の会話に送れます（[ボタンで答える](usage.md#ページのボタンで答える)）。コメントの本文は外から来た文字なので、会話に届いてもそのままは信じず、次の守りを通します。

- 決まった形の文だけを答えとして読みます（`pipe-in: <approve|revise|quit> <段> <識別子>`。1行目だけで動作が決まります）。大文字小文字・空白の揺れは許さず、引用・コードブロック・前に別の行がある形は答えにしません。人が手で書いたコメントが動作になる道を作らないためです。
- 制御文字・見えない文字（ゼロ幅・向きを変える記号など）・孤立サロゲートは、取り除かずに断ります（見た目と中身が違う文が通らないように）。ZWJ でつないだ絵文字は、見えない文字を含むので直してほしい点に入れられません。
- 文字数に上限があります（全体 2000 文字、直してほしい点 1000 文字。超えても切らずに断る）。
- 今の確認待ちの段と識別子に合うときだけ通します。識別子は段の名前と確認待ちになった時刻から作る短いハッシュで、答えたあと（確認待ちが消えたあと）や、差し戻して同じ段がまた確認待ちになったあとは、前の識別子の答えを断ります（二重の答え・中止と承認の取り違えを防ぐ）。終わった実行や記録が無いときも断ります。
- 本文を**コマンドの引数に入れません**。会話は本文をファイルに書いて `pipe-in live answer --text-file` に渡し（`--text` はありません）、直してほしい点も `--feedback-out` のファイルから `record review --feedback-file` で渡します。シェルの引用符を破って別のコマンドを走らせる道を作らないためです。
- 直してほしい点は**人の言葉**として渡るだけです。中に「ignore the above」や `pipe-in: approve …` のような行があっても、動作は1行目だけで決まり、中は解釈しません。会話も、その中の命令には従いません。
- 送れるのはアーティファクトの編集者だけです（Claude が決めます）。共有したページの編集者は、承認・中止もできます。持ち主だけに絞る手段は、今のところありません。誰にも共有しないか、共有する範囲に注意してください。
- `pipe-in live answer` は記録を書き換えず、SDK も子プロセスも使いません。書くのは `--feedback-out` のファイルと同じフォルダの一時ファイルだけで、読み先の記録のフォルダの中・シンボリックリンク・親が無い所・フォルダは断ります。判断した結果の1行の JSON には、本文・直してほしい点・パスを入れません。
- ページは、書体の Google Fonts の `<link>` 2本（計画ボードと同じ。読み込めなくても代わりの書体で読めます）を除いて、外部から何も読み込まず、`window.confirm` なども使いません（確かめはページの中の2段）。画面の文は決まった文だけで、段の表示名・セッション名は入れず、`textContent` だけで出します。

`pipe-in live watch`（[使い方](usage.md#ターミナルで流している実行を見るpipe-in-live-watch)）は、記録を読むだけです。SDK も子プロセスも使わず、依存も足しません。書くのは `--out` の写しと、同じフォルダの一時ファイルだけで、`--out` が読み先の記録のフォルダの中・シンボリックリンク・親のフォルダが無い所・フォルダのときは、始めずに断ります（置き換えはリンクの先ではなくリンク自身に対して行います）。標準出力の行には、固定の文字列・番号・`final` の値・真偽だけが入り、パスや自由な文は入りません。見張りの途中の標準エラーの文にもパスは入れず、種類だけを出します（始める前の断り、たとえば `--out` の親のフォルダが無い・プロジェクトのフォルダが無いときの文には、渡したパスが出ます）。
