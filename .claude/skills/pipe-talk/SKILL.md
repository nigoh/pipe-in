# /pipe-talk — 壁打ちして、次の作業へ回す

人と一緒に考えを詰め、区切りで要点をまとめて、中身に合わせた次の作業へ回す。回す先は、GitHub の issue・デザイン・`/pipe-in`・計画ボードの4つ。

## 必ず守ること

- 外へ出す操作（issue を作る・Figma に書く・アーティファクトを公開する）は、どれも、出す中身を全文見せて、人の承認を得てからだけ行う。`gh issue create` も、GitHub の MCP の道具で issue を作るのも同じ（`gh issue create` は `.claude/settings.json` の `ask` にも入れてある。ただし当たるのは Bash の道具で流す決まった形だけ）。計画ボードには `/pipe-talk` の中では書かない（人が流す `/pipe-plan add` が書く。7.）。
- 書くのは要約のファイルだけ。要約は手元にだけ残す（`docs/talk/`。`.gitignore` 済み）。書く前に `git check-ignore` で無視されているかを確かめる。ほかのファイルには書かない（例外は、issue の本文を渡す一時ファイルだけ。会話のスクラッチの場所に置き、リポジトリの中には置かない）。コミット・push はしない。
- issue の本文・デザインに渡す文・要件メモ・計画ボードの項目に、秘密（API キー・トークン・`.env`・鍵ファイル）・手元の事情（ユーザー名の入った絶対パス・社内や私的なプロジェクトの名前・メールアドレス）・要約のファイルのパスを入れない（CLAUDE.md の「公開リポジトリとしての注意」）。見せる前に確かめる。
- `/pipe-in`・`/pipe-plan` は Claude からは始めない。人がメッセージの先頭に貼って流す1行を示す。
- 候補は、人が選ぶまでどれも行わない。
- 決まりがあやふやになったら、思い出しで進めず、この SKILL.md を読み直す。

## 0. 始める

話したいこと: $ARGUMENTS

（空なら、何を話したいかを一言で聞いてから始める。）

## 1. 壁打ち

- 問い返す・案を比べる・前提を確かめる。答えを急がない。人の考えをなぞるだけにせず、気になる点・ほかの案・見落としていそうなことも言う。
- コードや文書を読むのはよい（Read・Grep・Glob）。書かない・作らない（要約は 2. で書く）。
- 区切りは、人が「まとめて」と言ったとき。Claude が一区切りと見たときは、まとめてよいかを人に確かめてから。

## 2. まとめる

- 要約は次の3つの見出しで作り、会話に見せる。
  - 決まったこと
  - 残った問い
  - やりたいこと
- 置き場所は `docs/talk/<日時>-<名前>.md`。`<日時>` は手元の時刻の `YYYYMMDD-HHMMSS`、`<名前>` は話の中身を表す英小文字・数字・`-` だけ（決定の記録の名前と同じ決まり）。1回の壁打ちで1つのファイルにし、区切りが何度もあれば同じファイルに書き足す。
- 書く前に `git check-ignore -q docs/talk/<日時>-<名前>.md` で無視されているかを確かめる。無視されていなければ（`.gitignore` にその行が無い古い枝など）、書かずにそのことを伝える（要約は会話に見せたまま）。
- 書くのは、今の作業フォルダ（main か worktree）の `docs/talk/` の下だけ。ほかのファイルには書かない。

## 3. 次の作業の候補

要約に合わせて、下の4つから候補を選び、理由を添えて出す。いくつ選んでもよく、どれも選ばなくてもよい。人が選ぶまで、どれも行わない。

| 回す先 | 向いている話 |
| --- | --- |
| issue を作る（4.） | あとでやる・人に頼む・不具合の控え |
| デザインに回す（5.） | 画面・見た目の話のときだけ |
| `/pipe-in` で実装する（6.） | すぐ作れるほど決まった機能・直し |
| 計画ボードに足す（7.） | まだ決まっていない、やりたいこと |

## 4. issue を作る

1. 題と本文を作り、会話に全文見せる。本文は要約から作り、「必ず守ること」の入れないもの（秘密・手元の事情・要約のファイルのパス）が入っていないかを、見せる前に確かめる。
2. 人の承認を得てから、`gh issue create --title "<題>" --body-file <一時ファイル>` で作る。一時ファイルは会話のスクラッチの場所に置き、リポジトリの中には置かない。直してと言われたら、直して見せ直す。
3. GitHub の MCP の道具で作るときも、同じく本文を見せて承認を得てから。
4. 作ったら、issue の番号と URL を会話に見せる。要約には issue の番号だけを書き足してよい。URL はリポジトリのファイル（要約も含む）に書かない。
5. `gh` が無い・ログインしていないときは、そう伝えて止まる（題と本文は見せたまま。人が手で作れる）。

## 5. デザインに回す

- 画面・見た目の話のときだけ候補にする。Claude のアーティファクトの Design か Figma かを、人に選ばせる。
- 渡す内容（どの画面か・目的・決まったこと）を見せて、承認を得てから行う。色・部品・言葉づかいは `docs/design/README.md` の決まりに沿う。
- 選んだ道具が会話に無ければ、そう書いて止まる（渡す内容は見せたまま）。

## 6. `/pipe-in` で実装する

- 要約を要件メモの形（作りたいこと・人と決めたこと・残った問い）に整えて見せる。
- `/pipe-in` は人が呼ぶスキルなので、Claude からは始めない。人がメッセージの先頭に貼って流せる `/pipe-in <要件メモ>` の1行を示す。

## 7. 計画ボードに足す

- やりたいことを、1件ずつの短い文に整えて見せる。
- `/pipe-plan` も人が呼ぶスキルなので、人が流せる `/pipe-plan add <やりたいこと>` の行を示す（ボードへは `/pipe-plan` が書く。`/pipe-talk` の中では書かない）。人がその行を流すことを、その項目を足す承認とみなす。

## してはいけないこと

- 中身を見せずに、または承認なしに、外へ出す。
- 要約のほかのファイルを書く（issue の本文の一時ファイルだけは例外。「必ず守ること」）。コミット・push をする。
- issue・アーティファクト・計画ボードの実際の URL やセッション ID を、リポジトリのファイルに書く。
- 人の発言にない秘密や手元のパスを、本文や要約に入れる。
