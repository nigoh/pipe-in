# /pipe-design — 画面の見本を触って比べ、決めて残す

「なんとなく気持ちよくない」画面を、言葉で詰めるより先に、触って比べられる見本で決める。流れは、不満を言葉にする → 見本を作る → 良さの条件を調べる → ★ を読んで決める → まとめて残す、の5つ。

## 必ず守ること

- 外へ出す操作（アーティファクトを公開する・issue を作る・リポジトリにコミットする・push する・PR を作る）は、どれも、出す中身を見せて人の承認を得てからだけ行う。issue の本文と要約は全文を見せる。見本は、どの画面の・何を比べるか・つまみと選択肢の一覧を見せる。
- 人に聞く所（不満の中身・承認・割れた所の選び）は、質問欄（AskUserQuestion）で聞く。1回に1〜4問、1問に2〜4択で、推しを添える（CLAUDE.md の「必ず守ること」）。
- 見本は、明るい画面と暗い画面の両方で読めるようにする。色は役の名前で決め、文字は 4.5:1・枠や線は 3:1 以上の対比にする（mock.md）。
- 見本の数字・サービス名・料金は作りものにし、そう見本の中に書く。本物の記録・秘密・手元の事情（ユーザー名の入った絶対パス・私的なプロジェクトの名前・メールアドレス）を、見本・issue・要約に入れない（CLAUDE.md の「公開リポジトリとしての注意」）。
- 良さの条件は、出典を開いて確かめたものだけを使う。調べものは、軽いモデルで回す調べ係 `pipe-in-ux-researcher` に任せる（メインの重いモデルで回さない）。
- ★ を読むまで、案を決めつけない。★ と良さの条件が食い違う所は、人に聞く。
- 書くのは、見本の HTML とその README（対象のリポジトリの `docs/design/`）・要約（`docs/talk/`）・issue の本文の一時ファイル（会話のスクラッチの場所）だけ。コミット・push は人に言われたときだけ。
- 決まりがあやふやになったら、思い出しで進めず、この SKILL.md と補助ファイル（`mock.md`・`favs.md`）を読み直す。

## 0. 始める

話したいこと: $ARGUMENTS

（空なら、どの画面のどこが気になるかを一言で聞いてから始める。）

## 1. 不満を言葉にする

- 先に対象の今の画面を読む（画面の撮影・部品のファイル・使い方の文書）。読まずに案を出さない。
- 質問欄で、まとめて聞く。
  - どの瞬間か（いくつでも）：押しても手応えがない／長くて迷子になる／文と但し書きが多い／見た目と動きが硬い
  - どの画面か：スマホ・PC・両方
  - 直す先：どのコードか（作り直し中のものがあれば、どちらを直すか）
  - どこまで変えてよいか：構成から組み替える／今の構成のまま磨く／案を見てから決める
- 答えに合わせて、骨組みの案を2〜3つ比べ、推しを1つ出す（例：操作と結果を同じ画面に置く形・一歩ずつ進む形・今の形のまま要約だけ追わせる形）。気になる点（テストの基準の撮り直し・公開の予定との順番・デザインの決まりとの関わり）も言う。

## 2. 見本を作る

- 作り方は `mock.md` に従う。互いに独立したつまみ（4〜7本）に分け、選択肢を2〜6つずつにする。今の形を、必ずどれかの選択肢に入れる。
- 公開する前に、渡す内容（どの画面か・目的・つまみと選択肢・おすすめの案の数）を見せ、質問欄で承認を得る。
- 公開の前に1回だけ、ブラウザで開いて、全部のおすすめの案を押し、明るい画面と暗い画面・スマホの幅で、エラーと横のはみ出しが無いことを確かめる。
- 人が「もっと」「全部」と言ったら、つまみ・選択肢・構成の見本を足す。1枚が大きくなりすぎたら、見本を分けて互いにリンクする（例：画面全体と、その中の図）。

## 3. 良さの条件を調べる

- 調べ係 `pipe-in-ux-researcher` を、テーマごとに分けて同時に呼ぶ（例：その種の画面〔料金の計算機など〕・手応えと動き・情報の量と日本語の画面）。渡すのは、テーマ・画面の種類・いまの不満・条件の ID の頭文字だけ。手元の事情は渡さない。
- 報告から、開いて確かめた出典のある条件だけを集める。調べ係が「推測」「確かめられなかった」と書いたものは入れない。
- つまみの選択肢ごとに、○ 合う・△ 注意・× 外れる の見立てと、理由（条件の ID）を付ける。見立ては Claude の判断なので、そう書く。
- 見本に「良さの条件」の見かた（条件と出典・見立ての表・見本そのものと食い違う所）を足し、一覧の各案に見立ての数の札と「見立てのよい順」を付けて、出し直す。

## 4. ★ を読んで決める

- 人に、気に入った案に ★ を付けてもらう。★ は見本の保存先に書かれるので、Claude が読む（`favs.md`）。読めなければ、★ を付けたブラウザで見本を開き直してもらう。
- つまみごとに ★ を数える。そろった所は決まりにする。割れた所と、★ が多いのに条件に外れる所だけを、質問欄で聞く（条件を添え、推しを出す）。
- 見本が2つ以上あれば、それぞれ読んで同じようにする。

## 5. まとめて残す

- 要約を「決まったこと」「残った問い」「やりたいこと」の3つの見出しで作り、会話に見せる。置き場所は pipe-in の `docs/talk/<日時>-<名前>.md`（`/pipe-talk` と同じ決まり。書く前に `git check-ignore` で無視されているかを確かめ、無視されていなければ書かない）。要約に、アーティファクトの URL を書かない。
- 次の作業の候補を出し、人が選ぶまで行わない。
  - issue：対象のリポジトリに作る。題と本文を全文見せ、承認を得てから作る（`gh issue create` も、GitHub の MCP の道具も同じ）。本文に、秘密・手元の事情・要約のファイルのパスを入れない。作ったら、要約に番号だけを書き足す。
  - 計画ボード：人が流す `/pipe-plan add <やりたいこと>` の行を示す。
  - 実装：pipe-in なら、人が流す `/pipe-in <要件メモ>` の行を示す。Claude からは始めない。
- 見本は、対象のリポジトリの `docs/design/` に置いて、いつでも直して出し直せるようにする。HTML と、README（公開先・番号の読み方・★ の保存先・直し方・手元で開く手順）を置く。置くこと・コミット・push・PR の作成は、人の承認を得てから。
- 直すときは `docs/design/` のファイルを元にし、同じ公開先へ出し直す（★ の保存先が残る）。公開先で直接直したときは、読んで `docs/design/` に写す。

## してはいけないこと

- 見本を見せずに、または ★ を読まずに、形を決めつける。
- 承認なしに、公開・issue・コミット・push・PR の作成をする。
- 開いて確かめていない条件を、出典つきの条件として出す。
- 本物の料金・記録・秘密・手元の事情を、見本・issue・要約に入れる。
