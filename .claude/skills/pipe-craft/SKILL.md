# /pipe-craft — 目的に合わせてパイプを組み立てる

依頼: $ARGUMENTS

（空なら、何のためのパイプか（例：図を作る・仕様とソースの突き合わせ・開発）と、対象プロジェクトの場所を聞いてから始める）

パイプの書き方は README.md の「パイプ」の節にある。ここに書いたのは進め方だけ。
CLAUDE.md の「公開リポジトリとしての注意」を守る。作ったパイプは `pipes/`（.gitignore 済み）に置き、対象プロジェクトの中身（コード・仕様書・社内の名前）を `generator/templates/` などの追跡されるファイルに書き写さない。

## 進め方

### 1. 目的と対象を確かめる

- 何を作りたいか（成果物）、だれが読むか、どこまでを対象にするか、を一言ずつにまとめる。
- 対象プロジェクトのフォルダを決める（指定がなければ聞く）。
- あいまいな点だけを質問にまとめて聞く（聞かなくても決められることは、決めて伝える）。

### 2. 対象を調べる（読むだけ）

- `devpipe-gen list` で、ひな形と、すでにある `pipes/` のパイプを見る。
- 対象のファイルの形（言語・テストのコマンド・ソース／文書／仕様書の場所）を見る。`devpipe-gen new` も自動で調べるが、外れていそうならあとで直す。

### 3. 形を決めて見せる

- ひな形でほぼ足りるなら、それをもとにする（`dev` / `diagrams` / `spec-qa`）。足りなければ、いちばん近いひな形から作って段を足す・削る・指示を変える。
- 段ごとに、名前・表示名・成果物・`access`（read / docs / tests / code）・`review`・Bash の要否・指示の要点を表にして見せ、確認を取る。
  - `access` は、目的を満たす中でいちばん狭い型にする（文書を作るだけなら `read`、別のフォルダに文書や図を置くなら `docs`）。
  - `bash = true` は、テストの実行など本当に必要な段だけ。
  - 人が中身を確かめるべき段（方針が決まる段・最終の成果物）には `review = true` を付ける。
  - 図は Mermaid で書かせる。

### 4. 作って検査する

- `devpipe-gen new <名前> --from <ひな形> --project <対象>` で `pipes/devpipe-<名前>/` を作る（同じ名前があれば止まる。作り直しは、人に確かめてから `--force`）。
- 段を変えるなら `pipe.toml` を、指示を変えるなら `prompts/` のファイルを直す。段を足したら `prompts/` にその段の指示文も足し、`README.md` の段の表も合わせる。
- `devpipe-gen check <名前> --project <対象>` が「問題ありません」になるまで直す。

### 5. 流し方を伝える

- 流すコマンドを示す：`devpipe --pipe <名前> --project <対象> --text "依頼メモ"`（`input` が required なら依頼メモは必須）。
- チャットから流すなら `--pause` を付け、確認の段で `--review approve` / `--review revise --feedback "…"` / `--review quit`（どれも `--pipe <名前>` と一緒に）で答える、と伝える。
- 記録は対象の `<work_dir>/<名前>/`（既定は `docs/pipeline/<名前>/`）に残ることと、対象が公開リポジトリなら `docs/pipeline/` を `.gitignore` に入れるとよいことを伝える。
- **流すのは、人に言われてから。** devpipe を流すと Claude の利用料がかかる。
